# 第 13 章精华：Triton 的布局、通信与调度

[校订正文](../insider-compiler-ch13.md) · [读前导读](../guide/ch13.md) · [笔记目录](README.md)

本章源码基准是 Triton 提交 `47fc046ff29c9ea2ee90e987c39628a540603c8f`。它与本地 LLVM 18.1.8 的 API 基准分开；下述顺序来自该提交 NVIDIA 后端的 `compiler.py`。长清单已按源码和扫描核对，本机没有配套 `triton-opt`，不能把静态核验当成已重跑完整 GPU 编译或执行。

## 1. 每个编译阶段增加一种决策（13.1～13.3.2）

| 表示 | 主要决定什么 | 尚不能据此断言什么 |
| --- | --- | --- |
| Python DSL / TTIR | 每个 program 的张量计算、地址、mask 与控制流 | 一个张量元素已经分配给哪个物理线程 |
| TTGIR | 线程、warp、CTA 及存储布局，专用计算与通信 | 每个逻辑布局转换都能零成本完成 |
| LLVM、NVVM 等 MLIR 方言 | 更低层的地址计算与目标操作 | 已经是原生 LLVM IR 文件 |
| LLVM IR → PTX → CUBIN | LLVM 目标代码生成与 NVIDIA 汇编工具产物 | 仅凭中间 IR 就已测得内核性能 |

Triton program 处理一个逻辑 tile，`program_id` 选择 tile，`arange` 产生 tile 内索引。tile 可能分布在寄存器或共享内存中，并不固定存入共享内存。尾部 mask 与完整指针构造共同保证实际访问有效；某些清单使用 splat 指针、重复 store 地址或未使用的结果，只是结构测试。

固定提交还使用 TritonNvidiaGPU 及自有低层 NVGPU。它们与上游 `nvgpu`、`nvvm` 的命名层次不能随意互换。较新版本的 NVWS 等节点不应强行插入此提交的必经流程。

## 2. 实际流水线不是小节的讲解顺序（13.3.1）

TTIR 阶段依次执行内联、tensor pointer 重写、Combine、规范化、ReorderBroadcast、CSE、循环不变量外提与符号死代码删除。

TTIR 转 TTGIR 时传入目标、warp 数、每 warp 32 线程及 CTA 数。随后 NVIDIA 路径的核心顺序如下，方括号表示条件执行：

```text
Coalesce → [SM80+：F32DotTC] → PlanCTA
→ RemoveLayoutConversions → OptimizeThreadLocality
→ AccelerateMatmul → RemoveLayoutConversions
→ OptimizeDotOperands → CSE
→ [SM80+：CombineTensorSelectAndIf → Pipeline]
→ Prefetch → OptimizeDotOperands → RemoveLayoutConversions
→ ReduceDataDuplication → ReorderInstructions → CSE → SymbolDCE
→ [SM90+：FenceInsertion → TMALowering] → Canonicalize
```

重复的布局清理有用途：矩阵加速、操作数改写和预取会产生新的布局转换，后续要重新传播、折叠和清理。Pass 被加入流水线，不意味着它对每个输入都必然产生改动。

`make_llir` 才执行不支持转换的分解、select/if 合并、SCF→CF、Index→LLVM、共享内存分配分析、TritonGPU 与自有 NVGPU 降级，再处理 Arith 和通用清理。之后才导出原生 LLVM Module、设置目标相关属性、链接外部库并进行 LLVM 优化。因而第 11 项优化虽在 GPU 优化小节介绍，实际位置位于这个降级阶段。

## 3. 先优化逻辑计算，再决定分工（13.3.3）

Tensor pointer 重写把块指针携带的 base、shape、stride、offset 等信息展开为元素指针张量与边界 mask；它不会因此消除全部访存。固定实现处理适用的 `scf.for`、`scf.if` 路径，不能任意推广到所有控制结构。

Combine 把匹配条件成立的 dot、加法、select、masked load 或地址计算合并。零累加器、类型、精度及使用关系是规则的一部分。ReorderBroadcast 则争取先在标量或较小形状上做纯计算，再广播，以减少重复计算；不能对带副作用的任意操作套用交换律。

## 4. 布局是逻辑元素的拥有者与位置（13.3.4）

分布式布局描述逻辑索引到线程、寄存器位置的映射，允许某些元素被多个线程复制持有。shared 布局描述共享内存中的位置。两者都不是简单的“矩阵按行还是按列存储”。

| 布局信息 | 核心参数或作用 | 判断要点 |
| --- | --- | --- |
| blocked | `sizePerThread`、`threadsPerWarp`、`warpsPerCTA`、`order` | 每线程小块、warp 和 CTA 的分工；`order` 首项是优先连续维 |
| CTA 布局 | `CTAsPerCGA`、`CTASplitNum`、`CTAOrder` | 区分 cluster 内 CTA 数、实际切分与复制 |
| slice | 从 parent 去掉一个维度的分布映射 | 不等于已经执行了一次数学归约 |
| MMA | 指令对应的结果与累加器布局 | 编码版本不能等同产品宣传中的 Tensor Core 代数 |
| dot operand | `opIdx` 区分 A/B，关联 parent 与 K 维信息 | 必须与选定矩阵指令兼容 |
| shared | `vec`、`perPhase`、`maxPhase`、`order` 等 | 决定向量组和 swizzle；不是 L2 缓存布局 |

blocked 的基本 CTA tile 在每维的大小为：

$$T_k=\mathrm{sizePerThread}_k\,\mathrm{threadsPerWarp}_k\,\mathrm{warpsPerCTA}_k.$$

张量超过这个基本覆盖范围时，线程继续持有重复分块中的元素。单用“元素总数除以线程数”只能估计平均负载，不能决定最优布局；连续性、对齐、位宽、指令需求与寄存器压力同样重要。

原章的 `16×16` 示例采用 `sizePerThread=[2,2]`、`threadsPerWarp=[8,4]`、`warpsPerCTA=[1,2]`、`order=[1,0]`。两个 warp 的 64 个线程各持有四个元素，恰好覆盖整个张量。线程 0 持有行 0、1 与列 0、1 组成的小块；线程 32 则持有行 0、1 与列 8、9 的小块。相邻逻辑列可能仍属于同一线程，跨过列 7、8 才进入另一个 warp，不能按线性元素序号简单对 32 取模分配。

这个例子也说明 `order` 与底层地址连续性需要共同理解：即使线程持有相邻逻辑列，实际指针若经过转置、非单位 stride 或切片，其全局地址未必相邻。Coalesce 要分析地址数据流，而不只是看张量形状；向 dot 所需布局转换时，则可能又要改变这种最有利于全局加载的分工。

对不带 leading offset 的普通二维 shared 模型，按其连续方向记行列 $r,c$，有：

$$p=(\lfloor r/\mathrm{perPhase}\rfloor)\bmod\mathrm{maxPhase},$$
$$c'=\bigl(\lfloor c/\mathrm{vec}\rfloor\mathbin{\oplus}p\bigr)\mathrm{vec}
+(c\bmod\mathrm{vec}).$$

末项保留组内位置，漏掉它会把不同元素映射到同一地址。以 `perPhase=2,maxPhase=8,vec=2` 为例，行 2 的列 0、1 分别映射到列 2、3。在每个 bank 对应一个 4 字节字的简化模型中，bank 为线性字地址模 32；分析冲突还必须给出同时访问的线程集合和每线程访问宽度。

布局转换可能只涉及线程内寄存器，也可能用 warp shuffle，或通过共享内存 store、同步、load 在跨 warp 之间搬运。`local_alloc` 可以把分布式张量初始化到共享存储，`local_load` 取回分布式寄存器张量；`convert_layout` 本身不等同一次 DRAM load。

## 5. 十二项优化的目的和边界（13.3.5）

下表按原小节编号归纳用途，实际执行顺序见上文。

| 项 | 策略与收益来源 | 必须保留的前提或代价 |
| --- | --- | --- |
| 1. Coalesce | 用 AxisInfo 的连续性、整除与对齐信息选择线程访存分工 | 受元素位宽、形状和 warp 数限制；mask 等操作数及 load 结果布局都要衔接 |
| 2. PlanCTA | 为 dot、reduce、store 等选择 cluster 中的 CTA 切分与复制 | 固定名称为 NVIDIA 的 PlanCTA；cluster 分工不等于 CTA 内线程分工 |
| 3. RemoveLayoutConversions | 布局传播、代价选择、重物化和局部折叠减少转换 | reshape、常量、shared 路径各有匹配条件，不能无条件删除 `cvt` |
| 4. OptimizeThreadLocality | 将适用循环归约拆成线程局部部分与循环外剩余归约 | 需要可识别的累加链；可能改变浮点结合顺序，寄存器累加器也会变大 |
| 5. AccelerateMatmul | 按架构、类型、形状选择 MMA 布局与指令 | Hopper MMA v3 可生成 warp-group dot；Ampere 不走同一条 WGMMA 路径 |
| 6. Prefetch | 提前把 dot 操作数从共享内存加载到寄存器 | 有布局版本、输入路径、K 宽度与循环关系限制；增加活跃寄存器值 |
| 7. Pipeline | 调度加载和计算，异步搬运、多缓冲与跨迭代值传递形成重叠 | 依赖、异步等待、短循环、启动和排空必须正确；不是简单移动 load |
| 8. OptimizeDotOperands | 调整转置、共享分配及逐元素操作与转换的次序 | 包括受支持的 MMA v3 寄存器左操作数路径；不是任意 elementwise 都可移动 |
| 9. ReduceDataDuplication | 为适用的 dot operand 转换安排 shared 中转 | 跳过可快捷转换的部分布局；处理单 GPU 内协作，不是减少多 GPU 通信 |
| 10. ReorderInstructions | 靠近使用位置加载或转换，安排分配、释放及 A/B 加载顺序 | 要满足使用关系与生存期约束；可能用重复执行换取更短活跃区间 |
| 11. DecomposeUnsupportedNVIDIAConversions | 把后端不能直接处理的转换拆成合法序列 | 某模式变成 `local_load → local_alloc → local_load`，多一次 shared 往返并非免费 |
| 12. CombineTensorSelectAndIf | 让相同条件的 if 分支结果替代冗余 select | 同块且 select 支配 if、if 支配 select 的全部使用；中间构造快照不一定是合法完成态 |

优化第 4 项时，原循环的每轮完整归约可以改为先累积线程局部部分，结束后再进行剩余通信。乘法归约的中性值为 1；浮点重结合可能影响舍入、溢出或特殊值，不能从代数结合律推导逐位相同。

第 8 项尤其体现布局与计算相互影响：转换移到 `bitcast`、浮点转换之前，可能让转换靠近原始加载而被消除；Hopper 支持的情形还可以让 A 留在寄存器中，而 B 仍采用共享操作数。不能把所有矩阵乘操作数都概括成同一种存储路径。

## 6. Prefetch 与 Pipeline 的收尾（13.3.5 第 6～7 项）

Prefetch 先为初始共享数据生成子视图与寄存器加载，再把预取值加入新循环的迭代参数，在循环中准备下一轮数据并更新 yield。它重点覆盖**共享内存到寄存器**。本章原 B 更新误接旧值的清单已修正；结构测试仍含循环外及末轮额外读取，实际执行必须保证这些地址有效。

Pipeline 示例重点覆盖**全局内存到共享内存的异步拷贝与计算重叠**。过程是识别 load—dot 链、定阶段、分配 shared 多缓冲、创建拷贝和提交/等待、补齐依赖与未调度操作，再构造前言及新的循环携带状态。缓冲数量取决于生产与使用之间的阶段距离等因素，不恒等于总阶段数。

默认三个阶段编号为 0、1、2，示例 load 在 0、dot 在 2，中间阶段最初可以为空。最大阶段编号是 2，不是 3。对半开循环 $0\le i<N$，剥离后序的教学模型在 $N\ge2$ 时为：

```text
前言：S0(0)；S0(1), S1(0)
稳态：对 i = 0, ..., N-3，执行 S0(i+2), S1(i+1), S2(i)
后序：S1(N-1), S2(N-2)；S2(N-1)
```

每个阶段对应的每次原迭代应恰好出现一次；$N<2$ 可回退原循环。原书后序的 `S1(N)`、`S2(N)` 越过半开边界，不能照搬。

固定实现配置 `peelEpilogue=false` 并支持动态循环，实际示例保留原循环上界，用谓词关闭超范围的提前拷贝，因而不必产生上面的显式后序。例中三个阶段使用两个缓冲槽，新循环携带预取视图及令牌；等待数量 2 允许较新的组继续在途，最终释放前的等待数量 0 则排空相关异步工作。读代码时应同时跟踪槽位、迭代编号和令牌，不能只检查调度表是否把所有操作列出来。

长清单可分三次核对。先只跟踪 A、B 和累加器，确认每次 dot 使用的是对应迭代的数据，下一轮指针与 B 的更新没有接回旧值。再跟踪 shared 子视图、缓冲槽及异步令牌，检查使用与复用之间的等待。最后看 `iter_args`、yield 与结果类型是否成对更新，以及 mask 是否与提前的迭代编号一致。清单 13-46 只展示前言生成后的内部状态，不能单独拿来检验完整变换等价性；检查 SSA 名称是否都出现，也不等于完成类型、支配和运行时内存验证。

## 7. 性能最后要回到资源账本（13.3.6、13.4）

共享内存分配分析考虑显式分配、转换和归约等临时空间，以及对齐、生存期与调用关系。它设置操作的 `allocation.offset` 和模块的 `triton_gpu.shared`，后者进入启动元数据；并非简单给属性改名为 CUDA 声明。

本章 128 字节示例是 f32 临时形状 `[16,1]` 在连续维增加一个 padding 元素：$16(1+1)\times4=128$ 字节。不能误用 64-bit 元素宽度凑出同一个数值。

评估一种方案应同时看全局访存合并、共享 bank 与容量、寄存器压力、同步、指令吞吐和占用率。减少一种成本可能增加另一种成本，后端支持和历史性能数据也有范围。复习时选定一条 load—dot—store 链，能解释其每次布局改变与等待的必要性，再查[本章固定源码与证据](../issues/ch13.md)核对具体规则。
