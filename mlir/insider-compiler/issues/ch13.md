## 13.1：GPU 编程模型与硬件说明

涉及 PDF50–52。

| 原书说法或片段 | 校订 |
| --- | --- |
| “H100包含32个线程” | 一个 NVIDIA warp 通常为32线程；H100包含大量warp、SM等资源，不是整个芯片只有32线程。 |
| “合理规划线程束的大小”、以提升occupancy直接推出性能提高 | NVIDIA warp大小固定；可配置线程块/warp数等。occupancy与性能并非单调关系，要考虑寄存器、共享内存、指令级并行及延迟隐藏。 |
| bank宽度4字节仅限定“Ampere之前” | CUDA资料明确CC5.x及以后连续32-bit字映射32个bank；bank不是容量只有4字节。广播同一字与访问同bank不同字应区分。 |
| Triton着重“在共享内存中以tile方式进行计算” | tile是编程组织方式，值可分布在寄存器等存储层，不是只在共享内存中计算。 |
| 无显式寄存器控制，因此“不具备寄存器的复用能力”，始终达不到硬件理论最大值 | 不成立。编译器仍进行寄存器分配、活跃区间和布局优化；是否达到某种性能目标取决于工作负载和目标，不能由未暴露全部低层接口推出绝对结论。 |
| `BLOCK_SIZE`为每个线程处理的元素数 | 该向量加内核中为每个program实例处理的元素数。程序实例如何映射到warp和线程由编译器及配置决定。 |
| Python中使用`//`、`/* ... */`注释 | 改为`#`，清单1补齐`triton`、`triton.language`导入。 |
| “program_id给算子函数添加一组实例” | `tl.program_id(axis)`查询启动网格相应轴上的program编号，并非静态向函数附加实例的操作。 |

硬件的官方依据、核对日期和详细限制见[硬件独立审计](evidence/hardware-review.md)。Triton接口对应固定提交 [`python/triton/language/core.py`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/python/triton/language/core.py) 中的 `program_id`、`arange`、`load`、`store`，以及[向量加教程](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/python/tutorials/01-vector-add.py)。`arange`的具体范围/幂次等约束仍需配套Triton前端检查；Python语法检查不能替代它。

原书关于XLA、Tensor Comprehensions、TVM的易用性/灵活性/性能评价属于宽泛概括，正文保留项目背景和比较意图，并去掉不可由本章证据支持的绝对结论；不把不同项目全部说成同一种Python DSL。

## 13.2.1：方言清单、操作名及内存语义

涉及 PDF52–54。

1. 原书列出的七类名称为 `Triton`、`TritonGPU`、`TritonNvidiaGPU`、`TritonAMDGPU`、`NVVM`、`NVWS`、`Proton`。固定提交的目录划分并不全与之相符。尤其 NVVM 是上游目标方言，NVIDIA后端另有自定义 **NVGPU**；未发现该提交中的 NVWS 方言定义；已有 Proton 分析工具不意味着当时已定义同名 MLIR 方言。正文完整保留七项和原书“未来迁移”等历史描述，但明确版本范围。
2. 原书称 DSL 算子和Triton方言操作一一对应，过于绝对。前端可能展开多个操作，也会复用arith等社区方言。
3. `cast`、`pointer_arith`、`shape_manipulation`、`spmd`是用途分类，不是相应四个操作。实际操作包括`tt.fp_to_fp`、`tt.addptr`、`tt.trans`、`tt.get_program_id`等；`external_elementwise`改为`extern_elementwise`。`tt.dot`在此提交表达支持形状下的矩阵乘加，不能当作任意向量dot接口。
4. 原书多处把操作定义文件写成`TritonAttrDefs.td`，正文改为各方言真正的`*Ops.td`，布局定义另指向`TritonGPUAttrDefs.td`。
5. `async_commit_group`对异步复制分组，`async_wait`按允许未完成组数等待，并非任意异步执行队列的提交/全部等待接口。
6. `local_dealloc`是可选的共享缓冲区生存期标记。其TD明确说明未显式dealloc时按使用关系推断结束点；原文“避免内存泄漏”容易误导为设备堆分配必须逐一释放，已改。
7. `memdesc_subview`构造子视图描述符，不改变底层内存。`local_load`产生分布式张量，`local_store`写入已有共享缓冲区。
8. NVVM不只是`thread_id`等少量指令；GPU方言也不只有printf。保留原书的用途分类，限定其介绍范围。

依据：[`TritonOps.td`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/include/triton/Dialect/Triton/IR/TritonOps.td)、[`TritonGPUOps.td`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/include/triton/Dialect/TritonGPU/IR/TritonGPUOps.td#L137-L239)、[`TritonNvidiaGPUOps.td`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/include/triton/Dialect/TritonNvidiaGPU/IR/TritonNvidiaGPUOps.td)、[`NVGPUOps.td`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/third_party/nvidia/include/Dialect/NVGPU/IR/NVGPUOps.td)、[`third_party/proton`](https://github.com/triton-lang/triton/tree/47fc046ff29c9ea2ee90e987c39628a540603c8f/third_party/proton)。

## 清单13-4、13-5：张量指针重写的真实含义

涉及 PDF62–64。

原书反复说“直接操作张量数据，而无需再通过指针访问”“scf.for操作仅依赖张量的偏移信息”。这会误导读者认为该pass消除了内存寻址。实际它记录基址、shape、stride、offset，消除高层张量指针，将使用者改写为相应元素指针张量、mask和访存。对于此例没有load/store、只推进指针的循环，携带两个偏移就能表示所需循环状态；不能推广到一般访存。

清单4的第二维stride为0、两个advance增量为0，内联汇编文本`asm_multiple_results`是结构测试占位符，不是可执行PTX。清单5中的`%6/%8`是更新后的两个偏移，不是新读取的张量数据。固定版支持scf.for与scf.if两类控制流中的重写，原文“仅for”遗漏if；while仍不支持，转for必须保持原语义。

依据：[`RewriteTensorPointer.cpp`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/lib/Dialect/Triton/Transforms/RewriteTensorPointer.cpp#L327-L517)、[同名asm_in_loop测试](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/test/Triton/rewrite-tensor-pointer.mlir#L87-L100)。该测试也使用省略指针方言前缀的`<tensor<...>>`自定义打印形式，正文依固定源码保留，结果/函数类型仍写全`!tt.ptr<...>`。

## 清单13-6～13-10：组合与广播重排

涉及 PDF64–67。

表13-1原五项名称为DotAddPattern、SelectMaskedLoadPattern、AddPtrPattern、BroadcastConstantPattern、BroadcastMulReducePattern。固定实现注册的实际类有`CombineDotAddIPattern`、`CombineDotAddFPattern`及反序版本等，不止五个类。dot-add要求原累加器为零、dot结果单一使用；浮点模式还要求maxNumImpreciseAcc为0。不能忽略这些约束，也不能从数学表达推断所有浮点结果逐位不变。

广播重排减少的是逐元素操作在展开后张量上的重复运算，不是单纯“减少broadcast/splat工作量”。broadcast通常扩展长度1的维度，增加秩另有expand_dims。实际模式检查多种条件，也可识别splat形式常量，不是所有出现splat输入的操作都能移动。清单9是插入新操作、尚未清理旧操作的解释性快照，清单10才展示清理后的形式；指针值1只用于类型转换/返回，没有解引用。

依据：[`Combine.td`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/lib/Dialect/Triton/Transforms/Combine.td)、[`Combine.cpp`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/lib/Dialect/Triton/Transforms/Combine.cpp#L225-L247)、[`ReorderBroadcast.cpp`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/lib/Dialect/Triton/Transforms/ReorderBroadcast.cpp)。

## 清单13-11～13-21、图13-5与表13-2～13-6：布局、地址与存储层

涉及 PDF67–74。

1. 元素→线程的布局映射不等于全局内存行/列优先存储。blocked描述分布式张量在线程寄存器中的分布，shared描述共享内存排列，MMA受指令及编译器分块约束。CTA布局还包含原书漏列的CTAOrder，dotOperand还包含漏列的kWidth。

// 清单36

## 表13-8、清单13-48～49：dot 操作数优化

原表保留的四种模式如下；这些是模式简写，不能作为完整 IR：

```text
cvt(trans(src)) #dot_operand
  -> cvt(local_load(trans(local_alloc(src)))) #dot_operand
cvt(elementwise(x)) #dot_operand
  -> elementwise(cvt(x #dot_operand))
dot(alloc(trans() #shared1))
  -> dot(trans(alloc() #shared2))
dot(cvt(lhs #mma) #shared, rhs) #mma
  -> dot(cvt(lhs #mma) #dot_operand, rhs) #mma
```

原表第一项解释“将tt.trans操作分解成triton_gpu.local_load、triton_gpu.local_alloc操作”，忽略了描述符转置及重新选择共享布局；第四项效果写“使用MMA布局数据作为tt.dot指令的操作数”，混淆了 MMA v3 的 warp-group dot 与普通 `tt.dot`。正文保留四行，澄清实际匹配对象。

对应固定源码 [`OptimizeDotOperands.cpp`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/lib/Dialect/TritonGPU/Transforms/OptimizeDotOperands.cpp)：

- `SwizzleShmemConvert`（约L18–73）：匹配二维 `[1,0]` 转置及目标 dot operand 编码，构造考虑 `needTrans=true` 的 shared encoding、`LocalAllocOp`、作用于描述符的 `TransOp`、`LocalLoadOp`；并不是简单删除转置。
- `HoistLayoutConversion`（约L102–203）：仅处理有一个张量结果且输入都是 ranked tensor 的受支持操作，检查向后依赖切片中确实有 load，且 load 后操作符合条件。支持 `FpToFpOp`、`BitcastOp`、纯一元 inline asm 或 arith 方言的一部分操作；排除 `TruncIOp`、`TruncFOp`、`SelectOp`。前移可能复制运算，目的在于减少共享内存往返，不能宣称任意 elementwise 均无条件变换或总能提升性能。
- `FuseTransHopper`（约L213–274）：匹配 `LocalAllocOp` 单一 DotLike 使用者、源 `TransOp`，重建 shared encoding 与 alloc/trans；f16/bf16以外类型需要采用相应操作数次序，不能把注释中的“Hopper”当成省去所有类型约束。
- `MMAV3UseRegOperand`（约L282–320）：真正 pattern 根是 `triton::nvidia_gpu::WarpGroupDotOp`；其 A 来自 `LocalAllocOp`，源和结果为 MMA v3，并须满足 `isMmaToDotShortcut`。改用 `ConvertLayoutOp` 的 dot operand 张量作为 A。

清单48对应 [`test/TritonGPU/dot-operands.mlir`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/test/TritonGPU/dot-operands.mlir#L3-L41) 的 `push_elementwise`。14个原布局别名全部保留；清单49顺序与该测试的 CHECK 数据流一致：load→convert i8→bitcast fp8→fp_to_fp f16→dot。没有将 LLVM18不能识别 Triton 方言当成原书 IR 错误。

## 清单13-52～53：不能直接降级的 shared→dot 加载

原文说“将该操作分解成 triton_gpu.local_alloc 和 triton_gpu.local_load”，但书中结果本身显示三步：从旧共享描述符加载到 blocked、重新分配/初始化适当 shared 布局、再加载为 dot operand。源码 [`DecomposeUnsupportedConversions.cpp`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/DecomposeUnsupportedConversions.cpp#L24-L83) 也明确创建这三个操作。

清单53把原先逐处展开的相同编码改为 `#blocked/#mma/#dot/#shared/#shared1` 别名，全部操作、类型结构、编码值和模块属性保留。清单52/53没有在本机执行；其 `cuda:80` 与演示的 Hopper 风格 shared 布局组合用于展示分解输入，不声称可直接在该硬件上运行完整 kernel。

## 13.3.6、清单13-58～59：共享内存属性与128字节推导

原书关键片段：

> 该属性在编译生成PTX时会被替换成可以识别的shared属性，等价于CUDA的`__shared__`；大小计算为`shape * 64 / 8 = 16 × 64 / 8 = 128`。

- 模板名称是 `ConvertOpToLLVMPattern`，不是原文的 `ConvertOpToLLVM`。Triton实际使用例见 [`ElementwiseOpToLLVMBase.h`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/include/triton/Conversion/TritonGPUToLLVM/ElementwiseOpToLLVMBase.h#L54-L62)。LLVM等MLIR方言与导出的LLVM IR分属不同阶段。

- NVIDIA [`compiler.py`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/third_party/nvidia/backend/compiler.py#L243) 把整数读入 `metadata["shared"]`；[`driver.py`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/third_party/nvidia/backend/driver.py#L194-L222) 把共享字节数传给 `cuLaunchKernel` / `CUlaunchConfig.sharedMemBytes`。这不是直接将属性改名为PTX或CUDA声明。
- [`Allocation.cpp`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/lib/Analysis/Allocation.cpp#L60-L141) 先计算repShape，再按输入/输出连续性求inVec/outVec，为二维以上临时存储添加padding。L272–280再乘实际元素字节数。L38的 `kPtrBitWidth=64` 只在元素为PointerType时使用，本例是f32。
- 本例 `[16,1]` 的第二维截断了MMA/blocked的每线程连续宽度，故inVec=outVec=1，repShape从 `[16,1]` pad成 `[16,2]`，`16*2*32/8=128`。`getUniqueContigPerThread` 的min规则见 [`Dialect.cpp`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/lib/Dialect/TritonGPU/IR/Dialect.cpp#L176-L198)，MMA连续宽度定义见 [`TritonGPUAttrDefs.td`](https://github.com/triton-lang/triton/blob/47fc046ff29c9ea2ee90e987c39628a540603c8f/include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td#L1191-L1198)。128字节的scratch alignment也存在，但不能将本例的数值解释为f32变成64位或只因对齐而翻倍。

根代理另以源码独立复核了本例布局与padding推导，见[allocation-review.md](evidence/ch13-tail/allocation-review.md)。
