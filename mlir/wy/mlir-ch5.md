优化深度学习等高性能计算领域程序（特别是嵌套循环）面临复杂的挑战。这些挑战源于多样化的硬件架构、复杂的内存层次结构、不同计算特征的工作负载，以及巨大的优化权衡空间。

针对以矩阵乘法和卷积运算为中心的深度学习和高性能计算模型，通过发掘和利用程序并行性、时间和空间局部性，以及其他性能来源特性，可以显著提升大规模计算模型性能。这类计算模型中包含大量循环嵌套。循环嵌套通常对大规模数据集执行密集计算，从而导致计算复杂度成倍增加。而且，循环嵌套中的数据访问导致大量的内存读写，从而占用过多内存带宽、增加访存延迟。因此，对循环嵌套进行优化可以减少计算量，提高计算性能，加速模型执行速度，同时还可以改善访存模式，减少缓存未命中（cache miss），从而提高访存效率。

不同编译器有不同优化策略和目标，可根据具体情况选择合适的优化技术实现最佳性能。编译器在进行循环嵌套优化时需要在性能优化和时间／空间开销之间做出权衡，需要识别循环中可独立计算的部分，以便在循环迭代中发现并行计算的机会，并通过向量化和指令级并行增加计算并行度，提高计算性能。

循环访存模式对程序性能有重要影响。为了充分发挥硬件性能，编译器应设计合理的访存模式，以减少缓存未命中并最大限度地利用硬件预取与缓存机制。具体而言，编译器可以通过重排循环中的计算顺序，使计算所需的数据在内存中呈现更高的连续性，从而提升数据局部性并降低访存开销。

为了综合考虑计算并行度、数据局部性、不同 AI 处理器的硬件架构与存储架构，以及模型性能约束类型，MLIR 将多面体编译作为提升依赖性分析及循环变换的效率和可靠性的重要手段，以实现更全面、更高效的编译优化。

本章 5.1 节对多面体编译的基本概念进行了阐述，介绍了多面体模型中的核心要素，并结合矩阵乘法示例分析了影响多面体编译性能的主要因素。5.2 节重点介绍了 MLIR 框架中对多面体编译的支持，简要介绍了 MLIR 中已有的多面体优化 pass 功能。5.3 节通过 AffineLoopTiling 与 AffineLoopFusion 两个具体的多面体优化 pass 实例，详细说明了多面体编译在 MLIR 中的应用方式。

## 5.1 多面体编译的基本概念

传统的循环优化方法，如循环展开（loop unrolling）、循环交换（loop interchange）、循环融合（loop fusion）、循环分块（loop tiling/blocking）等通常针对特定的循环结构和优化目标而设计，在处理复杂的循环嵌套和存在复杂数据依赖的循环时，往往显得力有不逮，且缺乏统一的优化指导理论框架。为了克服这些传统循环优化方法的局限性，研究者提出了通过多面体模型实现循环优化的思路。

### 5.1.1 多面体模型基础

作为多面体编译技术的基础，多面体模型是一种描述多维循环嵌套的灵活表示。越来越多的研究表明，多面体模型是对计算密集型程序进行高效转换的最佳框架之一。适合用多面体模型描述的、各种形式的循环嵌套被称为静态控制部分（Static Control Parts，SCoP），即满足特定条件的最大连续语句集合（语句集合中没有 `goto` 等跳转语句）。SCoP 控制流（循环、条件分支）行为在编译时可以静态分析，且其中的条件和循环边界是循环索引和全局不变参数的仿射函数。这种类型的程序可以用 SCoP 格式表示，SCoP 中的语句包含三个元素，即迭代域（iteration domain）、调度（schedule）和访问关系（access relations）。

> 校订注：“静态分析”并不要求循环界限在编译时都是已知常量；它们可以依赖运行时给定、在所分析区域内不变的符号参数。这里保留原书的 SCoP 介绍，避免把“静态确定”误读成“编译时已知每一次迭代”。

多面体编译主要专注于 SCoP，通过循环迭代优化方法，特别是利用程序并行性及时间和空间局部性，完成循环转换和对应迭代域及调度的生成。

#### 1. 迭代域

从几何表示角度看，多面体模型中的迭代域通常是指由线性不等式描述的循环索引变量取值范围，这些循环索引变量值形成一个多维空间，每个循环迭代对应多维空间中的一个点，整个几何空间由循环上界和下界定义。由于循环索引变量只能取整数值，因此这些点在空间中离散分布。这些离散点构成的集合被称为整数集合（integer set）。整数集合包含了所有可能的循环迭代组合。例如，以下二重循环示例：

```cpp
for (int i = 0; i < N; i++) {
  for (int j = i; j < M; j++) {
    A[i][j] = B[i][j] + C[i][j]; // 语句 S
  }
}
```

上述迭代域可以表示为整数集合

\[
\{(i,j)\in\mathbb{Z}^{2}\mid 0\le i<N,\ i\le j<M\}。
\]

其中，\((i,j)\) 是迭代向量，\(\mathbb{Z}^{2}\) 表示二维整数空间，\(i\) 和 \(j\) 为循环索引，\(N\) 和 \(M\) 为全局不变参数。循环边界约束 \(0\le i<N\) 和 \(i\le j<M\) 是由循环索引 \(i\)、\(j\) 和全局不变参数 \(N\)、\(M\) 构成的仿射不等式组，同时也是描述迭代域约束的仿射不等式组。

在二维空间中，由仿射等式或不等式定义的迭代域是多面体内的整数集合，即整数集合可表示为一个或多个仿射等式和不等式的合取（conjunction）。使用整数集合表示迭代域可以精确描述循环迭代的所有可能组合，为后续依赖分析和循环变换奠定了基础。由有限个仿射等式或不等式定义的凸集（集合中任意两点之间的线段皆完全包含在该集合中）构成多面体；这里关注其中的整数点集，MLIR 用 `IntegerPolyhedron` 表示这类整数约束集合，它是 Presburger 算术处理的核心基础对象之一。

> 校订注：原书把“多面体中的整数点集”与数学上“整数多面体”这一术语混用，并称前者是多面体的特例。整数点集本身通常不是实数空间中的凸集。此处按 MLIR 类的用途说明它表示满足约束的整数点，保留原文关于凸性、约束与整数点的讲解。

循环边界等程序语义限定的约束通常是仿射表达式。为了描述迭代域约束，引入了 Presburger 算术，用于在多面体模型中精确表示循环边界、数据访问关系和依赖关系。

Presburger 算术是一种一阶逻辑，包含整数、加法、减法、比较运算符（\(=,<,>,\le,\ge\)）和存在／全称量词（\(\exists,\forall\)）。它不能表示一般的变量与变量相乘等非线性运算，但可以表示整数常数倍乘法，以及除数为固定正整数的整除和取模关系。使用 Presburger 算术可以精确地描述整数集合及其关系。整数变量元组所在的空间可用 Presburger 空间（Presburger space）描述，整数集合和整数约束关系则由该空间中的约束定义。上述二重循环示例对应的整数集合即为这种空间中的一个集合。上述二重循环的多面体迭代域如图 5-1 所示。

> 校订注：原文“不能表示乘法运算、除法运算、模运算”的限制过宽。例如 \(x=3q+r\)、\(0\le r<3\) 就能表达除以 3 的商和余数。另需区别“空间”和“集合”：MLIR 的 `PresburgerSpace` 记录变量数量和类别，不存储定义集合的约束；参见 `mlir/include/mlir/Analysis/Presburger/PresburgerSpace.h` 和 `IntegerRelation.h`。Affine 对常量除数的支持见 `mlir/docs/Dialects/Affine.md`。

**图 5-1 二重循环的多面体迭代域。** 横向限制为 \(0\le i<N\)，纵向限制为 \(i\le j<M\)，斜边为 \(j=i\)。因此每一列从对角线上的整数点开始，向上到 \(j=M-1\) 为止；\(i=N\) 和 \(j=M\) 是不包含的上界。若 \(N>M\)，\(i\ge M\) 的外层迭代没有对应的内层迭代点。这里明确保留原图的横纵坐标、斜边及两条上界，不能把它误画成矩形域。

从程序执行角度看，迭代域是语句的实例集合。在循环体内，每次循环迭代执行循环体中的语句，且每一次执行对应语句的一个实例。因此，迭代域可以看作是程序中所有语句执行实例的集合。每个实例由循环索引的具体取值唯一确定。在 \(n\) 层循环中的语句实例可以用一个整数 \(n\) 元组表示。例如，在上述二重循环示例中，对语句命名的标识符为 \(S\)，二层循环可用二元整数元组 \((i,j)\) 表示语句实例的维度，语句实例的完整表示为 \(S(i,j)\)。从程序执行角度看，符合 SCoP 格式的程序总是导致由仿射不等式界定的多面体迭代域，图 5-1 中的每个点 \((i,j)\) 也可以表示一个多面体语句实例。

为了支持整数集合、Presburger 空间和整数多面体，MLIR 定义了 `IntegerSet` 类、`PresburgerSpace` 类和 `IntegerPolyhedron` 类。

`IntegerSet` 类的功能是表示 IR 中的整数集合，该集合由一个或多个仿射等式和不等式的合取定义。`IntegerSet` 类主要用作操作的属性及 `affine.if` 操作的条件。例如，当常数 \(s_0=4\) 时，三角形整数集合

\[
\{(d_0,d_1)\mid 0\le d_0<s_0\ \land\ 0\le d_1\le d_0\}
\]

在二维坐标系上构成的整数三角形区域如图 5-2 所示。

**图 5-2 三角形整数集合。** 横轴为 \(d_0\)，纵轴为 \(d_1\)，对角线为 \(d_1=d_0\)，右侧竖线为排除的上界 \(d_0=s_0=4\)。图中的点逐列为 \((0,0)\)；\((1,0),(1,1)\)；\((2,0),(2,1),(2,2)\)；\((3,0),(3,1),(3,2),(3,3)\)，共 10 个整数点。

与整数集合相关的标识符被分为维度标识符和符号标识符两类。在 `affine_set` 语法上，维度标识符被括在圆括号内，符号标识符被括在方括号内。维度标识符和符号标识符的详细介绍见 5.2.1 节。

```mlir

```

与 `AffineMap` 类似，`IntegerSet` 是不可变的（immutable），意即一旦创建了一个 `IntegerSet` 对象，便不能修改其内容，这样可以避免在不同编译阶段跟踪 `IntegerSet` 对象变化，简化编译器分析和优化过程。`IntegerSet` 主要用于在 IR 中表示仿射约束的合取，而不是提供复杂集合运算和分析的可变数据结构。这类复杂运算和分析由仿射约束分析类完成，原书在此称为 `FlatAffineConstraints` 类。

> 校订注：原书“仅能表示少量仿射约束”不应理解为存在固定的小数量上限。当前仓库相关分析类为下文介绍的 `FlatLinearConstraints`、`FlatLinearValueConstraints` 和 `FlatAffineValueConstraints`；保留原书旧类名以便辨认版本差异。

`PresburgerSpace` 类的功能是表示整数变量的元组空间。元组空间可以直观地理解为一个多维整数空间，其中的每个维度对应一个变量。空间中的变量分为维度变量（dimension variable）、符号变量（symbol variable）和局部变量（local variable）三种类型。其中，维度变量表示空间的基本维度，即空间中的坐标。

维度变量又可进一步分为定义域（domain）和值域（range）。定义域和值域之间的对应关系被称为关系（relation）。这种关系通过仿射表达式定义，并且可以被约束条件进一步限制。定义域表示关系的输入变量，值域表示关系的输出变量。

符号变量表示固定但未知的值。带有符号变量的空间可以看作是由符号变量索引的一系列空间。例如，上述二重循环示例中的符号变量 \(N\) 和 \(M\) 都表示固定但未知的整数值。由符号变量 \(N\)、\(M\) 定义的空间可以看作是由符号变量 \(N\)、\(M\) 索引的一系列空间，每个具体值的 \(N\)、\(M\) 组合对应一个特定空间。

局部变量表示存在量化变量（existentially quantified variable），其作用域仅限于当前约束表达式。在 Presburger 空间中，局部变量和存在量词常用于表示更复杂的约束关系，例如，循环变换中的依赖关系。假设有集合描述：

\[
\{x\in\mathbb Z\mid \exists q\in\mathbb Z:\ 1\le x\le7,\ x=2q\}。
\]

其中，\(x\) 是维度变量，\(q\) 是局部变量，\(\exists\) 是存在量词，表示“至少存在一个”。该描述的含义是，对于给定 \(x\)，如果存在至少一个 \(q\) 值，使得约束 \(1\le x\le7\) 和 \(x=2q\) 成立，则 \(x\) 有效。集合描述中的局部变量 \(q\) 是存在量化变量，意即存在使得 \(x\) 满足给定约束的 \(q\)。对于上述描述，如果 \(q\) 等于 1、2、3，则 \(x\) 等于 2、4、6，满足约束 \(1\le x\le7\)，因此，满足条件的 \(x\) 集合是 \(\{2,4,6\}\)。

从数学角度看，存在量化可以被视为投影。在上面的例子中，可以将 \(q\) 从满足给定约束的所有 \((x,q)\) 组合构成的集合 \(\{(2,1),(4,2),(6,3)\}\) 中经投影（projection）消去，得到 \(x\) 集合 \(\{2,4,6\}\)。即消去局部变量 \(q\) 的投影可以将 \((x,q)\) 组合构成的高维空间映射到 \(x\) 集合的低维空间。经投影过程后，仅保留 \((x,q)\) 集合中的 \(x\) 值，忽略 \(q\) 值。\((x,q)\) 集合的投影过程如图 5-3 所示。

`PresburgerSpace` 类中定义了获取各种变量数量接口和检查空间相容性接口等，如 `getNumDomainVars()` 可获取定义域变量的数量，`getNumRangeVars()` 可获取值域变量的数量，`isCompatible()` 可检查两个空间是否兼容，`isEqual()` 可检查两个空间是否相等。如果除局部变量外，两个空间的各种变量的数量相同，则称两个空间兼容；如果两个空间的各种变量的数量完全相同，则称两个空间相等。

#### 2. 调度

迭代域仅描述了语句的实例集合，但不指定语句实例的执行顺序，迭代域中的语句实例可以通过各种可能的合法顺序遍历。多面体模型中指定语句执行顺序的过程被称为调度。调度在分析语句之间的数据依赖关系的基础上，通过对循环索引变量应用仿射变换，将语句实例映射到多维逻辑时间戳（time-stamp），实现循环中语句执行顺序的重排，达到优化数据局部性、减少数据依赖引起的同步开销的目的，并尽可能为并行执行创造条件。换言之，调度可被表示为语句实例到多维时间戳向量的映射。在最简单的原始顺序调度中，每个循环索引对应时间戳向量的一个维度。例如，对于上述二重循环示例中的语句 \(S\)，其调度可表示为 \(\{S(i,j)\to(i,j)\}\)，即给循环执行时的每个语句实例 \(S(i,j)\) 分配一个时间戳向量 \((i,j)\)。语句实例按其时间戳的递增顺序执行。

对于 \(n\) 层循环嵌套内的某个语句 \(S\)，可以为其指定一个 \(n\) 元组 \((i_1,i_2,\ldots,i_n)\) 表示其时间戳，其中，\(i_k\)（\(1\le k\le n\)）是第 \(k\) 层循环对应的顺序坐标。这些坐标共同按字典序（lexicographic order）比较。字典序在前的语句实例先执行，字典序在后的语句实例后执行。

多维向量的字典序先比较第一个维度的值。如果第一个维度的值不同，较小者排在前面；如果第一个维度的值相同，则比较第二个维度的值，以此类推，直到所有维度比较结束。例如，有两个向量 \([a,b]\) 和 \([c,d]\)。如果 \(a>c\) 或 \(a=c\) 且 \(b>d\)，则向量 \([a,b]\) 的字典序大于向量 \([c,d]\)，记为 \([a,b]>_{\mathrm{lex}}[c,d]\)（原书用 \(\gg\) 表示此关系）。

一种简单、直观的优化循环迭代方法是通过引入仿射变换改变循环的执行顺序。为了描述简单，假设有如下一维循环代码：

<!-- 原书第 163 页；PDF 第 7 页。 -->

```cpp
for (i = 0; i < 3; i++)
  a[i] = a[i] + 2; // 语句 S
```

上述代码片段是一个简单的 SCoP，因为其循环界限 `i = 0` 和 `i < 3` 是由常量（也可以是外层循环索引变量）组成的线性表达式，其数组访问模式 `a[i]` 依赖于循环索引变量，循环控制可以用复合线性不等式 \(0\le i<3\) 表示，且循环体内的操作是一个简单的加法操作，没有复杂的控制流或依赖关系。这些都符合 SCoP 的条件。

从几何表示角度来看，上述循环的迭代域可以表示为一维整数点集 \(\{(i)\mid0\le i<3\}\)，其中每个点对应语句 `a[i] = a[i] + 2` 的一次执行实例，所以，上述循环的迭代域也可描述为以下 3 次执行：

```text
S(0): a[0] = a[0] + 2;
S(1): a[1] = a[1] + 2;
S(2): a[2] = a[2] + 2;
```

由于示例代码仅为一维循环，因此此处的语句实例的时间戳只有一维，语句实例的字典序仅需按循环索引变量 \(i\) 进行比较。该调度可表示为 \(\{S(i)\to(i)\}\)。

为了优化或满足其他需求（如特定硬件要求、数据依赖分析的结果等），希望在不改变循环约束的前提下，重排上述循环迭代顺序，如反转运行时语句执行顺序，使得对原始 \(i\) 的遍历变成从 \(i=2\) 到 \(i=0\)，得到如下语句执行顺序：

```text
时刻 0，执行 S(2): a[2] = a[2] + 2;
时刻 1，执行 S(1): a[1] = a[1] + 2;
时刻 2，执行 S(0): a[0] = a[0] + 2;
```

> 校订注：原书把反转后第一行仍标为 `S(0)`，实际用的是新执行序号，而此前 `S(i)` 指原始语句实例。这里分开标明“时刻”和“原始实例”，避免把调度变换误认为改变了原始实例的身份。

为了实现上述语句执行顺序，可定义变换函数 \(f(i)\) 实现新循环索引变量 \(i\) 到原始访问索引的映射，使得执行顺序反转。将原循环代码修改如下：

```cpp
for (i = 0; i < 3; i++)
  a[f(i)] = a[f(i)] + 2;
```

假设 \(f(i)\) 是仿射函数且形式为 \(f(i)=a\times i+b\)。其中，\(a\) 和 \(b\) 是常数。为了达到语句执行顺序反转的目的，将 \(i=0,1,2\) 代入变换函数 \(f(i)\)，其函数值应为：

```text
f(0) = 2
f(1) = 1
f(2) = 0
```

将这些条件代入方程 \(f(i)=a\times i+b\)，可得：

```text
f(0) = a × 0 + b = 2  => b = 2
f(1) = a × 1 + b = 1  => a + 2 = 1 => a = -1
f(2) = a × 2 + b = 0
```

<!-- 原书第 164 页；PDF 第 8 页。 -->

所以，变换函数为 \(f(i)=-i+2\)。将 \(f(i)\) 代入循环代码可得：

```cpp
for (i = 0; i < 3; i++)
  a[-i + 2] = a[-i + 2] + 2; // 语句 S
```

上述代码的语句执行序列即为：

```text
时刻 0，执行 S(2): a[2] = a[2] + 2;
时刻 1，执行 S(1): a[1] = a[1] + 2;
时刻 2，执行 S(0): a[0] = a[0] + 2;
```

对循环索引变量做仿射变换的函数 \(f(i)\) 实际上实现了另一种调度方式。在这种调度方式中，迭代域本身没有变化（即循环索引变量 \(i\) 的取值范围没有变化），但原始语句实例的执行顺序被调度方式改变。

> 校订注：原书称 \(ai+b\) 为“线性函数”，本章按严格数学术语写为“仿射函数”。上述代码用新执行索引计算原始访问索引；若直接给原始实例写调度，则为 \(\theta(S(i))=2-i\)。本例反转映射恰好等于其逆映射，两种写法数值相同，但概念不同。

#### 3. 访问关系

语句中的每个数组引用通过访问关系表达。访问关系可将语句实例映射到一个或多个被读写的数组元素。这种映射以循环索引和全局参数的仿射函数表达。对标量变量的访问可被视为数组访问的特例，即标量变量可看作零维数组。

假设循环迭代中的语句实例 \(S(i,j)\) 有数组访问 `A[i + 2*j]`，则可以用仿射函数 \(f(i,j)=i+2j\) 表达该迭代空间中迭代点到数组元素索引的映射。该映射关系表示为整数关系（integer relation）\(\{(i,j,k)\mid k=i+2j\}\)，其中，\((i,j)\) 是迭代向量，\(k\) 是数组索引。整数关系的一些基本运算，如复合、投影等，在后续的依赖分析和变换中会用到。为了描述整数关系，MLIR 定义了 `IntegerRelation` 类，用于表示 Presburger 空间中的点集，该点集满足一系列仿射约束。仿射约束可以是以下等式和不等式两种形式：

\[
c_0x_0+c_1x_1+\cdots+c_{n-1}x_{n-1}+c_n=0,
\]

\[
c_0x_0+c_1x_1+\cdots+c_{n-1}x_{n-1}+c_n\ge0。
\]

其中，\(c_0,c_1,\ldots,c_n\) 是整数系数，\(x_0,x_1,\ldots,x_{n-1}\) 是整数变量，\(n\) 是空间中整数变量的总数。这样的关系对应于凸多面体中的整数点集。例如，整数关系 \((x)\to(y):(1\le x\le7,\ x=2y)\) 描述了 \(x\) 和 \(y\) 之间的关系，其中 \(x\) 的范围约束是 1～7，且 \(x\) 必须是 \(y\) 的两倍。

该整数关系可以被视为凸多面体中的整数点集 \((x,y):(1\le x\le7,\ x=2y)\)。该整数关系包含满足 \(1\le x\le7\) 和 \(x=2y\) 约束的 \((x,y)\) 集合 \(\{(2,1),(4,2),(6,3)\}\)。该点集在 Presburger 空间中的等式仿射约束为 \(x-2y=0\)，不等式仿射约束为 \(x-1\ge0\) 和 \(7-x\ge0\)。

> 校订注：因此实际定义域为 \(\{2,4,6\}\)，不是 1～7 的全部整数；实际值域为 \(\{1,2,3\}\)。原书把外部范围约束直接称作“定义域”，此处予以区分。

因此，整数关系既描述了整数变量之间的关系，也定义了满足这种关系的整数变量构成的集合。MLIR 中的 `IntegerRelation` 类与前文所述 `PresburgerSpace` 类共同用于表示整数关系。`IntegerRelation` 类中维护的 `PresburgerSpace` 实例 `space` 定义了变量的空间结构，而 `IntegerRelation` 类在该空间上施加约束，等式和不等式约束系数（即 \(c_0,c_1,\ldots,c_n\)）以矩阵形式保存在 `IntegerRelation` 类成员变量 `equalities` 和 `inequalities` 中。

<!-- 原书第 165 页；PDF 第 9 页。上段跨页。 -->

为了操作 `equalities` 和 `inequalities` 系数矩阵，`IntegerRelation` 类提供 `addEquality()`、`removeEquality()`、`addInequality()`、`removeInequality()` 等辅助函数，在增加或减少等式或不等式约束时增减系数矩阵中的对应元素。

此外，`IntegerRelation` 类还提供用于约束操作的辅助函数，如 `unionBoundingBox()` 函数、`getConstantBound()` 函数等。其中，`unionBoundingBox()` 函数可计算包围两个集合的边界框（bounding box），使得新得到的约束能够包含两个集合的所有点。在能够比较和合并对应上下界的情况下，其计算方式是对每个维度变量的下界取最小值、上界取最大值，同时保留符号变量的表达形式。例如，对于由维度变量 `d0` 和符号变量 `s0` 表示的两个集合约束 `s0 + 3 <= d0 <= s0 + 15` 和 `s0 + 1 <= d0 <= s0 + 8`，经 `unionBoundingBox()` 函数合并后得到的新约束为 `s0 + 1 <= d0 <= s0 + 15`。新约束的下界取最小值 `s0 + 1`，上界取最大值 `s0 + 15`。通过这种方式，该函数在这个例子中得到紧密包围两个输入集合的约束。

> 校订注：此接口返回 `LogicalResult`，有空间一致性等前提，不保证对任意两个符号约束系统总能成功构造所谓“最小”边界框。正文保留原书可成立的具体例子。

MLIR 中的 `IntegerPolyhedron` 类、`FlatLinearConstraints` 类和 `FlatLinearValueConstraints` 类等都是 `IntegerRelation` 类的子类，按照继承关系，各子类从基础的整数关系表示到高级的仿射分析和优化，逐步增强功能，以适应不同层次的编译优化需求。`IntegerRelation` 类及其子类的继承关系如图 5-4 所示。

**图 5-4 IntegerRelation 类及其子类。** 原图从上到下为以下完整继承链；每个下层类继承紧邻的上层类：

```text

            └─ FlatLinearValueConstraints

```

与 `IntegerRelation` 类似，`IntegerPolyhedron` 类表示的 Presburger 空间点集同样满足一系列等式和不等式仿射约束，但 `IntegerPolyhedron` 类强调集合表示，不区分定义域和值域变量，其 Presburger 空间的定义域变量数量为零。

`IntegerPolyhedron` 类可以对由 `affine.for`、`affine.if` 等操作形成的循环结构和整数多面体约束建模。例如，对于以下示例代码：

```mlir
#map0 = affine_map<()[s0, s1] -> (4 * s0 + 3)>

#cond = affine_set<(d0)[s0] : (d0 >= 0, s0 - d0 - 1 >= 0)>

%ub = affine.apply #map1()[%M, %N]
affine.for %i = %lb to %ub step 1 {
  affine.if #cond(%i)[%K] {
    // Loop body
  }
}
```

> 校订注：原书把 `affine.apply` 内嵌在 `affine.for` 的边界位置，又把条件直接写作 `affine.if (%i >= 0, %i < %K)`，这不是合法的 MLIR 文本语法。这里仅修正为独立的 `affine.apply` 结果和整数集合条件，保留两个原始映射、步长及循环体结构；`%M`、`%N`、`%K` 是外部给定的、在此处可用作符号的 `index` 值，代码仍为上下文片段。

由于 `PresburgerSpace` 实例是 `IntegerRelation` 类中的成员变量，而 `IntegerPolyhedron` 类继承自 `IntegerRelation` 类，因此也间接持有 `PresburgerSpace` 实例。上述维度变量、符号变量、局部变量（如果存在）由该 `PresburgerSpace` 实例维护。而且，`IntegerPolyhedron` 类在 `IntegerRelation` 类功能的基础上进行了限制。不同于 `IntegerRelation` 类对一般关系的描述，`IntegerPolyhedron` 类专注于处理多面体约束，不区分关系的输入元组和输出元组，仅支持集合类型。

`FlatLinearValueConstraints` 类的派生类 `FlatAffineValueConstraints` 类在 `FlatLinearValueConstraints` 类的基础上增加了分析和处理 Affine 操作（包括 `affine.for`、`affine.parallel`、`affine.if` 操作）约束功能和操作仿射约束等功能，加强了对各类变量的管理和处理能力，使其更适用于 MLIR 的仿射变换相关功能。`FlatLinearValueConstraints` 类在下文所述的 AffineLoopTiling pass 中将作为描述约束的关键数据结构，在分析循环迭代空间中读写操作依赖关系、计算内存占用量大小等方面发挥重要作用。

#### 4. 依赖关系

如果将上述“调度”中的一维循环代码示例略做修改：

```cpp
for (i = 0; i < 3; i++)
  a[i + 1] = a[i] + 2; // 语句 S
```

在上述循环中存在数据依赖关系，即后续迭代计算结果依赖于前次迭代计算结果。具体来说，上述代码的数据依赖关系如下：

```text
S(0): a[1] <- a[0]
S(1): a[2] <- a[1]
S(2): a[3] <- a[2]
```

<!-- 原书第 167 页；PDF 第 11 页。上面的代码块跨页。 -->

其中，符号 `<-` 表示数据流向，即从右侧数组元素读出数据，并将计算结果写入左侧数组元素。

为了确保程序的正确性和可靠性，调度不能破坏依赖关系。依赖关系可以表示为语句对集合。语句对的前一条语句是数据生产者，后一条语句是数据消费者。例如，在上述循环示例中，`S(0)` 向 `a[1]` 中写入数据，`S(1)` 从 `a[1]` 中读出数据，因此可以将 `S(0)` 看作数据生产者，将 `S(1)` 看作数据消费者。以此类推，可以将上述循环示例对应的依赖关系表示为语句对集合

\[
\{(S(i),S(i+1))\mid0\le i<2\}。
\]

> 校订注：原书上界写为 \(i\le2\)，会引入不存在的 `S(3)`，应为 \(i<2\)，即只有 `S(0) → S(1)` 和 `S(1) → S(2)` 两条相邻依赖。

如果经变换后循环的调度仍尊重原循环的依赖关系，则可以说，变换后循环的调度是合法的。否则，循环变换不正确。例如，将上述变换函数 \(f(i)=-i+2\) 应用于上述修改后的一维循环代码示例：

```cpp
for (i = 0; i < 3; i++)
  a[-i + 2 + 1] = a[-i + 2] + 2; // 语句 S
```

新顺序中的数据访问如下：

```text
时刻 0，执行原 S(2): a[3] <- a[2]
时刻 1，执行原 S(1): a[2] <- a[1]
时刻 2，执行原 S(0): a[1] <- a[0]
```

如果像原书那样以新执行序号给实例重新编号，原有的生产者到消费者关系就要求新编号中的 \(S(i)\) 先于 \(S(i-1)\)（\(1\le i\le2\)）执行。可以发现，这个要求与按新编号递增的实际执行方向相反。在原始循环中，`S(i)` 依赖于 `S(i-1)`；但上述反转执行先读 `a[2]`，之后才写入原本应供其使用的新 `a[2]`，同样先读 `a[1]`，之后才生成新 `a[1]`。这意味着变换函数 \(f(i)\) 导致的执行顺序改变破坏了原始的数据依赖关系，因此该循环变换不正确。

> 校订注：原书把 \(\{(S(i),S(i-1))\mid1\le i\le2\}\) 称为“新的依赖关系”，容易误认为反转后的程序仍保持原来的真依赖、只是箭头变向。严格地说，它是在新编号下必须保留、但已被违反的原始生产者—消费者顺序；实际反转后读到的是尚未更新的值。

多面体模型需要为每个被分析的程序构造依赖图。依赖图是一个有向图，其中的节点可以是语句、操作或循环嵌套结构，其中的有向边表示节点之间的依赖关系。有向边从某个节点（称为依赖的源点）出发，指向另一个节点（称为依赖的汇点），也称为汇点依赖于源点。

在循环嵌套中，可以使用迭代空间中源点和汇点之间的依赖距离来刻画依赖关系。假设 \(n\) 层循环嵌套结构中的语句 `S1` 在迭代点 \(\mathbf i=(i_1,i_2,\ldots,i_n)\) 写入某地址，语句 `S2` 在迭代点 \(\mathbf j=(j_1,j_2,\ldots,j_n)\) 读同一地址，则距离向量

\[
\mathbf d(\mathbf i,\mathbf j)=\mathbf j-\mathbf i
=(j_1-i_1,j_2-i_2,\ldots,j_n-i_n)
=(d_1,d_2,\ldots,d_n)。
\]

其中的分量 \(d_k\) 是在第 \(k\) 层循环中 `S2` 相对于 `S1` 的距离。在以下三层循环嵌套示例中，语句 `S1` 自身存在真依赖（true dependence）：

```cpp
for (int m = 1; m < M; m++) {
  for (int n = 1; n < N; n++) {
    for (int k = 1; k < K; k++) {
      A[m + 1][n][k - 1] = A[m][n][k] + 3; // S1
    }
  }
}
```

<!-- 原书第 168 页；PDF 第 12 页。上面的代码块跨页。 -->

即语句向内存地址单元写入数据后，从相同内存地址单元读出数据。例如，在迭代点 \(\mathbf j=(2,5,3)\) 中读取的数据 `A[2][5][3]` 是之前迭代点 \(\mathbf i=(1,5,4)\) 写入的数据，在迭代点 \(\mathbf i\) 处的语句 `S1` 实例为源点，在迭代点 \(\mathbf j\) 处的语句 `S1` 实例为汇点，两者之间的距离向量 \(\mathbf d(\mathbf i,\mathbf j)=(2-1,5-5,3-4)=(1,0,-1)\)。

对于上述的依赖，如果只关心先后顺序（即方向），那么可以将距离向量抽象为长度为 \(n\)、用 `<`、`=`、`>` 表示各维相对顺序关系的方向向量 \(\mathbf D(\mathbf i,\mathbf j)\)，其第 \(k\) 个分量 \(D_k\) 定义为：若 \(d_k>0\)，则 \(D_k\) 为 `<`；若 \(d_k=0\)，则 \(D_k\) 为 `=`；若 \(d_k<0\)，则 \(D_k\) 为 `>`。由方向向量定义可知，方向向量描述的是某个内存访问是否依赖于前、后循环迭代。在上述三层循环嵌套示例中，语句 `S1` 的方向向量为 `(<, =, >)`。

MLIR 中定义了结构体 `DependenceComponent`，用于描述某个 `affine.for` 操作的依赖方向和距离向量：

```cpp
struct DependenceComponent {
  // The AffineForOp Operation associated with this dependence component.
  Operation *op = nullptr;
  // The lower bound of the dependence distance.
  std::optional<int64_t> lb;
  // The upper bound of the dependence distance (inclusive).
  std::optional<int64_t> ub;
  DependenceComponent() : lb(std::nullopt), ub(std::nullopt) {}
};
```

区间 `[lb, ub]` 可以同时表示距离和方向。如果 `lb == ub`，则区间 `[lb, ub]` 表示距离向量的分量；如果 `lb < ub`，则区间 `[lb, ub]` 表示方向向量的分量。在 AffineLoopTiling pass 中的检查分块合法性和 AffineLoopFusion pass 中的检查源、目的访问依赖关系功能部分均涉及方向和距离向量的具体应用。

> 校订注：以上结构与 `mlir/include/mlir/Dialect/Affine/Analysis/AffineAnalysis.h` 一致。`lb` 或 `ub` 为 `std::nullopt` 表示对应方向无界；非单点区间还可包含多个方向，不一定只能归为 `<`、`=`、`>` 中的一个。

### 5.1.2 多面体编译影响因素

局部性和并行性是影响程序性能的两个关键因素。本节以常见的三重循环矩阵乘累加计算为例，着重从时间局部性与空间局部性的角度出发，分析经典的矩阵乘累加计算过程中的存储访问行为，揭示潜在的性能瓶颈。然后结合并行性特征，证明多面体编译优化方法的必要性和价值。

三重循环矩阵乘累加计算伪代码如下：

```text
for (i = 0; i < n; i++)
  for (j = 0; j < n; j++)
    for (k = 0; k < n; k++)
      C[i, j] += A[i, k] * B[k, j]
```

<!-- 原书第 169 页；PDF 第 13 页。 -->

其中，矩阵 \(C\) 的每个元素 `C[i][j]` 是由矩阵 \(A\) 的第 \(i\) 行与矩阵 \(B\) 的第 \(j\) 列之间的乘加计算得到的。

局部性是指程序在访问数据时存在某种模式，使当前被访问数据或邻近数据在一段时间内可能再次被访问。局部性可以分为时间局部性（temporal locality）与空间局部性（spatial locality）两类。

时间局部性是指程序在一段时间内多次访问相同内存位置的数据。例如，循环中某中间结果变量在多次迭代中重复使用，这体现了时间局部性。处理器中的缓存层次结构设计利用时间局部性，使得重复使用的数据被缓存到更靠近处理器的缓存层级，以便其在一段时间内可被快速重用。

空间局部性是指程序在一段时间内对邻近内存位置的数据进行访问。缓存行（cacheline）可以利用空间局部性提高数据的访问效率。如果数组元素按照连续的内存布局存储，那么当硬件存储单元加载数组某个元素时，可以一次在一个缓存行中加载多个元素，即同一缓存行中将包含该元素的多个相邻元素。在矩阵乘累加计算的内层循环中，如果后续加载的矩阵元素已在先前装入的缓存行中，那么内积计算将从缓存中获取元素，而不需要从主存中获取。这减少了主存访问的延迟，提高了数据的访问速度。此外，预取（prefetching）技术可以进一步利用空间局部性改善访问效率。当加载矩阵的某一行时，预取技术可以在加载当前行的同时预取下一行或下几行的数据至缓存中。

并行性指的是程序中可以被同时执行的指令或任务的数量。计算密集型应用（如矩阵乘）往往具有丰富的指令级、数据级和任务级并行性。在现代处理器（特别是 GPU）架构中，充分挖掘并行性是实现高性能的另一关键手段。程序可以利用并行性同时发起多个读写操作（包括向量化操作、并行预取等），从而在没有数据依赖的前提下隐藏访存延迟，提高执行效率。

多面体编译优化的本质是在进行循环优化时，综合运用循环顺序、分块、并行等优化方法组合，围绕局部性和并行性展开设计和变换。

现代计算机系统具有多种多样的硬件，如 CPU、GPU、FPGA 等，各自有不同的体系结构。同时，存储系统也分为多级缓存（L1、L2、L3）、片上存储、片外存储等，形成复杂的存储层次结构。为了更好地理解和量化缓存行为对性能的影响，通常会引入理想化的模型，从理想缓存模型的角度评估矩阵乘累加性能。

理想缓存模型假设存在一个具有容量 \(M\)、缓存行长度为 \(B\) 的理想高速缓存，其采用完全相联（full associativity）与最优替换（optimal replacement）策略。性能衡量指标包括计算工作量 \(W\) 及缓存未命中次数 \(Q\)，后者反映了主存与缓存之间的数据传输成本。

> 校订注：原书将 \(M\)、\(B\) 的单位定义为字节，但后面的公式直接以矩阵元素计数。为保证量纲一致，下文统一令 \(M\) 为缓存可容纳的元素数、\(B\) 为每行元素数；若每个元素占 \(e\) 字节，则分别用缓存字节数除以 \(e\)、缓存行字节数除以 \(e\) 得到这两个量。

在上述矩阵乘累加中，其计算工作量 \(W=O(n^3)\)。但在实际执行中，性能瓶颈往往在于数据的加载与存储，尤其是在 GPU 等现代处理器架构上，从寄存器到共享内存、再到 L2 缓存和全局内存，各层之间的访问延迟和带宽差异巨大，访存成本可能远高于算术操作。在多级存储架构中，对于将大量执行时间花费在片外存储访问的内存受限型模型，很难仅通过提升指令级并行性消除其片外存储访问的成本。如何优化矩阵乘法中的数据访问模式，以最大化局部性、减少高延迟的全局内存访问，是提升性能的关键所在。这时，缓存命中与否通常直接决定了数据访问的快慢。为了提升性能，总是希望数据在被访问之后能够在缓存中保留足够长的时间，以便后续访问能够命中。这涉及时间局部性的关键量化指标：重用距离（reuse distance）。

<!-- 原书第 170 页；PDF 第 14 页。上段跨页。 -->

重用距离通常指对同一数据的相邻两次访问之间所访问的不同数据项的数量。重用距离越短说明时间局部性越强，数据在下一次访问时很可能仍驻留在缓存中，因此缓存命中率越高；反之，则说明缓存中的数据可能被其他数据替换，因此缓存命中率越低。

> 校订注：原书写“所间隔的访问数”，没有区分重复访问。直接计数全部访问通常称重用时间／访问间隔，而以不同数据项数定义的重用距离更直接反映缓存容量压力。具体缓存行为还取决于缓存行、相联度和替换策略。

在上述矩阵乘累加的每一次 `C[i][j] += A[i][k] * B[k][j]` 操作中，假设矩阵内存布局为行优先（row major）。`C[i][j]` 的内存地址唯一并且在最内层 \(k\) 维循环中重复使用，对矩阵 \(C\) 的访问则具有良好的时间局部性，重用距离为 \(O(1)\)，可为其分配寄存器。对矩阵 \(A\) 的访问具备良好的空间局部性，可以充分利用缓存行连续访问矩阵 \(A\) 某一行元素，而且，`A[i, k]` 在 \(j\) 维循环中重复使用，重用距离为 \(O(n)\)。对矩阵 \(B\) 的访问最为低效，因其按列访问，破坏了空间局部性，而且，`B[k, j]` 在 \(i\) 维循环中重复使用，重用距离为 \(O(n^2)\)。当矩阵较大、缓存不能保留足够的相关缓存行时，对矩阵 \(B\) 的每次访问都可能导致未命中，从而使缓存未命中次数 \(Q\) 达到 \(O(n^3)\)，成为缓存未命中的主要来源。后续的分析将主要针对矩阵 \(B\)。

为了缓解矩阵 \(B\) 缓存未命中过高这一问题，研究者引入了矩阵分块（tiling）技术。分块后的矩阵乘累加计算伪代码如下：

```text
for (i1 = 0; i1 < n; i1 += s)
  for (j1 = 0; j1 < n; j1 += s)
    for (k1 = 0; k1 < n; k1 += s)
      for (i = i1; i < i1 + s && i < n; i++)
        for (j = j1; j < j1 + s && j < n; j++)
          for (k = k1; k < k1 + s && k < n; k++)
            C[i, j] += A[i, k] * B[k, j];
```

上述矩阵分块通过将原始大矩阵划分为 \(s\times s\) 的分块矩阵，并调整块大小 \(s\)，使得一次块乘累加所需的子矩阵能够放入缓存中，即在忽略缓存行边界等常数开销时满足 \(3s^2\le M\)，因此取 \(s=\Theta(\sqrt M)\)。根据子矩阵缓存引理（submatrix caching lemma），经过分块处理后，在行宽、块大小与缓存行满足相应条件时，每个分块矩阵的缓存未命中次数为 \(O(s^2/B)\)，整个分块矩阵乘法的总缓存未命中次数可优化为

\[
Q=O\!\left(1+\frac{n^2}{B}+\frac{n^3}{B\sqrt M}\right)。
\]

其中，\(M\) 为缓存容量、\(B\) 为缓存行长度，均按元素数计。对于远大于缓存的大矩阵，主导项为原书所列的 \(O(n^3/(B\sqrt M))\)。5.2.2 节中介绍的 AffineLoopTiling pass 具体利用了多面体编译方法来优化仿射循环（affine loop）。

> 校订注：原书直接写 \(s=\sqrt M\)，忽略了同时驻留的多个矩阵块；还省略了输入输出的 \(n^2/B\) 项及模型适用条件。对按行存放的子矩阵，逐行边界开销一般还含 \(O(s)\) 项；在常见的 tall-cache 条件 \(M=\Omega(B^2)\)、选取合适块大小时，该项可被 \(O(s^2/B)\) 吸收。这里保留原公式作为大矩阵时的主导项，而不将其无条件称为所有规模和算法的理论最优成本。

在执行循环变换前，需要检查分块的合法性，即确保循环变换可保留数据依赖关系。MLIR 为实现分块合法性检查提供了相应的 `checkTilingLegality()` 辅助函数。该函数将内存访问间的依赖关系简化为检查依赖距离分量是否存在负值，只要发现原始循环带中存在这种负分量就拒绝该分块方案。因为在超矩形分块中，分块按照循环索引的字典序递增顺序执行，而带有负分量的依赖可能使当前分块依赖尚未执行的分块的结果，违反数据依赖顺序并导致执行错误。

AffineLoopTiling pass 中将调用 `checkTilingLegality()`。

> 校订注：此函数在 `LoopTiling.cpp` 中是 `static` 辅助函数，不是公开 API。它采用保守的合法性检查，拒绝某个循环带不等于证明该循环带在所有块大小下都绝对不能分块；也不应把“存在一个负分量”等同于整个依赖向量的字典序为负。

在满足数据依赖关系的前提下，矩阵分块除了可以改善局部性，还可以通过将大的循环迭代空间分解成更小的分块，为并行化提供更细粒度的任务。这些小任务可以在不同处理器或 GPU 的线程块／线程束／线程上并行执行。在 MLIR 的 Affine 方言中提供了 AffineParallelize pass 及其相关接口，如 `isLoopParallel()`、`affineParallelize()` 等，可以在识别可并行的 `affine.for` 循环后将其转换为一维 `affine.parallel` 循环，以实现并行优化。

<!-- 原书第 171 页；PDF 第 15 页。上段跨页。 -->

但是，循环优化方法的效果有时在优化空间中的并行性和局部性的权衡方面却相互冲突。例如，过小的分块大小可能会导致并行计算任务粒度过细，从而增加并行调度及线程间同步的开销，反而抵消局部性带来的收益；过大的分块大小虽然能减少并行任务对应的调度和同步开销，但可能会超出缓存容量，失去分块的意义。

此外，程序的并行性能不仅依赖于算法本身的并行潜力，还高度依赖底层硬件的并行能力，例如，多核架构的计算能力、SIMD（单指令多数据）指令集的支持、GPU 的线程组织与内存层次结构等。因此，在循环优化中选择合适的参数（如分块大小、循环变换顺序等）及并行化策略，必须在并行性与局部性之间寻求平衡，以避免某一优化方向的过度最优反而导致整体性能下降。在应对上述挑战时，多面体编译可以提供系统性的解决框架。

## 5.2 MLIR 中的多面体编译技术

多面体模型通过将循环迭代空间和数据访问模式形式化为整数线性不等式，为描述循环嵌套及数据依赖关系提供了精确、通用、可优化的数学框架。MLIR 使用多面体编译技术在编译器基础设施中实现了强大的循环变换和依赖性分析，使得循环变换能系统化进行，特别是通过 Affine 方言，结合上述整数集合、Presburger 空间等多面体相关的各种辅助类和方法，使编译器能够利用多面体方法对嵌套循环进行表示、数学分析和优化，并为自动分析和优化循环结构打下基础。这相比其他基于经验规则或启发式搜索的优化方法，能够为可建模部分的变换合法性提供严格的数学依据，可适用于复杂的代码结构。

本节将围绕 MLIR 中的多面体编译技术展开讨论。在介绍 Affine 方言的基础上，深入分析 MLIR 如何利用多面体方法实现高效的循环优化，并探讨关键优化 pass 的实现原理。

### 5.2.1 Affine 方言

Affine 方言是 MLIR 中专为仿射计算设计的方言，该方言能够表达循环迭代空间、数据访问模式及其依赖关系，可实现精确的循环建模。Affine 方言表示和优化循环索引、数组访问模式，以及其他仿射变换的重要组成部分是仿射映射和仿射表达式。仿射映射通过仿射表达式将维度和符号线性组合起来，以定义计算中的索引变换关系。

在数学上，仿射映射是由线性变换（linear map）和平移（translation）构成的函数。在向量代数中，线性变换可以表示为矩阵 \(A\) 的乘法，而平移则可以表示为向量 \(b\) 的加法，仿射映射 \(f\) 作用于向量 \(x\) 可表示为 \(f(x)=Ax+b\)。即，仿射映射首先对输入 \(x\) 进行线性变换（\(Ax\)），然后施加一个平移（\(b\)）。

<!-- 原书第 172 页；PDF 第 16 页。上段跨页。 -->

> 校订注：原书写“可逆矩阵 \(A\)”，但一般线性映射不要求矩阵可逆，甚至不要求是方阵，例如本页三个输入维度到两个输出维度的映射。

仿射表达式是由变量、常数和线性操作组成的数学表达式。这些操作按照特定的规则组合在一起，用于表示线性关系或者线性变换。在 MLIR 中，仿射映射通过仿射表达式将一组维度和符号转换为结果列表，可用于描述循环迭代空间的变换，例如，循环展开、循环融合和循环重排等。

MLIR 进一步扩展了仿射映射的定义，允许在仿射表达式中出现对正整数常量的 `ceildiv`、`floordiv` 和取模运算。这些运算扩展了传统仿射映射的能力，使其能够表达更复杂的整数索引计算。因此，MLIR 中通常所称的仿射映射，是以维度和符号为参数的多维准仿射函数。

原书的例子 \((d_0,d_1,d_2,s_0)\to(d_0+d_1,s_0d_2)\) 有三个维度（`d0`、`d1`、`d2`）和一个符号（`s0`），输出为二维，可用 `affine_map` 语法表示为：

```mlir
affine_map<(d0, d1, d2)[s0] -> (d0 + d1, s0 * d2)>
```

> 校订注：保留原例，但其中 `s0 * d2` 属于 **semi-affine（半仿射）** 表达式，不属于严格的 affine／quasi-affine 子集。符号在执行区域内不变，不等于它是编译时已知的整数常量；不能据此认为所有 Affine 分析都支持符号与维度相乘。依据为 `mlir/docs/Dialects/Affine.md` 的 “Semi-affine maps” 一节。

在 MLIR 的仿射映射语法中，维度在圆括号中声明，符号在方括号中声明。其中，`d0`、`d1` 和 `d2` 是维度标识符，`s0` 是符号标识符。如果用结果列表 `y0`、`y1` 表示该映射的输出 `(d0 + d1, s0 * d2)`，即：

\[
y_0=d_0+d_1,\qquad y_1=s_0d_2,
\]

则在固定 \(s_0\) 的前提下，上述表达式可用矩阵形式表示为：

\[
\begin{bmatrix}y_0\\y_1\end{bmatrix}
=\begin{bmatrix}1&1&0\\0&0&s_0\end{bmatrix}
\begin{bmatrix}d_0\\d_1\\d_2\end{bmatrix}
+\begin{bmatrix}0\\0\end{bmatrix}。
\]

可以看到，在固定参数之后，此处的映射由线性变换和位移构成。此处的矩阵运算对维度 \([d_0\ d_1\ d_2]^T\) 进行线性变换，平移项为零。MLIR 中严格 affine 表达式与 semi-affine 扩展的不同之处在于，它们对允许的乘法和整除形式施加了不同限制；这些限制与其能否被相应编译分析高效处理有关。

> 校订注：原书矩阵第二行写为 `[0 0 1]`，平移向量写入 `s1`，后文又称平移项为 `s0`，均与 `y1 = s0 * d2` 不一致。这里按原始代码和两个标量等式修正矩阵，不删去原书的矩阵推导。若把 `s0` 也当作变化的输入，`s0 * d2` 是双线性的，不能宣称它是这些全部输入上的普通仿射映射。

维度和符号是多面体结构中可能出现的两种索引类型（即 `IndexType`，这是一种位宽与平台相关的整数类型）标识符，多面体模型中的算法通常以不同的方式处理维度和符号。维度标识符表示数据结构（如映射、集合、张量等）的维度。例如，以下循环嵌套具有三个维度标识符 \(i,j,k\)：

```cpp
for (int i = 0; i < M; i++) {
  for (int j = 0; j < N; j++) {
    for (int k = 0; k < K; k++) {
      C[i][j][k] += /* 原书省略的表达式 */ ...;
    }
  }
}
```

<!-- 原书第 173 页；PDF 第 17 页。上面的代码块跨页。 -->

符号标识符表示在编译时可能未知但在相关仿射作用域中保持不变的整数值，在特定上下文中可以被视为参数常数。符号标识符通常表示输入参数或配置值，例如，循环边界、函数参数或数组大小。在 MLIR 中，定义在具有仿射作用域（affine scope）语义的操作（如模块和函数）顶层区域中的值，是可用作符号的一类值；其他值能否作为符号，还需满足相应的作用域和定义规则。在上述 semi-affine 扩展中，符号 `s0` 可以与维度 `d2` 相乘，但维度之间的乘积不是有效的 affine 或 semi-affine 表达式。

除了仿射映射，MLIR 还为 Affine 方言提供了整数集合属性，整数集合的定义与作用已在前文 5.1.1 节中详述。

Affine 方言利用上述概念定义了一系列操作。其中，`affine.for` 操作是一种 `for` 循环，其循环不变量下界和上界用仿射映射表示，步长为正常量。`affine.parallel` 操作是一种多重 `for` 循环嵌套，其中的迭代可以并发执行。`affine.for` 可通过循环携带值传递迭代间状态；`affine.parallel` 通过指定的归约运算产生归约结果。两种循环的边界都可以按相应语法组合多项表达式，取下界的最大值和上界的最小值。`affine.if` 操作是一种条件构造，可以带有可选的 `else` 区域，以及由给定值是否包含在某个整数集合中来定义的条件。最后，`affine.load` 和 `affine.store` 操作表达内存访问，其中，地址的计算通过仿射映射表示。

> 校订注：原书将循环携带值、归约以及边界 `max`／`min` 混在同一句中；边界取最大／最小值与循环体的归约结果是不同机制，现分别说明。

### 5.2.2 MLIR 中的多面体编译优化 pass

作为新一代编译框架，MLIR 在 Affine 方言的基础上实现了一系列多面体相关的编译优化 pass。这些 Affine 方言中的优化 pass 利用多面体模型进行循环转换和优化，或者专注于提升数据局部性，或者专注于挖掘并行度，从而为异构硬件高效执行提供助力。

MLIR 中已有的多面体优化 pass 包括 AffineLoopUnroll、AffinePipelineDataTransfer、AffineVectorize、AffineParallelize、AffineLoopNormalize、AffineLoopFusion、AffineLoopTiling 等。

其中，AffineLoopUnroll pass 支持完全展开（full unrolling）和部分展开两种仿射循环展开模式。在启用完全展开模式并设置完全展开阈值（full unroll threshold）时，该 pass 将对迭代次数不大于阈值的循环执行完全展开。这种模式主要用于测试外层循环展开的场景。该 pass 默认采用部分展开模式，对最内层仿射循环进行展开，以减少循环控制开销，增加指令级并行性（ILP）。

> 校订注：原书写“小于阈值”，当前仓库 `LoopUnroll.cpp` 的判断是 `*tripCount <= unrollFullThreshold`，包括等于阈值的情况。

AffinePipelineDataTransfer pass 的目的是优化多级存储层次结构，如全局内存与共享内存或片上缓冲区间的数据搬运过程。该 pass 将数据传输操作流水化（pipelining），安排异步数据传输及相应等待，使得计算和数据传输能够重叠执行，从而减少访存延迟对性能的影响。在实现上，该 pass 采用后序遍历（post-order walk）方式优先处理内层循环中的数据传输指令。否则，如果先对外层循环进行流水化，外层 `affine.for` 循环会被替换为包含前序（prologue）、稳态循环（steady-state loop）、后序（epilogue）的结构，导致此前收集的内部循环操作失效。因此，必须先处理内层循环中的数据传输，再逐层向外展开流水化过程，以保证生成的代码正确性与一致性。

<!-- 原书第 174 页；PDF 第 18 页。上段跨页。 -->

AffineVectorize pass 的目的是将仿射循环转换为目标无关的多维向量抽象（n-D vector abstraction），这是一种在函数级别实现的、以超向量（super-vector）粒度执行的高层次向量化策略。此处的超向量可理解为适合后续硬件映射、大小为某个硬件原生向量整数倍的向量类型。例如，相对于硬件向量 `vector<8xf32>`，`vector<16xf32>` 和 `vector<2x8xf32>` 都可被视为有效超向量。AffineVectorize pass 将循环迭代切分为给定超向量大小相匹配的块（即超向量化），并通过 `vector.transfer_read` 等操作将标量内存访问转换为向量读取。在超向量化之后，循环和操作将以超向量形状表示。这一方面能表达循环具备向量化条件并表示相应的内存访问结构，另一方面可将向量化语义以紧凑形式封装进向量类型，避免后续优化破坏结构。最终，这些超向量会在后续的递降 pass 中逐步映射到具体硬件的向量指令。

AffineVectorize pass 的核心功能是根据参数给定的向量大小和循环顺序模式，在当前函数中搜索可以被向量化的仿射循环嵌套，并按照从内到外的顺序对循环嵌套中的循环执行 \(n\) 维向量化。该 pass 可识别并行循环与所支持的归约循环，并将其映射到适合的向量操作，从而把循环级别的并行性转化为向量级别的并行性。

AffineLoopNormalize pass 的主要功能是对 `affine.for` 和 `affine.parallel` 循环进行规范化处理，将循环的下界统一转换为 0，步长调整为 1，并将上界设为循环的迭代次数（trip count），从而得到标准化的循环形式。如果循环已经处于规范化状态，pass 会直接跳过。此外，该 pass 还可根据相关编译选项（`promoteSingleIter`），将所支持的单次迭代循环提升为循环体中的操作，从而消除不必要的循环结构。通过这种方式，AffineLoopNormalize pass 简化了循环结构，并为后续的优化与变换（如循环融合、循环平铺、向量化等）创造条件。

总体而言，MLIR 中的多面体优化 pass 已经初步具备对循环结构和内存访问模式进行系统化分析与变换的能力，为编译器将高层循环语义映射为并行化的硬件执行形式提供了可选手段。可以预见，随着 Affine 方言和多面体优化技术的持续发展，MLIR 中的多面体编译优化 pass 将进一步完善，并在深度学习编译和高性能科学计算优化等领域发挥更大作用。

## 5.3 多面体编译在 MLIR 中的应用实例

在 MLIR 的 Affine 方言中，基于多面体模型的优化 pass 是提升编译器生成代码性能的关键工具，特别是在优化数据局部性与并行性方面。其中，AffineLoopTiling 和 AffineLoopFusion 是两种具有代表性的优化 pass，二者从不同的维度出发，针对不同场景，通过改变循环嵌套结构，优化计算过程中的访存行为和执行效率。

AffineLoopTiling pass 主要通过将大的循环结构划分为更小的分块，使得每个分块操作的数据更容易载入缓存，达到提升空间局部性的目的。该 pass 的实现过程可大体分为识别可分块循环带（band，该概念在 Pluto 等多面体优化算法中也有使用）、计算合适分块大小，以及根据分块大小生成分块循环结构三部分。AffineLoopFusion pass 则在考虑数据依赖关系的基础上，通过将相邻循环进行融合，达到提升时间局部性的目的。该 pass 的实现过程相对复杂，包括内存依赖分析、生产者-消费者融合，以及对循环融合可行性和潜在收益的判断。此外，还支持对结构对称的兄弟关系循环进行融合。

### 5.3.1 AffineLoopTiling pass 工作流程

循环分块是一种优化数据局部性的重要方法，也是针对数据密集型（data-intensive）程序最重要的性能优化方法之一。数据密集型程序性能主要受访存时间限制。循环分块通过将大型循环迭代空间分割成更小的分块，并调整循环的执行顺序，使得分块数据尽可能载入缓存（cache）或共享内存并在其中复用，而无须频繁访问全局内存。分块后的循环以较小的分块处理数据，通过改善局部性，增加了缓存重用概率，减少了缓存未命中，进而减少因此导致的处理器停顿。

然而，循环分块是一个复杂的问题，影响最优分块大小的因素有很多，包括存储层次结构、各级缓存空间大小等。AffineLoopTiling pass 只是 MLIR 中利用多面体编译方法优化仿射循环的初步方案，其主要作用于 MLIR 的 `affine.for` 循环嵌套结构，在通过仿射映射和仿射约束分析循环迭代空间中所有内存读写操作的内存占用量后，基于缓存大小计算合适的分块大小，使得分块后的内存读写数据尽可能适应缓存，以提高数据局部性，减少缓存未命中。AffineLoopTiling pass 没有实现更高级的循环变换，如基于成本模型针对不同硬件特性进行优化等，因此，在将其扩展为更通用的循环优化方案方面仍有改进空间。

AffineLoopTiling pass 处理的是仿射循环，这种循环的迭代范围和访问模式可以用循环索引变量的仿射表达式描述，且步长为常数。仿射循环示例代码如下（数组下标使用数学式二维记法，是伪代码）：

```text
for (i = 0; i < 10; i++) {
  for (j = 0; j < 2 * i + 1; j += 2) {
    C[2 * i + 2, j + 2] += A[3 * i, j] + B[j, i];
  }
}
```

其中，外层循环索引变量 `i` 和内层循环索引变量 `j` 的上界分别为常数 10 和 `2 * i + 1`，外、内层循环步长分别为常数 1 和 2，数组 A、B 和 C 的访问索引分别由仿射表达式 `3 * i` 等决定，均符合仿射循环要求，因此上述循环是仿射循环。

AffineLoopTiling pass 通过收集可分块的循环带，计算合适的分块大小，并执行循环分块，以提高缓存利用率，并为并行执行创造条件。本小节使用如下测试用例 `simple_matmul.mlir` 辅助分析 AffineLoopTiling pass 的执行过程：

#### 1. 收集可分块循环带

`runOnOperation()` 函数首先调用 `getTileableBands()` 函数，分析和识别当前 MLIR 函数中作为循环分块优化候选的循环嵌套。符合条件的循环嵌套保存在集合 `bands` 中。此处的循环嵌套通常是完美循环嵌套，即内、外层循环之间没有其他操作。集合 `bands` 中的每一个循环带表示一个循环嵌套。所谓的循环带实际上是包含多个 `affine.for` 操作的向量，这些 `affine.for` 操作构成一组连续的完美循环嵌套。例如，由两个 `affine.for` 组成的循环带示例如下：

```mlir
affine.for %i = 0 to 128 {
  affine.for %j = 0 to 128 {
    // ... some_ops
  }
}
```

<!-- 原书第 178 页；PDF 第 22 页。上面的代码块跨页。 -->

如果在上述内、外层循环间插入其他操作，则上述两层循环不能一起被称为一个完美嵌套的循环带。

> 校订注：原书将收集目标描述为“适合进行循环分块优化并且分块后能够带来性能收益”的循环嵌套。当前仓库函数注释明确说明，这还是用于测试分块代码生成的占位实现，实际收集最外层的最大完美循环嵌套；收集成功不等于已证明性能收益，也不等于已经通过后续依赖合法性检查。插入其他操作会截断循环带，不表示单层循环本身不能构成较短的带。

`getTileableBands()` 函数代码实现如下：

```cpp
void mlir::affine::getTileableBands(
    func::FuncOp f, std::vector<SmallVector<AffineForOp, 6>> *bands) {
  for (AffineForOp forOp : f.getOps<AffineForOp>()) {
    SmallVector<AffineForOp, 6> band;
    getPerfectlyNestedLoops(band, forOp);
    bands->push_back(band);
  }
}

void mlir::affine::getPerfectlyNestedLoops(
    SmallVectorImpl<AffineForOp> &nestedLoops, AffineForOp root) {
  for (unsigned i = 0; i < std::numeric_limits<unsigned>::max(); ++i) {
    nestedLoops.push_back(root);
    Block &body = root.getRegion().front();
    if (body.getOperations().size() != 2)
      return;
    root = dyn_cast<AffineForOp>(&body.front());
    if (!root)
      return;
  }
}
```

> 校订注：按当前仓库补上命名空间 `affine`。原书及本地 `LoopUtils.cpp` 的数量判断均为 `body.begin() != std::prev(body.end(), 2)`；若循环体仅含终结操作，向前移动两次会越过起点。这里在书中代码改用操作数判断，保留原算法，避免无效迭代器操作；没有修改仓库源码。下文仍解释原书的迭代器写法，便于对照实现。

`getTileableBands()` 函数遍历 MLIR 函数操作 `f` 中直接包含的所有 `affine.for` 操作，并以这些 `affine.for` 操作为根循环调用 `getPerfectlyNestedLoops()` 函数，找到以该 `affine.for` 操作为根的循环带 `band`，将其添加到 `bands` 集合中。这里的 `f.getOps<AffineForOp>()` 不是递归遍历；继续向内寻找循环由后一个函数完成。

#### 2. 计算循环带分块大小

生成 `bands` 集合后，`runOnOperation()` 函数接下来遍历 `bands` 集合中的每个循环带，调用 `checkTilingLegality()` 函数检查循环带合法性，调用 `getTileSizes()` 函数为循环带计算分块大小，以便随后根据分块大小对每个循环带执行循环分块。

计算循环带分块大小功能由函数 `getTileSizes()` 完成。该函数使用启发式方法，根据内存读写操作涉及的内存占用量和缓存大小选择分块大小。如果无法计算内存占用量，则使用分块大小默认值（`kDefaultTileSize = 4`）。`getTileSizes()` 函数代码实现如下（保留原书摘录及其省略位置）：


该函数的接口意图是获取参数 `memorySpace` 指定的内存地址空间中，所有被参数 `forOp` 指定的 `affine.for` 操作访问的内存数据占用量（以字节为单位）。如果 `memorySpace` 为 -1，即未指定内存空间，则考虑所有内存空间。不过，在本地这版 MLIR 实现中，参数 `memorySpace` 没有用于过滤访存操作。`forOp` 指定的 `affine.for` 操作为循环带的第一层循环 `band[0]`。

实际计算内存占用量功能由内部版本 `getMemoryFootprintBytes()` 函数实现。外部版本 `getMemoryFootprintBytes()` 函数在调用内部版本函数时，将 `affine.for` 操作的块、起始迭代器（指向 `forOp` 操作）和结束迭代器（指向 `forOp` 操作的下一个操作）传递给内部版本 `getMemoryFootprintBytes()` 函数。内部版本 `getMemoryFootprintBytes()` 函数代码实现如下：

```cpp
static std::optional<int64_t> getMemoryFootprintBytes(
    Block &block, Block::iterator start, Block::iterator end, int memorySpace) {
  SmallDenseMap<Value, std::unique_ptr<MemRefRegion>, 4> regions;
  auto result = block.walk(start, end, [&](Operation *opInst) -> WalkResult {
    if (!isa<AffineReadOpInterface, AffineWriteOpInterface>(opInst)) {
      return WalkResult::advance();
    }
    auto region = std::make_unique<MemRefRegion>(opInst->getLoc());
    if (failed(region->compute(opInst, getNestingDepth(&*block.begin())))) {
      return opInst->emitError("error obtaining memory region\n");
    }
    auto it = regions.find(region->memref);
    if (it == regions.end()) {
      regions[region->memref] = std::move(region);
    } else if (failed(it->second->unionBoundingBox(*region))) {
      return opInst->emitWarning(
          "getMemoryFootprintBytes: unable to perform a union on a memory "
          "region");
    }
    return WalkResult::advance();
  });
  if (result.wasInterrupted())
    return std::nullopt;

  int64_t totalSizeInBytes = 0;
  for (const auto &region : regions) {
    std::optional<int64_t> size = region.second->getRegionSize();
    if (!size.has_value())
      return std::nullopt;
    totalSizeInBytes += *size;
  }
  return totalSizeInBytes;
}
```

> 校订注：原书称这两个函数定义在 `LoopTiling.cpp`，当前仓库实际定义在 `mlir/lib/Dialect/Affine/Analysis/Utils.cpp`。原摘录省略了 `result.wasInterrupted()` 的失败返回，现补回，避免把部分遍历结果误当作完整占用量；原书缩写的警告字符串也按源码补全。同一个 memref 的多次访问先合并包围盒，再求大小，不是把每次 load／store 的字节数直接相加。

<!-- 原书第 182 页；PDF 第 26 页。 -->

内部版本 `getMemoryFootprintBytes()` 函数首先遍历 `affine.for` 循环中的所有操作。在遍历到其他 `affine.for` 或 `affine.yield` 等非内存读写操作时直接跳过，而在遍历到 `affine.load` 和 `affine.store` 操作（即内存读写操作）时，则调用 `MemRefRegion::compute()` 函数为每个 `affine.load` 或 `affine.store` 操作计算 `MemRefRegion`（内存引用区域）实例的内容，并用 `FlatAffineValueConstraints` 实例 `cst` 表示该 `MemRefRegion` 实例的约束系统。在此基础上，`getMemoryFootprintBytes()` 函数可计算得到所有内存读写操作的内存占用总量。`compute()` 函数的参数 `loopDepth` 值由 `getNestingDepth()` 计算得到；在这里，它表示待分析块外部保留为参数的循环嵌套深度。

> 校订注：原书把这里的 `loopDepth` 解释成“内存读写操作被多少个 affine.for 循环包围”。调用实参却是 `getNestingDepth(&*block.begin())`，不是 `getNestingDepth(opInst)`。对顶层 `%i` 循环进行整体占用分析时，该值为 0，而最内层 load 本身被三层循环包围。这个区别决定哪些循环变量被消去、哪些留作访问区域的参数，不能混淆。

`MemRefRegion` 结构体的作用是用仿射表达式和不等式约束描述 memref 的内存访问范围。这意味着内存访问范围的边界可以不是常数，而是用包含变量（如循环索引变量）的仿射表达式描述。编译器可以根据内存读写操作对象 memref 的内存访问范围，辅助确定两个内存读写操作之间的依赖关系和合适的循环分块。例如，对于以下 `affine.for` 循环中的 `affine.load` 操作：

```mlir
// 假设 %A 是作用域内已定义的 memref<?xf32>，长度至少为 39。
affine.for %i = 0 to 32 {
  affine.for %ii = %i to affine_map<(d0) -> (d0 + 8)>(%i) {
    %value = affine.load %A[%ii] : memref<?xf32>
  }
}
```

> 校订注：原书省略了 load 的结果和类型，并将上界映射简写为 `(d0) -> (d0 + 8)`，这里补为可辨识的 MLIR 语法。外层 `%i` 最大为 31，内层 `%ii` 最大为 38，因此同时注明缓冲区长度条件。

假设 `loopDepth` 为 1，可以得到对应上述 `affine.load` 操作的 `MemRefRegion` 实例各字段及约束为 `{memref = %A, write = false, {%i <= %ii <= %i + 7}}`，分别表示该 `MemRefRegion` 实例访问的 memref 为 `%A`，访存操作为读操作（即 `affine.load` 操作），内存索引变量 `%ii` 的范围为 `%i`～`%i + 7`，`%i` 是外层循环索引变量。`compute()` 函数的主要功能围绕着构造由整数约束系统描述的内存访问范围展开。在构造 `MemRefRegion` 实例的整数约束系统时，必须正确处理维度变量和符号变量之间的关系，`FlatAffineValueConstraints` 类作为关键数据结构在其中发挥了重要作用。

`MemRefAccess` 类封装了内存读写操作访问的 memref 变量、是否是写操作及索引相关的访问映射等 memref 访问信息。`compute()` 函数中通过解析内存读写操作的 memref 访问信息，可以得到 memref 变量（如上述示例中的 `memref = %A`）和写操作标识（如上述示例中的 `write = false`）。

例如，对于测试用例 `simple_matmul.mlir`，`getMemoryFootprintBytes()` 函数在遍历到其中的三个 `affine.load` 和一个 `affine.store` 操作时会为其分别构造 `MemRefRegion` 实例。当处理第一个 `affine.load` 操作 `affine.load %arg0[%i + 1, %k + 2]` 时，`compute()` 函数通过该操作的 `MemRefAccess` 实例可得到操作访问的 memref 变量为 `%arg0`，写操作标识为 `false`。并且，通过解析该操作的内存索引表达式 `%arg0[%i + 1, %k + 2]`，可得到循环索引变量到内存索引变量（以 `AffineMap` 形式表示）的访问映射 `(d0, d1) -> (d0 + 1, d1 + 2)`，即 `affine.for` 语句的索引变量 `i`、`k` 偏移 1 个和 2 个单位后用作内存索引。在这种情况下，由于 `FlatAffineValueConstraints` 类间接继承自 `IntegerPolyhedron` 类，在 `FlatAffineValueConstraints` 实例 `cst` 表示的约束系统中，所有维度变量被视为 Presburger 空间的值域变量。此时，`cst` 初始状态下的定义域变量数量为 0，值域变量数量为 2（即 `%i` 和 `%k`），符号变量数量为 0，局部变量数量为 0，约束为空。

<!-- 原书第 183 页；PDF 第 27 页。 -->

`compute()` 函数接下来遍历所有维度变量和符号变量对应的操作数，并将其约束加入 `cst`。由于操作 `affine.load %arg0[%i + 1, %k + 2]` 的维度变量 `%i`、`%k` 都是 `affine.for` 操作的循环索引变量，对应的 `affine.for` 操作分别为 `affine.for %i = 0 to 256` 和 `affine.for %k = 0 to 250`，因此，调用 `FlatAffineValueConstraints` 类的成员函数 `addAffineForOpDomain()` 添加两个循环的上下界约束 `%i >= 0`、`%i <= 255` 和 `%k >= 0`、`%k <= 249`。整理后的 `cst` 中的 4 个不等式约束如下：

```text
 (1) * %i +  (0) * %k +   0 >= 0
(-1) * %i +  (0) * %k + 255 >= 0
 (0) * %i +  (1) * %k +   0 >= 0
 (0) * %i + (-1) * %k + 249 >= 0
```

上述不等式系数保存在继承自 `IntegerRelation` 类的成员变量 `inequalities` 中。

至此，`cst` 中包含了与操作 `affine.load %arg0[%i + 1, %k + 2]` 所涉及循环索引变量的整数线性约束关系。但 `cst` 仍无法描述这些循环索引变量如何用于访问内存（即 memref），即无法描述内存索引表达式 `%arg0[%i + 1, %k + 2]` 的内存访问范围约束，而这是计算内存读写操作内存占用量不可或缺的信息。

由前文可知，操作的内存访问范围约束由 `affine.load` 操作的访问映射 `(d0, d1) -> (d0 + 1, d1 + 2)` 得到。因此，`compute()` 函数调用 `FlatAffineValueConstraints` 类成员函数 `composeMap()`，将访问映射 `(d0, d1) -> (d0 + 1, d1 + 2)` 合并到 `cst`，并在 `cst` 中添加用新维度变量表示的约束，确保 `cst` 包含完整、正确的访问约束。由访问映射 `(d0, d1) -> (d0 + 1, d1 + 2)` 得到的新增内存访问范围约束为 `x = %i + 1` 和 `y = %k + 2`，其中，`x`、`y` 为内存索引变量（由于内存索引变量没有关联 SSA 值，为表述方便将其命名为 `x` 和 `y`）。整理后的 `cst` 中的 6 个约束（包括 2 个等式约束和 4 个不等式约束）如下：

```text
 (1) * x + (0) * y + (-1) * %i +  (0) * %k + (-1) = 0
 (0) * x + (1) * y +  (0) * %i + (-1) * %k + (-2) = 0
 (0) * x + (0) * y +  (1) * %i +  (0) * %k +    0 >= 0
 (0) * x + (0) * y + (-1) * %i +  (0) * %k +  255 >= 0
 (0) * x + (0) * y +  (0) * %i +  (1) * %k +    0 >= 0
 (0) * x + (0) * y +  (0) * %i + (-1) * %k +  249 >= 0
```

上述等式系数保存在继承自 `IntegerRelation` 类的成员变量 `equalities` 中。此时，`cst` 中的定义域变量数量为 0，值域变量数量为 4（即 `x`、`y`、`%i` 和 `%k`），符号变量数量为 0，局部变量数量为 0，约束数量为 6。

`compute()` 函数主要关注与内存读写操作内存占用量密切相关的内存访问范围，即关于内存索引变量 `x`、`y` 的约束。但到目前为止，`x`、`y` 的约束均与循环索引变量 `%i`、`%k` 有关，尚未得到仅用内存索引描述的访问范围。为了消除内存索引约束对循环索引变量的依赖，`compute()` 函数调用 `FlatAffineValueConstraints` 类的成员函数 `setDimSymbolSeparation()`，将内存索引变量作为维度变量，而将用于计算内存索引变量的循环索引变量（视为计算内存索引的参数）作为符号变量。此时，`cst` 中的值域变量数量为 2（即 `x` 和 `y`），符号变量数量为 2（即 `%i` 和 `%k`），其他不变。这些符号变量将被消除（project out）。

<!-- 原书第 184 页；PDF 第 28 页。上段跨页。 -->

`compute()` 函数随后调用 `FlatAffineValueConstraints` 类的成员函数 `projectOut()`，从 `cst` 的整数集合约束系统中依次消除 `projectOut()` 函数参数指定的符号变量 `%i` 和 `%k`，得到其余维度变量和符号变量的投影。

> 校订注：原书此句把 `%k` 误写为 `%j`；该 load 的访问映射不涉及 `%j`，后面的消元过程也使用 `%k`，现统一修正。

由于 `%i = x - 1`，将其代入 `cst` 其他各约束，可消除第一个等式约束和其他约束中的符号变量 `%i`。调用 `projectOut(%i)` 后，`cst` 剩余 5 个约束为：

```text
 (0) * x +  (1) * y + (-1) * %k + (-2) = 0
 (1) * x +  (0) * y +  (0) * %k + (-1) >= 0
(-1) * x +  (0) * y +  (0) * %k +  256 >= 0
 (0) * x +  (0) * y +  (1) * %k +    0 >= 0
 (0) * x +  (0) * y + (-1) * %k +  249 >= 0
```

此时，`cst` 中的值域变量数量为 2（即 `x` 和 `y`），符号变量数量为 1（即 `%k`），约束数量为 5，其他不变。

同理，由于 `%k = y - 2`，将其代入 `cst` 其他各约束，可消除另一个等式约束和其他不等式约束中的符号变量 `%k`。调用 `projectOut(%k)` 后，`cst` 剩余 4 个约束为：

```text
 (1) * x +  (0) * y + (-1) >= 0
(-1) * x +  (0) * y +  256 >= 0
 (0) * x +  (1) * y + (-2) >= 0
 (0) * x + (-1) * y +  251 >= 0
```

此时，`cst` 中的值域变量数量为 2（即 `x` 和 `y`），符号变量数量为 0，约束数量为 4，其他不变。

由上述约束系统可得，内存访问范围为 `1 <= x <= 256`、`2 <= y <= 251`。显然，对于原书未经修正的操作数类型 `memref<256x256xvector<64xf32>>`，当 `x = 256` 时将出现访存越界。在启用 `addMemRefDimBounds` 时，`compute()` 函数还会在现有 `cst` 约束系统基础上，调用 `IntegerRelation` 类成员函数 `addBound()`，根据 memref 操作数类型的维度大小，增加内存索引变量 `x`、`y` 的上下界约束 `x >= 0`、`x <= 255`、`y >= 0`、`y <= 255`，将分析区域限制在 memref 的有效范围内。调用 `addBound()` 函数后，`cst` 中的 8 个约束为：

```text
 (1) * x +  (0) * y + (-1) >= 0
(-1) * x +  (0) * y +  256 >= 0
 (0) * x +  (1) * y + (-2) >= 0
 (0) * x + (-1) * y +  251 >= 0
 (1) * x +  (0) * y +    0 >= 0
(-1) * x +  (0) * y +  255 >= 0
 (0) * x +  (1) * y +    0 >= 0
 (0) * x + (-1) * y +  255 >= 0
```

> 校订注：这里按原书的 **256×256 原始类型** 保留约束推导，不能当作前面 **257×256 安全修正版** 的结果。原书将增加约束的目的写成“避免出现访问越界”，这是对分析与程序执行的混淆。源码注释说明，这一步用于收紧投影可能产生的过近似；它不改变循环，不添加运行时边界检查，也不修复输入程序中的未定义行为。对于 257×256 修正版，第六行应为 `-x + 256 >= 0`，访问区域保持 `1 <= x <= 256`。

<!-- 原书第 185 页；PDF 第 29 页。 -->

其中，后 4 个不等式约束对应上述内存索引变量 `x`、`y` 的上下界约束。

上述 8 个不等式约束描述的内存访问范围显然有重复，因此，`compute()` 函数调用 `IntegerRelation` 类成员函数 `removeTrivialRedundancy()`，将冗余约束删除。删除后的 `cst` 中剩余 4 个约束为：

```text
 (1) * x +  (0) * y + (-1) >= 0
 (0) * x +  (1) * y + (-2) >= 0
 (0) * x + (-1) * y +  251 >= 0
(-1) * x +  (0) * y +  255 >= 0
```

综上所述，`compute()` 函数根据循环索引范围（`%i >= 0`、`%i <= 255`、`%k >= 0`、`%k <= 249`）、循环索引变量到内存索引变量的映射关系 `(d0, d1) -> (d0 + 1, d1 + 2)` 和内存索引变量上下界约束（`x >= 0`、`x <= 255`、`y >= 0`、`y <= 255`），可最终得到原始类型的分析区域 `x >= 1`、`x <= 255`、`y >= 2`、`y <= 251`。

测试用例 `simple_matmul.mlir` 中其他 `affine.load` 和 `affine.store` 操作的 `MemRefRegion` 实例计算方法与上述过程类似。所有 `MemRefRegion` 实例按 memref 合并后保存在集合 `regions` 中。`regions` 集合是将 memref 操作数映射到其对应内存读写操作的 `MemRefRegion` 实例的集合，集合的键是 `Value` 类型的 memref，值则指向 `MemRefRegion` 实例。测试用例 `simple_matmul.mlir` 中的所有 `affine.load` 和 `affine.store` 操作经过 `getMemoryFootprintBytes()` 函数处理后得到的 `regions` 集合如图 5-8 所示。

> 校订注：原图把 `cst` 标为 `cts`，现更正。`%arg2` 的 `write = false` 是图中及这段实现按第一次访问保留下来的字段，不能据此推断这个 memref 从未被写入；合并占用区域的目的在于去除重复计数。257×256 修正版只需将 `%arg0` 矩阵最后一行常数改为 256。

在获得上述各内存读写操作对应的 `MemRefRegion` 实例后，`getMemoryFootprintBytes()` 函数调用 `MemRefRegion::getRegionSize()` 函数，根据 `MemRefRegion` 实例中的 memref 操作数类型和内存访问范围，计算各内存读写操作的内存占用量。例如，对于操作 `affine.load %arg0[%arg3 + 1, %arg5 + 2]`，原始 memref 操作数类型为 `memref<256x256xvector<64xf32>>`，其裁剪后的访问索引 `x ∈ [1, 255]`、`y ∈ [2, 251]`，于是可得该操作的分析区域内存占用量为 16,320,000（= 256 × 255 × 250）字节。同理可计算得到 `affine.load %arg1[%arg5, %arg4]` 和 `affine.load %arg2[%arg3, %arg4]` 操作的内存占用量分别为 16,384,000（= 250 × 256 × 256）字节和 16,777,216（= 256 × 256 × 256）字节。`affine.store %4, %arg2[%arg3, %arg4]` 操作因与 `affine.load %arg2[%arg3, %arg4]` 操作对应同一个 `MemRefRegion` 实例，不需要单独计算内存占用量。

综上，`getMemoryFootprintBytes()` 函数对原书测试用例 `simple_matmul.mlir` 中所有 `affine.load` 和 `affine.store` 操作计算得到的分析区域内存占用总量为 49,481,216（= 16,320,000 + 16,384,000 + 16,777,216）字节。

> 校订注：每个 `vector<64xf32>` 元素占 `64 × 4 = 256` 字节。前面安全修正版的 `%arg0` 区域有 `256 × 250` 个元素，占 16,384,000 字节，三者合计 49,545,216 字节。原书的 49,481,216 是带越界原例经过形状约束裁剪后的分析值，不是对原程序内存安全性的证明。

获得循环带中所有内存读写操作的内存占用总量后，AffineLoopTiling pass 中的 `getTileSizes()` 函数计算内存占用总量（`memoryFootprintBytes`）相对缓存大小超出多少倍。缓存选项 `cacheSizeInKiB` 要先乘 1024 转换为字节，再计算过剩因子：

\[
\mathrm{excessFactor} =
\left\lceil\frac{\mathrm{memoryFootprintBytes}}
{1024\,\mathrm{cacheSizeInKiB}}\right\rceil.
\]

随后根据该过剩因子确定分块大小。例如，原书测试用例的内存读写操作内存占用总量为 49,481,216 字节，缓存大小为 512 KiB（524,288 字节），过剩因子为 95（即 `ceil(49481216 / 524288)`）。这说明整体内存占用量远超缓存大小，分块可使每次处理的工作集缩小。

> 校订注：原书正文公式直接用字节除以 `cacheSizeInKiB`，单位不一致且遗漏向上取整；按代码修正。原书写的“512 KB”实际使用 1024 进制，改为 KiB。安全修正版 `ceil(49545216 / 524288)` 也为 95，因此不改变本例随后算出的分块大小。

`getTileSizes()` 函数计算分块大小的方法是遍历循环带中的所有循环，并尽可能在所有维度上均衡分配。因此，按照以下方式用一种启发式（heuristic）方法为前面的循环计算分块大小：

\[
\mathrm{tileSize} =
\left\lfloor\mathrm{excessFactor}^{1/\mathrm{band.size}}\right\rfloor.
\]

其中，`band.size` 是循环带中循环嵌套的层数，也是可被分块的维度数量。例如，测试用例 `simple_matmul.mlir` 中的循环带包含三层循环，前两层循环的分块大小为 4（`floor(95^(1/3))`），最后一层循环的分块大小为 5（整数除法 `95 / (4 * 4)`）。最终的分块结果 `tileSizes = [4, 4, 5]` 意味着 `i`、`j`、`k` 维度的分块大小分别为 4、4、5，其意图是使分块适应缓存大小，并尽可能在各维度上均衡地分配分块，实现缓存访问局部性（cache locality）。

> 校订注：原书写“这保证了分块能适应缓存大小”，但源码将此模型明确标为近似，假定各维度大小与 footprint 近似一一线性相关；一般情况下不能保证最优或缓存适配。对本例，仅计完整 4×4×5 块访问的三个数组区域，数据量为 `(4×5 + 5×4 + 4×4)×256 = 14,336` 字节，确实小于 512 KiB，但这个具体结果不能推广为算法保证。

#### 3. 执行循环分块过程

计算得到循环带分块大小后，实际的分块过程由 AffineLoopTiling pass 中的 `tilePerfectlyNested()` 函数完成。该函数的代码实现如下：

<!-- 原书第 187 页；PDF 第 31 页。 -->

```cpp
LogicalResult mlir::affine::tilePerfectlyNested(
    MutableArrayRef<AffineForOp> input, ArrayRef<unsigned> tileSizes,
    SmallVectorImpl<AffineForOp> *tiledNest) {
  if (input.empty())
    return success();
  if (failed(performPreTilingChecks(input, tileSizes)))
    return failure();
  MutableArrayRef<AffineForOp> origLoops = input;
  AffineForOp rootAffineForOp = origLoops[0];
  unsigned width = input.size();
  SmallVector<AffineForOp, 6> tiledLoops(2 * width);
  constructTiledLoopNest(origLoops, rootAffineForOp, width, tiledLoops);
  SmallVector<Value, 8> origLoopIVs;
  extractForInductionVars(input, &origLoopIVs);
  constructTiledIndexSetHyperRect(origLoops, tiledLoops, tileSizes);
  for (unsigned i = 0; i < width; i++)
    origLoopIVs[i].replaceAllUsesWith(
        tiledLoops[i + width].getInductionVar());
  rootAffineForOp.erase();
  if (tiledNest)
    *tiledNest = std::move(tiledLoops);
  return success();
}
```

> 校订注：原书开头的省略号中包含空输入检查，现按源码补回，避免直接访问空的 `origLoops[0]`。

```text
│  ├─ affine::isPerfectlyNested()：检查完美循环嵌套
│  └─ checkIfHyperRectangular()：检查超矩形条件

├─ constructTiledLoopNest()：构造分块间循环和分块内循环
```

`tilePerfectlyNested()` 函数的主要功能分为三部分。首先应检查原始循环嵌套是否为完美循环嵌套，以及原始循环嵌套索引变量上下界构成的集合是否为超矩形。这部分功能涉及构建 `FlatAffineValueConstraints` 实例的约束系统。然后对符合条件的原始循环嵌套进行分块。最后设置分块循环结构中的索引变量上下界和步长，并删除原始循环嵌套，保留分块后的循环嵌套结构。

<!-- 原书第 188 页；PDF 第 32 页。上段跨页。 -->

`tilePerfectlyNested()` 函数首先调用 `performPreTilingChecks()` 函数，检查循环带是否符合分块条件，包括检查循环带中的循环嵌套是否为完美循环嵌套，以及循环嵌套是否为超矩形（hyper-rectangular）。此处讨论的 AffineLoopTiling pass 实现只对满足超矩形条件的完美循环嵌套进行分块。

检查循环带中的循环嵌套是否为完美循环嵌套由 `affine::isPerfectlyNested()` 函数完成。该函数的完美循环嵌套判断条件与前述 `getPerfectlyNestedLoops()` 函数类似：检查循环带中相邻两层循环之间，外层循环体是否仅含内层 `affine.for` 操作和终结操作 `affine.yield`。如果是，则满足此处的完美嵌套结构要求；最内层循环体可以含实际计算操作。

检查循环带中的循环嵌套是否为超矩形由 `checkIfHyperRectangular()` 函数完成。所谓超矩形，是在多维空间中的几何概念，是二维矩形和三维长方体在更高维度上的推广。在二维情况下，超矩形是一个普通矩形，其长、宽由两个区间 `[a₁, b₁]` 和 `[a₂, b₂]` 确定，区间长度为 `bᵢ - aᵢ`。超矩形各区间的范围相互独立（例如，长度区间不依赖于宽度区间）。超矩形与这些区间的笛卡儿积同构，即超矩形的形状与这些区间形成的笛卡儿积集合完全一致。例如，长、宽分别为 5 和 8 的矩形，其边界可由区间 `[0, 5]` 和 `[0, 8]` 确定。区间的笛卡儿积为：

\[
H=[0,5]\times[0,8]
 =\{(x_1,x_2)\mid x_1\in[0,5],\ x_2\in[0,8]\}.
\]

该集合中的所有元素构成一个二维超矩形。二维超矩形的上述概念可以推广到高维空间，且超矩形的每个面都必须是低维超矩形（即四维超矩形的每个三维面必须是三维超矩形，依此类推）。

> 校订注：这里的长度是几何区间长度；闭区间 `[0,5]` 中有 6 个整数点，不是 5 次循环迭代。下面 MLIR 循环上界排除、约束上界包含，需继续区分这两种记法。

`checkIfHyperRectangular()` 函数以一种简单且保守的方法检查给定的循环嵌套是否为超矩形。该方法分为两步。首先，`checkIfHyperRectangular()` 函数调用 `getIndexSet()` 函数，为所给循环嵌套构建 `FlatAffineValueConstraints` 约束系统，从而将多重循环嵌套构成的迭代关系转换为线性约束系统。`getIndexSet()` 接口也可处理传入的 `affine.if` 条件；`affine.if` 本身并不定义循环索引变量。然后，调用 `isHyperRectangular()`，根据约束系统中的每个约束是否同时涉及多个被检查的变量来判断迭代点集合是否满足这里的超矩形条件。如果每个约束最多只涉及其中一个变量，说明这些维度区间的范围相互独立；否则该保守检查不通过。

> 校订注：原书只提到不等式，本地 `IntegerRelation::isHyperRectangular()` 同时检查等式与不等式；它检查指定变量范围内的系数。检查失败不等于经过所有等价化简后该集合都不可能是超矩形。

例如，测试用例 `simple_matmul.mlir` 的循环带包含三个 `affine.for` 操作构成的三层循环，各 `affine.for` 操作的索引变量分别为 `%i`、`%j`、`%k`，各索引变量有各自的上下界，例如，`affine.for %i = 0 to 256` 的约束为 `0 <= %i <= 255`。这些索引变量上下界会被加入约束系统。`getIndexSet()` 函数提取所有 `affine.for` 操作索引变量，并由这些索引变量上下界转换得到如下线性不等式约束系统：

```text
 (1) * %i +  (0) * %j +  (0) * %k +   0 >= 0
(-1) * %i +  (0) * %j +  (0) * %k + 255 >= 0
 (0) * %i +  (1) * %j +  (0) * %k +   0 >= 0
 (0) * %i + (-1) * %j +  (0) * %k + 255 >= 0
 (0) * %i +  (0) * %j +  (1) * %k +   0 >= 0
 (0) * %i +  (0) * %j + (-1) * %k + 249 >= 0
```

<!-- 原书第 189 页；PDF 第 33 页。 -->

上述不等式系数保存在继承自 `IntegerRelation` 类的成员变量 `inequalities` 中。`isHyperRectangular()` 函数通过遍历 `inequalities` 可以发现，每个不等式中最多只涉及一个索引变量，`%i`、`%j`、`%k` 在边界表达式上相互之间没有依赖（即两个索引变量的非零系数不会同时出现在同一行），因此，上述约束系统表示的迭代点集合是超矩形。

在确定循环带符合分块条件后，AffineLoopTiling pass 的分块过程函数 `tilePerfectlyNested()` 调用 `constructTiledLoopNest()` 函数，构造分块循环嵌套。对于有 n 层循环的原始循环嵌套，AffineLoopTiling pass 将其分为 2n 层分块循环嵌套。分块循环嵌套中的所有循环分为两类：分块间循环（inter-tile loop，也称 tile-space loop）和分块内循环（intra-tile loop，也称 point loop）。其中，外面的 n 层循环用于在分块间进行迭代，即分块间循环；里面的 n 层循环用于在分块内进行迭代，即分块内循环。

图 5-11 展示了原始循环嵌套（上半部分）和尝试使用循环分块后（下半部分）的循环嵌套代码和计算依赖图。由图 5-11 可见，原始循环嵌套直接对整个 A 矩阵逐行、逐列执行整个 20×20 区域的计算，计算每个矩阵元素 `A[i][j]` 需要依赖图中下方一定范围的先前计算结果（即元素 `A[i-1][j-1]`、`A[i-1][j]`、`A[i-1][j+1]`）。例如，`A[1][1] = A[0][0] + A[0][1] + A[0][2]`。由于数据依赖，当前行的计算依赖于前一行的数据，导致数据的访问范围较大，计算过程中上一行数据需要保留，影响缓存局部性。图 5-11 中右侧的每个圆点代表一次循环迭代，也可理解为循环迭代中一个语句实例的计算结果。


从调度的角度看，循环分块是在满足依赖关系的前提下，将一种调度变换为另一种调度的过程。例如，上述原始循环嵌套的调度可表示为 `{S(i, j) -> (i, j)}`。候选矩形分块调度是在 i、j 维度上分别除以各自维度的分块大小（都为 4），可写为：

\[
S(m,n)\mapsto
\left(\left\lfloor\frac{m-1}{4}\right\rfloor,
      \left\lfloor\frac{n-1}{4}\right\rfloor,m,n\right).
\]

若用外层块起点 i、j 与内层点坐标 m、n 表示扩展循环，原书的写法为 `{S(i, j, m, n) -> ((i-1)/4, (j-1)/4, m, n)}`。其中，`(i-1)/4` 表示 i 维度的分块编号，`(j-1)/4` 表示 j 维度的分块编号，m 和 n 表示分块内正在处理的全局位置坐标。它们不是从 0 开始的块内相对偏移。对图 5-11 的递推，上述候选调度违反依赖，必须拒绝或先做适当变换。

`constructTiledLoopNest()` 函数在构造时先构造分块内循环，再构造分块间循环。该函数构造的分块循环嵌套尚未设置最终循环边界，先用上下界均为 0 的占位循环包裹原始循环嵌套，并搬移计算体。分块循环边界将在后续调用的 `constructTiledIndexSetHyperRect()` 函数中设置。因此，`constructTiledLoopNest()` 函数构造的分块循环嵌套尚不完善。

`constructTiledLoopNest()` 函数从循环嵌套的根操作（即原始循环嵌套的最外层循环）出发，调用 `b.create<AffineForOp>()` 接口生成分块内循环 `affine.for` 操作。新生成的 `affine.for` 操作的循环体中放入的是此前的整个根循环操作，而不只是根循环体里的操作。然后，以新生成的 `affine.for` 操作为新的根操作，调用 `b.create<AffineForOp>()` 接口，生成另一层分块内循环 `affine.for` 操作。依此处理，直到生成的分块内循环数量达到原始循环嵌套深度（`width`）。所有生成的分块内循环 `affine.for` 操作保存在 `tiledLoops` 数组中。该数组长度为原始循环嵌套深度的两倍，因为每个原始循环会被分解为分块内循环和分块间循环。

例如，测试用例 `simple_matmul.mlir` 的原始循环嵌套根操作为 `affine.for %i = 0 to 256`，为该根操作生成的分块内循环为 `affine.for %arg3 = 0 to 0 {}`。此时循环体为空（除隐式终结操作外），初始上下界设为 0。将原始根操作整体移入分块内循环后，分块内循环及其循环体如下：

```mlir

    affine.for %arg5 = 0 to 256 {
      affine.for %arg6 = 0 to 250 {
        %0 = affine.load %arg0[%arg4 + 1, %arg6 + 2]
            : memref<257x256xvector<64xf32>>
        // ... 原书省略的其余计算。
```

### 5.3.2 AffineLoopFusion pass 工作流程

循环融合是一种循环变换方法，用于将多个具有相同或兼容迭代范围的循环嵌套合并为一个具有统一迭代范围的循环，其目的是提高时间局部性、减少开销，并为其他编译优化技术的实施创造条件。

在 MLIR 中，AffineLoopFusion pass 实现的是一种基于切片（slicing-based）和依赖图的循环嵌套融合方法。该 pass 工作粒度为 MLIR 块（block，即一系列经过排序的操作），其核心流程包括构建分析数据依赖关系的内存依赖图，并在此基础上结合贪婪（greedy）融合、生产者-消费者（producer-consumer）融合和兄弟（sibling）融合等模式对循环结构进行优化。通过循环融合生成的新循环嵌套可以用更小的局部缓冲区代替原始的 memref，从而减少访存开销，提升数据复用率。为了评估融合优化引入的代价，AffineLoopFusion pass 使用计算成本和内存占用量两个指标评估各融合模式效果，以决定是否执行融合。

如前文 5.1.1 节中第 4 点所述，多面体模型需要为被分析的程序构造依赖关系表示。为此，AffineLoopFusion pass 使用 `MemRefDependenceGraph` 结构，以 memref 依赖图形式管理块中的内存访问依赖关系。memref 依赖图中的节点表示块中的顶层内存访问单元，既可以是以 `affine.for` 为根节点的循环嵌套结构（其内部包含若干加载或存储操作，如 `affine.load` 或 `affine.store`），也可以是直接在顶层定义的加载或存储操作。图中的边表示节点之间的 memref 依赖关系，也会记录 SSA 值的定义-使用关系。此处的内存依赖关系一般是写后读（RAW）、写后写（WAW）或读后写（WAR），在兄弟融合模式下还关注读后读（RAR）的共同读取关系。

> 校订注：RAR 不要求两次读取保持先后顺序，不是读写冲突意义上的依赖。后面的图构造代码对两个纯读取节点不添加 memref 冲突边；兄弟融合利用共享读取寻找复用机会，不应理解成图里一定建立了 RAR 边。

AffineLoopFusion pass 在依赖图的基础上支持贪婪融合、生产者-消费者融合和兄弟融合三种融合模式，这些模式在枚举类型 `FusionMode` 中定义如下：

<!-- 原书第 194 页；PDF 第 38 页。 -->

```cpp
enum FusionMode { Greedy, ProducerConsumer, Sibling };
```

其中，贪婪融合模式是生产者-消费者融合和兄弟融合模式的结合，因此，本节通过分析 AffineLoopFusion pass 在生产者-消费者融合和兄弟融合两个测试用例上的执行过程，详细介绍这两种融合模式的实现方法。

因为计算模式和张量数据流特性，在深度学习模型中多个连续的循环嵌套间通常存在生产者-消费者关系。当某个循环嵌套负责计算或产生中间结果数据，并将其写入内存或缓冲区时，该循环嵌套即为生产者循环；当某个后续循环嵌套读取这些中间结果数据，并将其作为输入执行下一步计算时，该循环嵌套即为消费者循环。如果中间结果数据规模较大，由于上述生产者循环和消费者循环在时间和空间上解耦，生产者循环的写入方式和消费者循环的读取方式不同，或生产者循环写入数据后消费者循环读取数据延迟过长，都可能导致缓存未命中。

生产者-消费者融合模式的目标是将生产者和消费者循环融合为单一循环嵌套，减少中间缓冲区的使用，使生产者循环写入数据后消费者循环尽快读出，并使生产者和消费者循环访问的数据尽量位于同一缓存行或缓存块中，以提高缓存命中率。

本小节使用如下测试用例 `loop_fusion.mlir` 辅助分析 AffineLoopFusion pass 的生产者-消费者融合执行过程：

```mlir
func.func @producer_consumer_fusion(%arg0: memref<10xf32>,
                                     %arg1: memref<10xf32>) {
  %0 = memref.alloc() : memref<10xf32>
  %1 = memref.alloc() : memref<10xf32>
  %cst = arith.constant 0.000000e+00 : f32
  affine.for %arg2 = 0 to 10 {
    affine.store %cst, %0[%arg2] : memref<10xf32>
    affine.store %cst, %1[%arg2] : memref<10xf32>
  }
  affine.for %arg2 = 0 to 10 {
    %2 = affine.load %0[%arg2] : memref<10xf32>
    %3 = arith.addf %2, %2 : f32
    affine.store %3, %arg0[%arg2] : memref<10xf32>
  }
  affine.for %arg2 = 0 to 10 {
    %2 = affine.load %1[%arg2] : memref<10xf32>
    %3 = arith.mulf %2, %2 : f32
    affine.store %3, %arg1[%arg2] : memref<10xf32>
  }
  return
}
```

AffineLoopFusion pass 融合过程的入口函数为 `LoopFusion::runOnOperation()`，原书代码实现如下：

```cpp
void LoopFusion::runOnOperation() {
  for (Region &region : getOperation()->getRegions())
    for (Block &block : region.getBlocks())
      runOnBlock(&block);
}
```

`runOnOperation()` 函数遍历当前操作的所有区域和块，并对每个块调用 `runOnBlock()` 函数，执行具体的循环融合逻辑。块是 MLIR 中代码的基本组织单元，此处作为执行循环融合的基本粒度。AffineLoopFusion pass 主要功能由 `runOnBlock()` 函数实现，大体分为构建内存依赖图、执行生产者-消费者融合和执行兄弟融合三个部分，代码实现如下：

```cpp
void LoopFusion::runOnBlock(Block *block) {
  MemRefDependenceGraph g(*block);
  if (!g.init())
    return;
  std::optional<unsigned> fastMemorySpaceOpt;
  if (fastMemorySpace.hasValue())
    fastMemorySpaceOpt = fastMemorySpace;
  unsigned localBufSizeThresholdBytes = localBufSizeThreshold * 1024;
  GreedyFusion fusion(&g, localBufSizeThresholdBytes, fastMemorySpaceOpt,
                      maximalFusion, computeToleranceThreshold);
  if (affineFusionMode == FusionMode::ProducerConsumer)
    fusion.runProducerConsumerFusionOnly();
  else if (affineFusionMode == FusionMode::Sibling)
    fusion.runSiblingFusionOnly();
  else
    fusion.runGreedyFusion();
}
```

#### 1. 构建内存依赖图

循环融合过程需要根据块中的访存关系分析循环间的读写依赖关系。因此，`runOnBlock()` 函数首先调用 `MemRefDependenceGraph::init()` 函数对依赖图进行初始化，为后续的依赖分析和融合操作做好准备。`MemRefDependenceGraph::init()` 函数代码实现如下（保留原书主要摘录范围）：

```cpp
bool MemRefDependenceGraph::init() {
  DenseMap<Value, SetVector<unsigned>> memrefAccesses;
  DenseMap<Operation *, unsigned> forToNodeMap;
  for (Operation &op : block) {
    if (auto forOp = dyn_cast<AffineForOp>(op)) {
      // affine.for 操作的图节点实例生成代码。

      collector.collect(&op);
      if (collector.hasNonAffineRegionOp)
        return false;

        node.loads.push_back(opInst);
        auto memref = cast<AffineReadOpInterface>(opInst).getMemRef();
        memrefAccesses[memref].insert(node.id);
      }
      for (auto *opInst : collector.storeOpInsts) {
        node.stores.push_back(opInst);
        auto memref = cast<AffineWriteOpInterface>(opInst).getMemRef();
        memrefAccesses[memref].insert(node.id);
      }
      forToNodeMap[&op] = node.id;
      nodes.insert({node.id, node});
    } else if (auto loadOp = dyn_cast<AffineReadOpInterface>(op)) {
      // ... 原书省略：顶层 load 节点及访问记录。
    } else if (auto storeOp = dyn_cast<AffineWriteOpInterface>(op)) {
      // ... 原书省略的顶层 store 分支；按当前源码补出分支位置。
    } else if (op.getNumResults() > 0 && !op.use_empty()) {
      // 被其他节点使用的操作的图节点实例生成代码。
      Node node(nextNodeId++, &op);
      nodes.insert({node.id, node});
    } else if (isa<CallOpInterface>(op)) {
      // ... 原书省略的调用处理；当前版本使用更一般的内存效果判断。
    }
    // ... 当前版本还处理其他有内存效果的操作及不支持的区域操作。
  }
  for (auto &idAndNode : nodes) {
    const Node &node = idAndNode.second;
    if (!node.stores.empty())
      continue;
    Operation *opInst = node.op;
    for (Value value : opInst->getResults()) {
      for (Operation *user : value.getUsers()) {
        if (block.getParent()->findAncestorOpInRegion(*user)->getBlock()
            != &block)
          continue;
        SmallVector<AffineForOp, 4> loops;
        getAffineForIVs(*user, &loops);
        auto *it = llvm::find_if(loops, [&](AffineForOp loop) {
          return loop->getBlock() == &block;
        });
        if (it == loops.end())
          continue;
        unsigned userLoopNestId = forToNodeMap[*it];
        addEdge(node.id, userLoopNestId, value);
      }
    }
  }
  for (auto &memrefAndList : memrefAccesses) {
    unsigned n = memrefAndList.second.size();
    for (unsigned i = 0; i < n; ++i) {
      unsigned srcId = memrefAndList.second[i];
      bool srcHasStore =
          getNode(srcId)->getStoreOpCount(memrefAndList.first) > 0;
      for (unsigned j = i + 1; j < n; ++j) {
        unsigned dstId = memrefAndList.second[j];
        bool dstHasStore =
            getNode(dstId)->getStoreOpCount(memrefAndList.first) > 0;
        if (srcHasStore || dstHasStore)
          addEdge(srcId, dstId, memrefAndList.first);
      }
    }
  }
  return true;
}
```

#### 2. 执行生产者-消费者融合

构建内存依赖图的目的是分析循环间依赖，确定不同循环是否可以融合。具体融合模式由 AffineLoopFusion pass 定义的 `GreedyFusion` 结构体实现。默认情况下，调用 `runGreedyFusion()` 函数，综合考虑生产者-消费者和兄弟融合模式，按贪婪模式尝试候选融合组合。如果从外部调用 AffineLoopFusion pass 的构造函数 `createLoopFusionPass()` 时指定了选项参数 `affineFusionMode`，则调用该参数值（`FusionMode` 枚举值）对应的融合模式实现函数完成循环融合。

`runGreedyFusion()` 函数实现逻辑涵盖了 `runProducerConsumerFusionOnly()` 和 `runSiblingFusionOnly()` 函数的核心功能，该函数实现代码如下：

```cpp
void runGreedyFusion() {
  fuseProducerConsumerNodes(/*maxSrcUserCount=*/1);
  fuseSiblingNodes();
  fuseProducerConsumerNodes(
      /*maxSrcUserCount=*/std::numeric_limits<unsigned>::max());
  eraseUnusedMemRefAllocations();
}
```

`runGreedyFusion()` 函数实现了一个多阶段的综合融合模式，尝试最大化融合收益。第一阶段调用 `fuseProducerConsumerNodes()` 函数并将函数参数 `maxSrcUserCount` 设置为 1，执行单一消费者的生产者-消费者融合模式。第二阶段调用 `fuseSiblingNodes()` 函数执行融合无依赖边冲突节点的兄弟融合模式。第三阶段再次调用 `fuseProducerConsumerNodes()` 函数，并将函数参数 `maxSrcUserCount` 设置为无符号整数（`unsigned`）最大值，即不限制生产者对应的消费者数量，尝试进一步融合剩余的生产者和消费者。最后，`runGreedyFusion()` 函数调用 `eraseUnusedMemRefAllocations()` 函数，清理未使用的缓冲区分配，减少生成程序的内存需求。

> 校订注：原书“尝试所有可能的融合组合”不应理解为穷举或全局最优保证。源码采用固定阶段的贪婪流程，甚至将整个流程重复到不动点仍列为 TODO。删除分配操作是编译期 IR 变换，不是编译器此时释放了目标程序的运行时缓冲区。

本节重点分析 `fuseProducerConsumerNodes()` 函数和 `fuseSiblingNodes()` 函数功能。前者的代码实现如下：

```cpp
void fuseProducerConsumerNodes(unsigned maxSrcUserCount) {
  init();
  while (!worklist.empty()) {
    unsigned dstId = worklist.back();
    worklist.pop_back();
    performFusionsIntoDest(dstId, maxSrcUserCount);
  }
}
```

以上代码逻辑分为初始化工作列表（worklist）和生产者-消费者融合两个部分。初始化工作列表功能由 `GreedyFusion::init()` 函数实现，目的是将上一小节构建的内存依赖图中的所有节点 id 添加到工作列表中，后续调用的 `performFusionsIntoDest()` 函数将工作列表中的各节点 id 作为目的循环节点 id（`dstId`）参数，尝试将其他符合条件的源（生产者）循环融合到该目的循环中。

`performFusionsIntoDest()` 函数是完成生产者-消费者融合的核心函数。该函数的逻辑结构主体是一个 `do-while` 循环。循环条件 `dstNodeChanged` 表示目的循环节点（`dstNode`）是否发生了变化。如果在本轮迭代中成功执行了一次融合操作（`dstNodeChanged = true`），导致目的循环发生变化并可能由此创造新的融合机会，则 `do-while` 循环继续进行下一轮迭代，以尝试执行更多可能的融合。

##### （1）获取候选源循环节点

如上所述，生产者-消费者融合的目的循环节点由 `performFusionsIntoDest()` 函数参数 `dstId` 确定，与目的循环节点融合的候选源循环节点则由 `performFusionsIntoDest()` 函数调用 `getProducerCandidates()` 函数获得。目的循环节点与候选源循环节点之间的联系纽带是二者读出和写入的同一共享 memref。例如，当目的循环节点为上述 `nodes` 集合中的节点 5 时，其中的 `affine.load` 操作读出 memref `%1`，节点 3 的 `affine.store` 操作写入 `%1`（`%1` 即为图 5-16 中对节点 5 而言的 `consumedMemrefs`）。因此，节点 3 是节点 5 可尝试融合的有效候选源循环节点。测试用例中候选源循环节点、目的循环节点与 memref 的关系如图 5-16 所示。

<!-- 原书第 202 页；PDF 第 46 页。 -->

图 5-16　候选源循环节点、目的循环节点与 memref。左侧源节点 `srcNode = 3` 分别写入中间的 `%0`、`%1`；右侧两个目的节点分别为 4、5，虚线数据流为 `3 → %0 → 4` 和 `3 → %1 → 5`。中间两个矩形标为 `consumedMemrefs`，分别表示对应消费者读取的 memref；对于固定的 `dstNode = 5`，集合仅为 `{%1}`，不是同时包含 `%0`。

为了从 `dstNode` 出发，获得对应的候选源循环节点，`getProducerCandidates()` 函数首先遍历 `dstNode` 的 `loads` 集合中的所有 `affine.load` 操作，并将其 memref 操作数保存在 `consumedMemrefs` 集合（如图 5-16 所示）中。遍历 `dstNode` 的入边（in-edge）可以找到对应的源节点（`srcNode`）。如果该源节点是循环节点，且遍历其 `stores` 集合中的所有 `affine.store` 操作，能找到任一 `affine.store` 操作写入的 memref 存在于 `consumedMemrefs` 集合中，则说明该源节点是 `dstNode` 的数据生产者，满足候选源循环节点条件。虽然从以上依赖图中可以看到，`dstNode` 节点 5 的两条入边分别对应节点 1 和节点 3，但仅有节点 3 的 `affine.store` 操作写入 `%1`，满足候选源循环节点条件。所有满足条件的候选源循环节点均保存在 `srcIdCandidates` 集合中。

`performFusionsIntoDest()` 函数接下来遍历 `srcIdCandidates` 集合中的候选源循环节点并尝试融合。作为评估融合成本功能的一部分，`performFusionsIntoDest()` 函数调用 `gatherProducerConsumerMemrefs()` 函数收集候选源循环节点写入且目的循环节点读取的共享 memref，并保存在集合 `producerConsumerMemrefs` 中，其逻辑与上述收集 `consumedMemrefs` 集合类似。由图 5-16 可知，候选源循环节点 3 和目的循环节点 5 的此类共享 memref 只有 `%1`，因此集合 `producerConsumerMemrefs` 中只有 memref `%1`。

随后，`performFusionsIntoDest()` 函数调用 `gatherEscapingMemrefs()` 函数，收集源循环写入的逃逸 memref（escaping memref）。在循环融合上下文中，原书将相关判断分为以下四种情况。

第一，memref 是没有定值操作的块参数（如函数参数、循环参数、区域参数等），这些 memref 不是由该块内的分配操作定义的局部独占缓冲区，因此保守地视为逃逸 memref。第二，由 `memref.view` 或 `memref.subview` 等实现 `ViewLikeOpInterface` 的操作创建的另一个 memref 的别名，需要递归检查其源 memref 是否逃逸；如果源 memref 是逃逸的，则别名也是逃逸的。第三，如果 memref 有定值操作，而该操作不满足对这个 memref 仅有 `MemoryEffects::Allocate` 效果的检查，则不能保证其别名独立性，因此视为逃逸 memref。第四，如果 memref 在被检查的当前块中被非仿射解引用操作（即不支持 `AffineMapAccessInterface` 的操作）使用，则超出这里的仿射访存分析范围，应保守地视为逃逸 memref。

上述条件判断逻辑在 `gatherEscapingMemrefs()` 函数调用的 `isEscapingMemref()` 函数中实现。满足相关逃逸条件的 memref 被保存在逃逸 memref 集合 `srcEscapingMemRefs` 中。在后续判断源循环是否可以被删除，以及为源循环和目的循环的共享 memref 创建私有 memref 副本过程中都要用到逃逸 memref 集合。

> 校订注：原书说只检查 `producerConsumerMemrefs` 中的共享 memref，源码实际遍历源节点的全部 `stores`；否则可能漏掉仍被外部观察的其他输出。view 的源不逃逸也不意味着 view 一定不逃逸，后续分配效果与用户检查仍会执行。原书所谓“作用域超出当前块”应理解为这里的局部存储所有权假设不成立，不是说所有循环块参数的 SSA 词法作用域都向外延伸。

<!-- 原书第 203 页；PDF 第 47 页。 -->

测试用例的候选源循环和目的循环的共享 memref 只有 `%1`，且 memref `%1` 不触发上述逃逸条件，因此 memref `%1` 不是逃逸 memref。源节点写入的另一个 memref `%0` 同样不逃逸，故 `srcEscapingMemRefs` 集合为空。

##### （2）计算融合循环插入点

在确定候选源循环和目的循环后，还应考虑将二者融合后的融合循环嵌套的插入位置。因为在候选源循环和目的循环间往往存在其他操作，这些操作如果与候选源循环或目的循环中的操作存在依赖关系，则选择融合循环嵌套的插入点位置（插入点位置实际上对应某一个操作的位置）不应导致原有依赖关系被破坏。如果没有找到合适的插入点，则返回空指针，表示融合不可行。

`performFusionsIntoDest()` 函数调用 `getFusedLoopNestInsertionPoint()` 函数，根据数据依赖关系计算融合后循环嵌套的插入点。

`getFusedLoopNestInsertionPoint()` 函数参数分别为 `srcId` 和 `dstId`。在测试用例中，`srcId` 对应候选源循环节点 3，`dstId` 对应目的循环节点 5。节点 3 和节点 5 中间的节点 4 中有 `affine.load %0`、`arith.addf` 等操作，且节点 4 中的 `affine.load %0` 操作依赖于节点 3 中的 `affine.store %cst, %0` 操作。节点 3、4、5 的先后顺序如图 5-17 所示。

图 5-17　计算融合循环插入点。左侧依赖子图以节点 1 为上方 `dstDepInsts`，节点 3 为左侧 `srcNodeInst`，节点 5 为右侧 `dstNodeInst`，节点 4 为下方 `srcDepInsts`；实线 `1 → 3`、`1 → 5` 表示 SSA 值依赖，虚线 `3 → 4`、`3 → 5` 表示读写依赖。原图在 `3 → 5` 的边上画叉，表示计算外部插入限制时不将源、目的之间的这条内部边作为外部限制。

右侧从上到下排列四个代码框，内容与前述完整测试例对应：

```text
Node 1 / dstDepInsts：%1 = memref.alloc() : memref<10xf32>
Node 3 / srcNodeInst：循环 0..9，向 %0 和 %1 写入 %cst
────────────────── 融合循环插入点（Node 4 之前）
Node 4 / srcDepInsts / firstSrcDepPos：
  循环 0..9，load %0，arith.addf，将结果 store 到 %arg0
Node 5 / dstNodeInst：
  循环 0..9，load %1，arith.mulf，将结果 store 到 %arg1
```

右侧连线分别强调 `%0` 从 Node 3 写入到 Node 4 读取，以及 `%1` 从 Node 1 定义到 Node 5 使用的关系。原图把 Node 1 的分配标成“写入 %1”，这里应为“分配／定义 %1”；`memref.alloc` 本身不初始化元素。

显然，如果节点 3 和节点 5 融合后的循环嵌套被整体移到节点 4 中的 `affine.load %0` 操作之后，该 `affine.load %0` 操作与节点 3 中的 `affine.store %cst, %0` 操作间原有的数据依赖关系将被破坏。

为了正确计算插入点，`getFusedLoopNestInsertionPoint()` 函数通过 `srcId` 的出边收集与 `srcId` 对应节点 `srcNodeInst` 有依赖关系的、非 `dstId` 节点集合 `srcDepInsts`，并通过 `dstId` 的入边收集与 `dstId` 对应节点 `dstNodeInst` 有依赖关系的、非 `srcId` 节点集合 `dstDepInsts`。在测试用例中，`srcId` 对应的节点 3（`srcNodeInst`）的出边分别连接节点 4 和节点 5，但节点 5 是 `dstId` 对应的节点，将其排除后，节点 3 的 `srcDepInsts` 集合中只有节点 4。`dstId` 对应的节点 5（`dstNodeInst`）的入边分别连接节点 1 和节点 3，但节点 3 是 `srcId` 对应的节点，将其排除后，节点 5 的 `dstDepInsts` 集合中只有节点 1。图 5-17 左侧描述了 `srcNodeInst`、`dstNodeInst` 节点与 `srcDepInsts`、`dstDepInsts` 集合在依赖图中的关系。

<!-- 原书第 204 页；PDF 第 48 页。上段跨页。 -->

集合 `srcDepInsts` 中的操作与 `srcNodeInst` 中的操作存在依赖关系，表现为 `srcNodeInst` 中的操作写入某个 memref 后被 `srcDepInsts` 中的操作读出。如图 5-17 右侧所示，在测试用例中，节点 3（`srcNodeInst`）中的 `affine.store %cst, %0` 操作向 memref `%0` 写入 0，节点 4（`srcDepInsts`）中的操作 `affine.load %0` 读出 memref `%0` 的值。而且，集合 `dstDepInsts` 中的操作与 `dstNodeInst` 中的操作也存在依赖关系，表现为 `dstDepInsts` 中的操作定义或写入某个 memref 后，被 `dstNodeInst` 中的操作使用。在测试用例中，节点 1（`dstDepInsts`）定义 memref `%1`，节点 5（`dstNodeInst`）中的操作 `affine.load %1` 读出 memref `%1` 的值。为了确保融合循环嵌套不破坏上述依赖关系，融合循环嵌套插入点应位于 `srcDepInsts` 集合的第一个相关操作之前（`firstSrcDepPos`），并位于 `dstDepInsts` 集合的最后一个相关操作之后（`lastDstDepPos`）。经过 `getFusedLoopNestInsertionPoint()` 函数计算，测试用例的节点 3 和节点 5 融合后的循环嵌套插入点应位于 Node 4 之前，如图 5-17 右侧所示。

> 校订注：原书把 Node 5 的 `affine.load %1` 读出对象误写为 `%0`，已更正。这里选择的是包含整个循环的块级插入位置，而不是任意移动到 Node 4 循环体内部。

如果目的循环有复杂的循环结构，且不同的 `affine.load` 或 `affine.store` 操作处于不同的循环嵌套层次，则需要调用 `getInnermostCommonLoopDepth()` 函数计算这些相关操作在循环嵌套结构中公共最内层循环深度，也就是这些操作共同拥有的最深层的 `affine.for` 操作所在深度。

测试用例中循环结构简单，不存在多层循环嵌套，由 `getInnermostCommonLoopDepth()` 函数计算得到的最内层公共循环深度为 1。因此，本例没有多个候选深度之间的选择问题。为了简化论述，下文按这一单层情况展开，不额外讨论循环深度因素。

##### （3）判断循环融合可行性

在真正进行循环融合之前还应判断融合可行性。`performFusionsIntoDest()` 函数通过调用 `canFuseLoops()` 函数，判断将以函数参数 `srcForOp` 为根的源循环嵌套融合进以函数参数 `dstForOp` 为根的目的循环嵌套中的可行性。如果融合后不破坏原有依赖关系等一系列条件，则认为融合可行。`canFuseLoops()` 函数代码实现如下：


`canFuseLoops()` 函数的核心功能是构造切片并集（slice union）。构造计算切片并集涉及构造源点／汇点操作对的依赖约束系统、获得切片状态信息和切片有效性判断三部分功能。如果经过这三部分功能能够得到有效计算切片并集，并通过其余前置检查，`canFuseLoops()` 函数就可以判定源循环与目的循环的融合可行。根据上述代码可总结得到 `canFuseLoops()` 函数调用流程图，如图 5-18 所示。

如以上代码所示，`canFuseLoops()` 函数首先需要检查一系列前置条件，包括检查源循环和目的循环是否属于同一个块、是否能为融合循环找到合适的插入点，以及生产者-消费者融合模式在指定循环深度是否能保持循环依赖关系。

此外，`canFuseLoops()` 函数两次调用 `gatherLoadsAndStores()` 函数，分别从按块内先后顺序排列的循环嵌套 `forOpA` 和 `forOpB` 中收集 `affine.load` 和 `affine.store` 操作，并分别保存在集合 `opsA` 和 `opsB` 中。在本例中，先执行的 `forOpA` 即源循环，`forOpB` 即目的循环。对于生产者-消费者融合模式，从 `opsA` 过滤到 `strategyOpsA` 中的只有写操作；对于兄弟融合模式，过滤保留的是读取指定共享 memref 的读操作。无论何种模式，`opsB` 集合收集所有相关的 `affine.load` 和 `affine.store` 操作。

在生产者-消费者融合模式中，`canFuseLoops()` 函数关注分别来自过滤后的源集合和 `opsB` 集合、且访问同一共享 memref 的操作对，将其作为后续依赖分析的候选源点／汇点操作对。

对于测试用例 `loop_fusion.mlir`，源循环为 `affine.for 0`，源集合中包括 `affine.store %cst, %0[%arg2]` 和 `affine.store %cst, %1[%arg2]` 两个源点操作；目的循环为 `affine.for 2`，`opsB` 中包括 `%2 = affine.load %1[%arg2]` 和 `affine.store %3, %arg1[%arg2]` 两个汇点操作。其中，源集合中的 `affine.store %cst, %1[%arg2]` 源点操作和 `opsB` 中的 `%2 = affine.load %1[%arg2]` 汇点操作读写同一共享 memref `%1`，结合相同的访问下标和迭代范围，可确认其间存在写后读依赖关系。

在检查一系列前置条件并构造上述集合后，`canFuseLoops()` 函数调用 `computeSliceUnion()` 函数遍历源点／汇点操作对，为每一对相关操作构造计算切片（computation slice，下文将解释其含义），并计算切片边界的合并结果，验证其是否有效。

`computeSliceUnion()` 函数的功能主体是一个双层 `for` 循环嵌套。该双层循环遍历传入的源、汇操作集合，并为每个操作构造 `MemRefAccess` 实例。为源点操作构造的 `MemRefAccess` 实例被称为源访问实例（`srcAccess`），为汇点操作构造的 `MemRefAccess` 实例被称为目的访问实例（`dstAccess`）。`MemRefAccess` 类的功能简介见 5.3.1 节第 2 点。当两个操作分别来自源、汇集合时，可由二者各自的 `MemRefAccess` 实例得到操作访问的 memref。如果两个操作访问的 memref 相同，则继续分析是否存在依赖关系。

> 校订注：原书混用了收集前的 `opsA` 和策略过滤后的 `strategyOpsA`，并两次把“同一 memref”直接当成“存在依赖”。访问相同缓冲区但下标区域不相交时可以没有依赖，原书下一页也给出了这种例子；因此这里改为候选筛选，实际判定由下面的约束检查完成。

为了表示源和目的访问实例在循环迭代空间中的线性关系，`computeSliceUnion()` 函数随后调用 `checkMemrefAccessDependence()` 函数，通过 Presburger 空间及约束关系为 `srcAccess` 和 `dstAccess` 构造各自对应的访问关系，建立循环索引变量到内存索引变量的访问映射，并进一步通过求逆、合成和添加顺序约束等接口，计算依赖约束系统（`dependenceConstraints`）。通过依赖约束系统可以检查访问同一 memref 的源、目的访问实例间是否存在依赖关系。如果根据依赖约束系统能确定这两个访问实例在相应顺序条件下不会访问同一内存地址，则返回 `NoDependence`；如果存在满足约束的同址访问，则返回 `HasDependence`，还可按需返回依赖分量。若分析失败，则不能把失败当成无依赖。

对于测试用例 `loop_fusion.mlir`，由源集合中的 `affine.store %cst, %1[%arg2]` 源点操作和 `opsB` 中的 `%2 = affine.load %1[%arg2]` 汇点操作的内存索引表达式 `%1[%arg2]`，可得到循环索引变量到内存索引变量（以 `AffineMap` 形式表示）的访问映射为 `(d0) -> (d0)`，即内存索引变量等于循环索引变量。源点操作所属的源循环为：

<!-- 原书第 207 页；PDF 第 51 页。上段跨页。 -->

```mlir
affine.for %arg2 = 0 to 10 {
  affine.store %cst, %0[%arg2] : memref<10xf32>
  affine.store %cst, %1[%arg2] : memref<10xf32>
}
```

汇点操作所属的目的循环为（将原书数学区分记号 `%arg2'` 在 MLIR 代码中写为 `%arg2_dst`）：

```mlir
affine.for %arg2_dst = 0 to 10 {
  %2 = affine.load %1[%arg2_dst] : memref<10xf32>
  %3 = arith.mulf %2, %2 : f32
  affine.store %3, %arg1[%arg2_dst] : memref<10xf32>
}
```

由于源和目的循环的循环索引变量范围均为 `[0, 10)`，因此，由访问实例 `srcAccess`、`dstAccess` 得到的访问关系均具有以下形式：

```text
 (1) * %arg2 + (-1) * x + 0  = 0
 (1) * %arg2 +  (0) * x + 0 >= 0
(-1) * %arg2 +  (0) * x + 9 >= 0
```

其中，假设内存索引变量用 x 表示，即 `x = %arg2`。在这个例子中，源和目的访问实例的访问关系形式完全相同，目的实例对应的循环变量应换为 `%arg2'`。根据上述访问关系，经过求逆、合成和添加顺序约束后得到的依赖约束系统（`dependenceConstraints`）为：

```text
(-1) * %arg2 +  (1) * %arg2' + 0  = 0
 (1) * %arg2 +  (0) * %arg2' + 0 >= 0
(-1) * %arg2 +  (0) * %arg2' + 9 >= 0
 (0) * %arg2 +  (1) * %arg2' + 0 >= 0
 (0) * %arg2 + (-1) * %arg2' + 9 >= 0
```

为了区分，此处以 `%arg2` 表示源循环的索引变量，以 `%arg2'` 表示目的循环的索引变量。上述依赖约束系统中的第一项为 `%arg2 = %arg2'`，表示 `srcAccess` 和 `dstAccess` 访问相同地址。

由上述过程计算所得依赖约束系统可以看到，源和目的访问实例分别表示的写访问和读访问引用了相同的内存元素 `%1[%arg2]`，且内存索引变量取值均落在合法循环范围 `[0, 9]` 内。因此，`checkMemrefAccessDependence()` 函数可以判定源和目的访问实例之间存在依赖关系（`HasDependence`）。如需要，`checkMemrefAccessDependence()` 函数可通过 `DependenceComponent` 组成的输出参数 `dependenceComponents` 返回依赖分量信息；原书将其概括为方向向量。

如果对测试用例 `loop_fusion.mlir` 略做修改，将其中的汇点操作 `%2 = affine.load %1[%arg2_dst]` 对应的 `affine.for` 操作循环范围改为 `[10, 19]`，即 `affine.for %arg2_dst = 10 to 20`，此时汇点操作和源点操作访问的内存范围不重叠，由上述过程计算得到的依赖约束系统为：

<!-- 原书第 208 页；PDF 第 52 页。 -->

```text
(-1) * %arg2 +  (1) * %arg2' +     0  = 0
 (1) * %arg2 +  (0) * %arg2' +     0 >= 0
(-1) * %arg2 +  (0) * %arg2' +     9 >= 0
 (0) * %arg2 +  (1) * %arg2' + (-10) >= 0
 (0) * %arg2 + (-1) * %arg2' +    19 >= 0
```

由于等式 `%arg2 = %arg2'` 与约束 `%arg2 <= 9`、`%arg2' >= 10` 相互冲突，没有任何一对 `%arg2`、`%arg2'` 索引变量能同时满足上述所有约束，因此，`checkMemrefAccessDependence()` 函数判定源和目的访问实例之间不存在依赖关系（`NoDependence`）。

> 校订注：这组不相交访问关系的数学结论成立，但不能只改循环上界便执行原来的 `memref<10xf32>` 程序。若要运行，相关 `%1`、`%arg1` 缓冲区及访问类型至少应扩为 20 个元素，且读取的 `%1[10..19]` 必须另外初始化。无依赖不等于没有越界或未初始化读取。

在获得源点／汇点操作对的依赖约束系统后，如果判断源和目的访问实例之间存在依赖关系，则 `computeSliceUnion()` 函数调用 `getComputationSliceState()` 函数，根据上述依赖约束系统获得计算切片的循环边界及相关操作数、源循环索引变量等切片状态信息，并保存在函数输出参数 `sliceState` 中。`sliceState` 的类型为 `ComputationSliceState` 结构体，其中记录了切片循环嵌套的索引变量集合（`ivs`）、由 `AffineMap` 表示的循环上下界集合（`lbs`、`ubs`），以及与循环上下界相关联的操作数集合（`lbOperands`、`ubOperands`）等切片状态信息。根据切片状态信息可将源循环中与目的循环相关的迭代空间和操作提取出来，并将其与目的循环融合。

计算切片的循环索引变量用源点操作所属源循环的循环索引变量 `%arg2` 表示。计算切片的上下界以汇点操作所属目的循环的循环索引变量 `%arg2'` 为变量表示，即由 `%arg2'` 推导出 `%arg2` 的上下界。后续融合过程将根据 `getComputationSliceState()` 函数输出的切片状态对象生成反向（backward）计算切片：

```mlir
affine.for %arg2 = affine_map<(d0) -> (d0)>(%arg2_dst)
    to affine_map<(d0) -> (d0 + 1)>(%arg2_dst) {
  affine.store %cst, %0[%arg2] : memref<10xf32>
  affine.store %cst, %1[%arg2] : memref<10xf32>
}
```

其中，该循环的含义是 `%arg2` 从 `%arg2_dst` 开始，在到达 `%arg2_dst + 1` 之前停止，即计算切片实际只执行一次迭代（`%arg2 = %arg2_dst`），数学上等价于 `%arg2' <= %arg2 < %arg2' + 1`。单点迭代子空间形式的计算切片可复制依赖相关的源点操作，对齐源和目的循环的迭代空间，为两个访问相同内存范围的循环融合创造条件。上述反向计算切片对应的切片状态对象 `sliceState` 中的 `ivs` 集合为 `{%arg2}`，`lbs` 集合为 `{(d0) -> (d0)}`，`lbOperands` 为 `{{%arg2_dst}}`，`ubs` 集合为 `{(d0) -> (d0 + 1)}`，`ubOperands` 为 `{{%arg2_dst}}`。操作数按每层边界组织，故此处明确写出外层集合。

后续融合过程将上述反向计算切片与目的循环融合后的结果为：

```mlir
affine.for %arg2_dst = 0 to 10 {
  affine.for %arg2 = affine_map<(d0) -> (d0)>(%arg2_dst)
      to affine_map<(d0) -> (d0 + 1)>(%arg2_dst) {
    affine.store %cst, %0[%arg2] : memref<10xf32>
    affine.store %cst, %1[%arg2] : memref<10xf32>
  }
  %2 = affine.load %1[%arg2_dst] : memref<10xf32>
  %3 = arith.mulf %2, %2 : f32
  affine.store %3, %arg1[%arg2_dst] : memref<10xf32>
}
```

<!-- 原书第 209 页；PDF 第 53 页。上面的代码块跨页。 -->

由于内部反向计算切片仅迭代一次，将其展开后的目的循环为：

```mlir
affine.for %arg2_dst = 0 to 10 {
  affine.store %cst, %0[%arg2_dst] : memref<10xf32>
  affine.store %cst, %1[%arg2_dst] : memref<10xf32>
  %2 = affine.load %1[%arg2_dst] : memref<10xf32>
  %3 = arith.mulf %2, %2 : f32
  affine.store %3, %arg1[%arg2_dst] : memref<10xf32>
}
```

在获得当前源点／汇点操作对的计算切片后，`computeSliceUnion()` 函数继续调用 `ComputationSliceState` 结构体中定义的接口 `getAsConstraints()`，根据当前切片状态对象的切片上下界约束构建切片约束系统，并将其与切片并集约束系统实例 `sliceUnionCst` 合并。当前切片约束系统的维度变量为切片状态对象的 `ivs` 集合中的值，符号变量为切片状态对象的 `lbOperands` 或 `ubOperands` 中的值。接口 `getAsConstraints()` 根据上述切片状态对象 `sliceState` 构建的当前切片约束系统为：

```text
 (1) * %arg2 + (-1) * %arg2' + 0  = 0
 (0) * %arg2 +  (1) * %arg2' + 0 >= 0
 (0) * %arg2 + (-1) * %arg2' + 9 >= 0
```

其中，维度变量 `%arg2` 来自 `ivs` 集合中的值，符号变量 `%arg2'` 来自 `lbOperands` 或 `ubOperands` 中的值。等式 `%arg2 = %arg2'` 由下界 `%arg2 >= %arg2'`、排除式上界 `%arg2 < %arg2' + 1` 以及整数性推导得到。

`computeSliceUnion()` 函数为每一对相关的源点／汇点操作构造计算切片及其约束系统，并将所有切片约束系统合并，得到切片并集约束系统实例 `sliceUnionCst`。在测试用例 `loop_fusion.mlir` 的这两个循环之间，只有一对相关的源点／汇点操作，即 `affine.store %cst, %1[%arg2]` 和 `%2 = affine.load %1[%arg2_dst]`，因此，切片并集约束系统与上述当前切片约束系统相同。

由切片并集约束系统实例 `sliceUnionCst` 调用 `convertLoopIVSymbolsToDims()`、`getSliceBounds()` 等接口，可以得到表示切片并集的 `computeSliceUnion()` 函数输出参数 `sliceUnion`（类型为 `ComputationSliceState`）各字段值。`sliceUnion` 与上述切片状态对象类似，也包括循环嵌套的索引变量集合（`ivs`）、循环上下界集合（`lbs`、`ubs`），以及与循环上下界相关联的操作数集合（`lbOperands`、`ubOperands`）等切片状态信息。根据这些信息，`computeSliceUnion()` 函数调用 `ComputationSliceState` 结构体中定义的接口 `isSliceValid()` 判断切片是否有效，即切片在目的循环迭代范围内产生的源迭代点是否均包含在原始源循环的迭代域中。

> 校订注：原书把上述包含关系写反了。有效性要求切片不越出源域，并非要求每次融合都覆盖源循环全部迭代。覆盖源域是后面讨论最大切片和能否删除源循环时的额外问题。

<!-- 原书第 210 页；PDF 第 54 页。 -->

`isSliceValid()` 接口中实现了一种快速判断切片有效性的方法。这个快速路径检查各切片循环是否为由单个目的循环归纳变量约束的单次迭代循环，以及对应源、目的循环变量的上下界是否完全一致。满足这些条件时可直接判定切片有效，并满足这里的最大切片检查。上述 `getComputationSliceState()` 函数生成的反向计算切片即符合这些条件。

如果对测试用例 `loop_fusion.mlir` 略做修改，将目的循环节点 5 的上界改为 5，即 `affine.for %arg2_dst = 0 to 5`，则上述反向计算切片不再是最大切片，因为源循环节点 3 与目的循环节点 5 的覆盖范围不一致。但该切片仍是有效切片，因为切片没有超出源循环迭代域。

如果判定切片有效，即表示 `computeSliceUnion()` 函数构造 `sliceUnion` 成功，在其他前置条件已通过的情况下，也表示 `canFuseLoops()` 函数可以判定源循环与目的循环的融合可行。

> 校订注：原书将最大切片的快速检查概括为“源、目的上下界一致”，遗漏了单次迭代和变量对应条件；这只是充分条件，不是一般定义。快速检查不成立时还需更完整的集合分析。有效切片要求 `sliceSet - srcSet` 为空，最大性则检查源域是否被切片覆盖；两者判断方向不同。

##### （4）计算循环融合收益

循环融合可以带来改善缓存局部性、减少访存开销等诸多收益，但也可能引入冗余计算、增加循环体操作数量等问题。为了在语义合法的基础上选择预计有性能收益的融合，`performFusionsIntoDest()` 函数在执行循环融合前调用 `isFusionProfitable()` 函数，通过在不同目的循环深度评估循环融合前后的计算成本和内存占用量变化，判断将源循环的反向计算切片与目的循环嵌套融合能否产生收益，以避免因盲目融合导致性能下降。

`isFusionProfitable()` 函数参数 `srcOpInst` 和 `dstForOp` 分别指定了源循环中的源点操作（如 `affine.store` 操作）和目的循环。函数参数 `depthSliceUnions` 表示每个合法融合深度下的切片并集，实际上就是上述 `computeSliceUnion()` 函数构造的各深度 `sliceUnion`。

`isFusionProfitable()` 函数判断循环融合是否有收益的指标有两个：计算成本和内存占用量。计算成本通过整个循环嵌套的总操作实例数表示；对本例的单层循环，即有效操作数量乘循环迭代总数。如果与循环融合前相比，融合后增加的冗余计算成本比例不小于指定阈值（`computeToleranceThreshold`，表示融合后可容忍的冗余计算成本比例，默认值为 30%），则该候选不满足此处的成本条件；如果估算的融合后内存占用量超过融合前源循环与目的循环内存占用量之和，亦不接受融合。

通过以下命令设置 `fusion-compute-tolerance` 选项，可修改可容忍冗余计算成本比例 `computeToleranceThreshold` 的默认值：

```sh
mlir-opt --pass-pipeline='builtin.module(func.func(affine-loop-fusion{fusion-compute-tolerance=0}))' loop_fusion.mlir
```

以上命令行将 `computeToleranceThreshold` 值设置为 0。对本例冗余计算比例为 0 的候选，由于源码使用严格小于比较，`0 < 0` 不成立，因此不会通过这个收益检查。

> 校订注：原书命令省略了 `func.func` 嵌套，已与前面的函数级 pass 命令统一。“阈值为 0 就不会融合任何循环”过于绝对：如果估算计算量减少，或使用跳过该成本判断的最大化融合选项，不能由这句话推出同样结论。原文“融合前目的循环加切片”是融合后的估算构成，不是比较右侧；比较右侧应为融合前源循环加目的循环。该模型也不直接证明重用距离最小或实际运行更快。

下文详述计算成本和内存占用量两个收益指标的计算过程。为了获得循环融合前的源循环和目的循环计算成本，`isFusionProfitable()` 函数首先两次调用 `getLoopNestStats()` 函数，分别以源循环和目的循环 `affine.for` 操作为根操作，收集循环嵌套的统计信息（用 `LoopNestStats` 结构体表示），包括根操作的子循环映射、循环迭代总数（trip count）和循环体中包含的操作数量。

<!-- 原书第 211 页；PDF 第 55 页。 -->

测试用例 `loop_fusion.mlir` 中源循环的循环迭代总数为 10，循环体中包含的操作数量为 3（包括两个 `affine.store` 操作和一个 `affine.yield` 操作）。循环体中没有子循环，所以子循环映射为空。上述统计结果保存在循环嵌套统计信息实例 `srcLoopNestStats` 中。

同理，对于测试用例中的目的循环，循环迭代总数为 10，循环体中包含的操作数量为 4（包括一个 `affine.load` 操作、一个 `arith.mulf` 操作、一个 `affine.store` 操作和一个 `affine.yield` 操作）。上述统计结果保存在循环嵌套统计信息实例 `dstLoopNestStats` 中。

然后，`isFusionProfitable()` 函数分别以源循环和目的循环及其对应的循环嵌套统计信息实例 `srcLoopNestStats` 和 `dstLoopNestStats` 为参数，两次调用 `getComputeCost()` 函数，分别获得融合前源循环和目的循环计算成本。根据以上“计算成本 = 操作数量 × 循环迭代总数”的计算方法，融合前源循环计算成本（`srcLoopNestCost`）为 20（= 2 × 10），融合前目的循环计算成本（`dstLoopNestCost`）为 30（= 3 × 10）。注意，获得计算成本时不计入 `affine.yield` 终结操作。

融合后的目的循环计算成本由切片计算成本和融合前的目的循环计算成本构成。为了获得融合后的目的循环计算成本，`isFusionProfitable()` 函数调用 `getFusionComputeCost()` 函数。融合后的目的循环计算成本通过整个目的循环嵌套的总操作实例数表示，此处目的循环体中包含的操作除了融合前目的循环体中原有的操作外，还包括切片循环体中包含的操作。例如，上述反向计算切片与目的循环融合后，切片循环体中包含的操作数量为 2，融合前的目的循环中原有 3 个操作，因此，融合后目的循环体中共有 5 个操作，融合后目的循环计算成本（`fusedLoopNestComputeCost`）为 50（= 5 × 10）。

在获得融合后目的循环计算成本、融合前源循环计算成本和目的循环计算成本后，根据以下方法可以计算得到循环融合后相比融合前增加的冗余计算成本比例：

```text
additionalComputeFraction =
    fusedLoopNestComputeCost / (srcLoopNestCost + dstLoopNestCost) - 1
```

如果 `additionalComputeFraction < computeToleranceThreshold`，则认为循环融合后增加的冗余计算比例在容忍范围内，可以继续评估其他收益条件。对于上述循环融合示例，循环融合前后的计算成本都为 50，`additionalComputeFraction` 为 0，且小于可容忍冗余计算成本默认阈值 30%，因此判定冗余计算成本没有增加。

为了衡量循环融合前后内存开销的变化，`isFusionProfitable()` 函数调用 `MemRefRegion::compute()` 函数，为源循环中的 `affine.store` 源点操作构造 `MemRefRegion` 实例，并调用 `MemRefRegion::getRegionSize()` 函数，根据 `MemRefRegion` 实例中的 memref 操作数类型和内存访问范围计算源点操作的写区域内存占用量。例如，对于测试用例中的源点操作 `affine.store %cst, %1[%arg2]`，其 memref 操作数类型为 `memref<10xf32>`，其访问索引 `%arg2 ∈ [0, 9]`，于是可得原始写区域的内存占用量为 40（= 4 × 10）字节。

> 校订注：当前源码还会以候选 `slice` 调用 `compute(srcStoreOpInst, /*loopDepth=*/0, &slice)`。这里会加入目的循环变量的范围，再投影消去循环变量，因此计算的是全部目的迭代覆盖的切片写区域，本例仍为 40 字节，`sliceMemEstimate` 也是 40。不能将固定一次目的迭代时的单点切片（4 字节）代入这个估算；后续私有缓冲区的大小与这里的全域区域估算是不同问题。

<!-- 原书第 212 页；PDF 第 56 页。 -->

为了获得融合前源循环和目的循环的内存占用量，`isFusionProfitable()` 函数两次调用 `getMemoryFootprintBytes()` 函数，分别计算得到融合前源循环和目的循环中所有内存读写操作的内存占用总量。`getMemoryFootprintBytes()` 函数遍历 `affine.for` 循环中的所有内存读写操作，并调用 `MemRefRegion::compute()` 函数为每个内存读写操作构造 `MemRefRegion` 实例。在此基础上，`MemRefRegion::getRegionSize()` 函数根据 `MemRefRegion` 实例中的 memref 操作数类型和内存访问范围，计算各内存读写操作的内存占用量。`getMemoryFootprintBytes()` 函数的详细功能介绍见“AffineLoopTiling pass 工作流程”小节。

循环融合前，测试用例 `loop_fusion.mlir` 的源循环中包括两个 `affine.store` 操作，其 memref 操作数类型均为 `memref<10xf32>`，其访问索引 `%arg2 ∈ [0, 9]`，因此，融合前源循环中所有内存读写操作的内存占用总量（`srcMemSizeVal`）为 80（= 4 × 2 × 10）字节。同理，融合前测试用例的目的循环中所有内存读写操作（包括一个 `affine.load` 操作和一个 `affine.store` 操作）的内存占用总量（`dstMemSizeVal`）也为 80（= 4 × 2 × 10）字节。

融合后目的循环的内存占用估算（`fusedMem`）由融合前目的循环内存占用量与切片内存占用量两部分构成，即 `fusedMem = dstMemSizeVal + sliceMemEstimate`。如果 `fusedMem > srcMemSizeVal + dstMemSizeVal`，则认为循环融合后内存开销过大，融合没有收益。本例估算 `fusedMem = 120`（= 80 + 40）字节，小于融合前源循环和目的循环内存占用量之和 160（= 80 + 80）字节，因此通过该项检查。

> 校订注：原书的 `120 = 80 + 40 < 160 = 80 + 80` 与此处源码估算一致。这些是启发式成本模型中的值，160 还对两个循环共同访问的 `%1` 重复计数，不能当作整个函数实际分配的不同缓冲区总字节数。

##### （5）执行循环融合

如果上述 `isFusionProfitable()` 函数判断循环融合有收益，`performFusionsIntoDest()` 函数在执行循环融合之前，还应判断源循环被融合进目的循环后是否可以删除，以及是否可以在不违反语义的前提下，为源循环和目的循环的共享 memref 创建私有 memref 副本。通过 memref 私有化可以减少不必要的共享存储和相关依赖，为融合创造条件；必须保留真实的数据流语义。

判断源循环是否可以被删除由 `canRemoveSrcNodeAfterFusion()` 实现。该函数通过遍历内存依赖图实例 `mdg` 中源循环节点的所有出边，判断内存依赖图中除目的循环外是否还有其他节点依赖源循环。对这些节点，必须先确认融合后的插入位置仍位于其前方，以保证结果先产生再被使用。如果没有其他输出依赖，也没有写入逃逸 memref，则可以删除源循环；如果有其他输出依赖或写入逃逸 memref，则还需进一步判断融合切片是否为最大切片。如果判断融合切片为最大切片，说明源循环中的迭代在融合后被完整覆盖，结合前面的依赖位置检查，可删除源循环；否则不能删除源循环。

对于上述测试用例 `loop_fusion.mlir` 中的源循环节点 3，其出边连接节点 4 和目的循环节点 5，因此有除目的循环外的其他节点（节点 4）依赖源循环。但由于源循环的融合切片是最大切片（判断方法见前文“判断循环融合可行性”步骤），且新的循环放在节点 4 前，源循环仍满足删除条件，可以被删除。

判断是否可以私有化 memref 由 `canCreatePrivateMemRef()` 函数实现。此处的私有化是针对集合 `producerConsumerMemrefs` 中由源循环和目的循环共享的 memref。该集合在前文的“获取候选源循环节点”阶段生成。

<!-- 原书第 213 页；PDF 第 57 页。上段跨页。 -->

私有化 memref 必须检查三个条件。第一，如果当前 memref 是 `srcEscapingMemRefs` 集合中的逃逸 memref，则在源循环可被删除的情况下，或在消费者节点（目的循环）中有向该 memref 写入数据的 `affine.store` 操作的情况下，不应私有化共享 memref。因为此时如果为共享 memref 创建私有副本，会导致原本应写入共享 memref 的数据转而写入私有副本，令原共享 memref 中的数据不被更新，进而导致错误。

第二，如果生产者节点（源循环）有与该共享 memref 相关的入边，或消费者节点（目的循环）有与该共享 memref 相关的出边，意味着共享 memref 在上下游还被其他节点依赖，此时不应私有化共享 memref。第三，如果源循环可被删除，但源循环节点通过该共享 memref 的出边又输出给了除目的循环节点外的其他节点，则不应私有化共享 memref，否则将导致其他原本依赖该 memref 的节点的依赖关系被破坏。如果以上三个条件都可以排除，则可以为共享 memref 创建私有 memref 副本，并将该共享 memref 添加到私有化 memref 集合 `privateMemrefs` 中。

如前所述，对于测试用例 `loop_fusion.mlir`，集合 `producerConsumerMemrefs` 中只有非逃逸 memref `%1`，且它满足私有化条件，因此后续会对其执行 memref 私有化过程。

接下来，`performFusionsIntoDest()` 函数可以调用 `fuseLoops()` 函数执行循环融合过程。`fuseLoops()` 函数的功能是将函数参数 `srcForOp` 指定的源循环与函数参数 `dstForOp` 指定的目标循环融合，并根据函数参数 `srcSlice` 指定的计算切片对克隆循环的上下界进行调整。`srcSlice` 是由前文介绍的 `computeSliceUnion()` 函数（见“判断循环融合可行性”部分）构造的切片状态对象，其中保存了切片循环边界和相关操作数等信息。源循环副本在目的循环中的插入点由 `srcSlice` 中的插入点信息决定。

`fuseLoops()` 函数根据 `srcSlice` 中的源循环索引变量（`ivs`）找到该索引变量所属的源循环，并根据 `srcSlice` 提供的源循环上下界 `AffineMap` 和关联操作数，设置复制出的源循环的上下界，将其转换为计算切片。测试用例 `loop_fusion.mlir` 中的源循环为：

```mlir
affine.for %arg2 = 0 to 10 {
  affine.store %cst, %0[%arg2] : memref<10xf32>
  affine.store %cst, %1[%arg2] : memref<10xf32>
}
```

`srcSlice` 切片状态对象中提供的源循环索引变量为 `%arg2`，源循环下界 `AffineMap` 和上界 `AffineMap` 分别为 `(d0) -> (d0)` 和 `(d0) -> (d0 + 1)`，源循环下界操作数和上界操作数均为目的循环变量 `%arg2_dst`（原书 `%arg2'`）。`fuseLoops()` 函数根据上述源循环下界 `AffineMap` 和源循环下界操作数重新设置副本的下界后的结果为：

```mlir
affine.for %arg2 = affine_map<(d0) -> (d0)>(%arg2_dst) to 10 {
  affine.store %cst, %0[%arg2] : memref<10xf32>
  affine.store %cst, %1[%arg2] : memref<10xf32>
}
```

<!-- 原书第 214 页；PDF 第 58 页。 -->

在此基础上，`fuseLoops()` 函数根据上述源循环上界 `AffineMap` 和源循环上界操作数重新设置副本的上界后，得到的计算切片为：

```mlir
affine.for %arg2 = affine_map<(d0) -> (d0)>(%arg2_dst)
    to affine_map<(d0) -> (d0 + 1)>(%arg2_dst) {
  affine.store %cst, %0[%arg2] : memref<10xf32>
  affine.store %cst, %1[%arg2] : memref<10xf32>
}
```

由于计算切片是单点迭代循环，因此，`fuseLoops()` 函数调用 `promoteIfSingleIteration()` 函数将计算切片的循环体内部操作提升到外层循环（即目的循环），并去除计算切片循环结构，展开后的目的循环为：

```mlir
affine.for %arg2_dst = 0 to 10 {
  affine.store %cst, %0[%arg2_dst] : memref<10xf32>
  affine.store %cst, %1[%arg2_dst] : memref<10xf32>
  %2 = affine.load %1[%arg2_dst] : memref<10xf32>
  %3 = arith.mulf %2, %2 : f32
  affine.store %3, %arg1[%arg2_dst] : memref<10xf32>
}
```

`fuseLoops()` 函数完成循环融合后，`performFusionsIntoDest()` 函数还要继续对上述融合循环中的 memref `%1` 调用 `createPrivateMemRef()` 函数，执行 memref 私有化过程。

`createPrivateMemRef()` 函数通过源点操作（`srcStoreOpInst`）的 `MemRefRegion` 实例可以知道源点操作在所选深度的访问区域实际大小，并以此重新构造 memref 类型和 `memref.alloc` 操作，为相关访问替换存储并重映射下标。

测试用例中的源点操作 `affine.store %cst, %1[%arg2]` 在每个计算切片中只访问一个位置 `%1[%arg2_dst]`。因此，由该操作的 `MemRefRegion` 实例约束系统可知，该切片访问区域实际大小为 1，由此重新构造的 memref 类型为 `memref<1xf32>`，重新构造的 `memref.alloc` 操作为 `%alloc = memref.alloc() : memref<1xf32>`。该原始位置在私有缓冲区中重映射为 `%alloc[0]`。

> 校订注：原书说切片访问的原位置就是 `%1[0]`，不准确；原位置随目的循环变量变化，只是每次切片宽度为 1。下标 0 是减去区域偏移后在新私有缓冲区中的位置。

源循环与目的循环融合结果如下：

```mlir

    affine.store %cst, %alloc_0[%arg2] : memref<10xf32>
    affine.store %cst, %alloc[0] : memref<1xf32>
    %0 = affine.load %alloc[0] : memref<1xf32>

  affine.for %arg2 = 0 to 10 {
    %0 = affine.load %alloc_0[%arg2] : memref<10xf32>

  }
```


#### 3. 执行兄弟融合

兄弟融合的目标是融合从共享 memref 中加载数据、但没有实际数据依赖关系的两个循环嵌套。生产者—消费者融合中，一个循环写入共享 memref，另一个循环读取该 memref；兄弟融合中，两个循环都读取共享 memref，利用的是读后读（RAR）关系。

融合后，同一共享 memref 中的数据可以在距离更近的计算中被使用，有利于提高数据局部性、减少数据在存储层次间的重复传输。在适用的生产者—消费者场景中，融合还可能配合缓冲区私有化，缩小中间存储乃至删除原来的中间缓冲区，从而降低内存占用。

> 校订注：原书将“融合后访问较小的局部缓冲区、原共享缓冲区通常被移除或压缩”作为兄弟融合的一般效果。这并不成立；下面的兄弟融合例子仍读取输入 `%arg0`，不创建其私有小缓冲区，也不删除它。兄弟融合首先改善访问的时间局部性，不能与中间缓冲区压缩混为一谈。

<!-- 原书第 216 页；PDF 第 60 页。 -->

本部分使用如下测试用例 `sibling_fusion.mlir` 辅助分析 `AffineLoopFusion` pass 的兄弟融合执行过程：

```mlir
func.func @sibling_fusion(%arg0: memref<10x10xf32>, %arg1: memref<10x10xf32>,
                         %arg2: memref<10x10xf32>, %arg3: memref<10x10xf32>,
                         %arg4: memref<10x10xf32>) {
  affine.for %arg5 = 0 to 3 {
    affine.for %arg6 = 0 to 3 {
      %0 = affine.load %arg0[%arg5, %arg6] : memref<10x10xf32>
      %1 = affine.load %arg1[%arg5, %arg6] : memref<10x10xf32>
      %2 = arith.mulf %0, %1 : f32
      affine.store %2, %arg3[%arg5, %arg6] : memref<10x10xf32>
    }
  }
  affine.for %arg5 = 0 to 3 {
    affine.for %arg6 = 0 to 3 {
      %0 = affine.load %arg0[%arg5, %arg6] : memref<10x10xf32>
      %1 = affine.load %arg2[%arg5, %arg6] : memref<10x10xf32>
      %2 = arith.addf %0, %1 : f32
      affine.store %2, %arg4[%arg5, %arg6] : memref<10x10xf32>
    }
  }
  return
}
```

以上测试用例中有两个循环嵌套。其中，第一个循环嵌套执行 `arg0` 元素与 `arg1` 元素的乘法（下文将第一个循环嵌套也称为乘法循环），并将结果保存在 `arg3` 中。第二个循环嵌套执行 `arg0` 元素与 `arg2` 元素的加法（下文将第二个循环嵌套也称为加法循环），并将结果保存在 `arg4` 中。这两个循环都从 `arg0` 读取数据；在它们互不写入另一循环使用的内存位置的前提下，无需维持循环间的真实数据依赖。如果在两个循环中间插入其他计算，在第二个循环开始时，第一个循环从 `arg0` 加载的缓存行可能已经被替换，从而导致缓存未命中。因此，从缓存局部性的角度看，兄弟融合是解决此类问题的优化选择之一。

> 校订注：不同的 memref 参数名本身不能证明底层存储不重叠。这里沿用原书的独立缓冲区使用前提；如果参数之间存在影响读写结果的别名，必须另行检查依赖，不能仅凭 `%arg0`、`%arg3` 等名字不同便断言融合合法。

如前所述，如果需要使用特定的优化模式（仅生产者—消费者融合模式或仅兄弟融合模式），可以单独调用对应的函数。当 `createLoopFusionPass()` 函数参数 `affineFusionMode` 为 `FusionMode::Sibling` 时，`runSiblingFusionOnly()` 函数和 `fuseSiblingNodes()` 函数被调用，完成兄弟融合场景下的优化。上一小节已经介绍生产者—消费者融合模式实现方法，本小节将介绍兄弟融合模式实现方法。

`fuseSiblingNodes()` 函数代码实现如下：

<!-- 原书第 217 页；PDF 第 61 页。 -->

```cpp
void fuseSiblingNodes() {
  init();
  while (!worklist.empty()) {
    unsigned dstId = worklist.back();
    worklist.pop_back();
    if (mdg->nodes.count(dstId) == 0)
      continue;
    auto *dstNode = mdg->getNode(dstId);
    if (!isa<AffineForOp>(dstNode->op))
      continue;
    fuseWithSiblingNodes(dstNode);
  }
}
```

与生产者—消费者融合模式实现代码类似，`fuseSiblingNodes()` 函数代码逻辑分为初始化工作列表（`worklist`）和执行兄弟循环节点融合两个部分。初始化工作列表实现函数 `GreedyFusion::init()` 在前文介绍生产者—消费者融合执行过程时已经说明，其作用是将内存依赖图中的所有节点 id 添加到工作列表中；后续从工作列表取出目的节点 id（`dstId`），取得相应节点并调用 `fuseWithSiblingNodes(dstNode)`，尝试将其他符合条件的兄弟循环嵌套融合到该目的循环嵌套中。

上述代码中的 `fuseWithSiblingNodes()` 函数是完成兄弟融合的核心函数。该函数在输入 IR 中不断尝试查找与目的循环加载同一共享 memref 的可融合兄弟循环节点。如果满足数据依赖和收益要求，则将目的循环嵌套与兄弟循环嵌套融合。`fuseWithSiblingNodes()` 函数调用流程图如图 5-19 所示。

```text

└── fuseWithSiblingNodes()

    ├── isFusionProfitable()               计算循环融合收益

```

##### （1）获取候选兄弟循环节点

融合的目的循环节点由 `fuseWithSiblingNodes()` 函数参数 `dstNode` 确定，与目的循环节点加载同一共享 memref 的可融合候选兄弟循环节点由 `findSiblingNodeToFuse()` 函数获得。在测试用例 `sibling_fusion.mlir` 中，目的循环节点为加法循环，候选兄弟循环节点为乘法循环。

<!-- 原书第 218 页；PDF 第 62 页。上段跨页。 -->

##### （2）计算融合循环插入点

在确定候选兄弟循环嵌套和目的循环嵌套后，`fuseWithSiblingNodes()` 函数调用 `getFusedLoopNestInsertionPoint()` 接口，计算将兄弟循环嵌套与目的循环嵌套融合后循环嵌套的插入位置。测试用例中的乘法循环（兄弟循环节点）在前，加法循环（目的循环节点）在后，两者相邻且没有其他操作形成插入位置限制，因此函数确定的融合循环嵌套插入点位于加法循环处。

> 校订注：原书将插入位置一概描述为两个循环中较后出现的循环处。一般情况下还必须考虑中间操作的输入、输出依赖，合法插入点并不总在较后循环处，也可能不存在；本例的结论不能推广到所有输入。

由于目的循环可能包含多层嵌套，在循环融合前还应计算目的循环嵌套深度。出于最大化数据重用和缓存局部性等因素的考虑，可以优先考察较深的融合位置；最终选择还取决于合法性检查及收益估算，不能无条件选择最深层。

##### （3）判断循环融合可行性

与生产者—消费者融合类似，在真正进行兄弟融合之前，`fuseWithSiblingNodes()` 函数还应调用 `canFuseLoops()` 函数，从最外层循环开始判断将兄弟循环融合进目的循环的可行性，直到找到最大合法融合深度（`maxLegalFusionDepth`）。对于兄弟融合模式，从兄弟循环嵌套中选择加载兄弟融合目标 memref 的 `affine.load` 操作，从目的循环嵌套中收集所有 `affine.load` 和 `affine.store` 操作，分别作为源端、目的端的操作集合参与分析。

> 校订注：按本地实现，源循环收集的 `opsA` 还会经过融合策略筛选，实际参与切片分析的是策略提供的 `strategyOpsA`。原书把收集集合和筛选后的集合都称为 `opsA`，这里区分其作用。

在兄弟融合模式中，用于构造重用切片的操作对是分别来自两端、读取共享 memref 的 `affine.load` 操作。在测试用例 `sibling_fusion.mlir` 中，目的循环嵌套和兄弟循环嵌套中均有 `affine.load %arg0` 操作，可将其组成待分析的 `affine.load` 操作对。

兄弟融合同样需要通过构造计算切片判定兄弟循环嵌套与目的循环嵌套融合的可行性，包括构造 `affine.load` 操作对的依赖约束系统、获得切片状态信息和切片有效性判断三部分功能。

目的循环嵌套和兄弟循环嵌套中的 `affine.load` 操作的访问关系完全相同，经过访问关系求逆、合成，并结合迭代域及所考察深度的顺序条件，得到的约束系统（`dependenceConstraints`）为：

```text
(-1) * %arg5 + ( 0) * %arg6 + ( 1) * %arg5' + ( 0) * %arg6' + 0 = 0
( 0) * %arg5 + (-1) * %arg6 + ( 0) * %arg5' + ( 1) * %arg6' + 0 = 0
( 1) * %arg5 + ( 0) * %arg6 + ( 0) * %arg5' + ( 0) * %arg6' + 0 >= 0
(-1) * %arg5 + ( 0) * %arg6 + ( 0) * %arg5' + ( 0) * %arg6' + 2 >= 0
( 0) * %arg5 + ( 1) * %arg6 + ( 0) * %arg5' + ( 0) * %arg6' + 0 >= 0
( 0) * %arg5 + (-1) * %arg6 + ( 0) * %arg5' + ( 0) * %arg6' + 2 >= 0
( 0) * %arg5 + ( 0) * %arg6 + ( 1) * %arg5' + ( 0) * %arg6' + 0 >= 0
( 0) * %arg5 + ( 0) * %arg6 + (-1) * %arg5' + ( 0) * %arg6' + 2 >= 0
( 0) * %arg5 + ( 0) * %arg6 + ( 0) * %arg5' + ( 1) * %arg6' + 0 >= 0
( 0) * %arg5 + ( 0) * %arg6 + ( 0) * %arg5' + (-1) * %arg6' + 2 >= 0
```

为了区分，此处以 `%arg5`、`%arg6` 表示兄弟循环嵌套的循环索引变量，以 `%arg5'`、`%arg6'` 表示目的循环嵌套的循环索引变量。上述约束系统中的第一和第二项等式 `%arg5 = %arg5'`、`%arg6 = %arg6'`，分别表示两个 `affine.load` 操作读取相同内存地址的数据。

<!-- 原书第 219 页；PDF 第 63 页。上段跨页。 -->

由上述约束系统可以看到，目的循环嵌套和兄弟循环嵌套的内存访问范围相同，因此可以确定存在 RAR 关系。兄弟融合的重用分析允许将两个 `affine.load` 操作间的 RAR 关系作为待分析关系，因此 `checkMemrefAccessDependence()` 在允许 RAR 的这次分析中返回 `HasDependence`。这不表示读—读之间产生了必须维持的写入先后依赖。

在获得 `affine.load` 操作对的约束系统后，可根据该系统调用 `getComputationSliceState()` 函数，获得切片状态信息。对应切片状态信息的计算切片与目的循环融合后的结果为：

```mlir
affine.for %arg5_dst = 0 to 3 {
  affine.for %arg6_dst = 0 to 3 {
    affine.for %arg5 = affine_map<(d0, d1) -> (d0)>(%arg5_dst, %arg6_dst)
        to affine_map<(d0, d1) -> (d0 + 1)>(%arg5_dst, %arg6_dst) {
      affine.for %arg6 = affine_map<(d0, d1) -> (d1)>(%arg5_dst, %arg6_dst)
          to affine_map<(d0, d1) -> (d1 + 1)>(%arg5_dst, %arg6_dst) {
        %0 = affine.load %arg0[%arg5, %arg6] : memref<10x10xf32>
        %1 = affine.load %arg1[%arg5, %arg6] : memref<10x10xf32>
        %2 = arith.mulf %0, %1 : f32
        affine.store %2, %arg3[%arg5, %arg6] : memref<10x10xf32>
      }
    }
    %3 = affine.load %arg0[%arg5_dst, %arg6_dst] : memref<10x10xf32>
    %4 = affine.load %arg2[%arg5_dst, %arg6_dst] : memref<10x10xf32>
    %5 = arith.addf %3, %4 : f32
    affine.store %5, %arg4[%arg5_dst, %arg6_dst] : memref<10x10xf32>
  }
}
```

> 转写说明：原书在代码中以带撇号的 `%arg5'`、`%arg6'` 区分目的循环变量。为使用合法的 SSA 名称，代码统一写成 `%arg5_dst`、`%arg6_dst`；上面的数学约束仍保留撇号记法。

上述计算切片对应的切片状态对象中各集合为：

```text
ivs = {%arg5, %arg6}
lbs = {(d0, d1) -> (d0), (d0, d1) -> (d1)}
ubs = {(d0, d1) -> (d0 + 1), (d0, d1) -> (d1 + 1)}
lbOperands = {{%arg5_dst, %arg6_dst}, {%arg5_dst, %arg6_dst}}
ubOperands = {{%arg5_dst, %arg6_dst}, {%arg5_dst, %arg6_dst}}
```

> 校订注：`lbOperands` 和 `ubOperands` 按源循环逐个保存操作数列表；原文用一组变量表示整个集合，遗漏了这一层结构。此处的每个二维 AffineMap 都需要两个操作数，即使其中一个维度没有出现在结果表达式中。

与前述生产者—消费者融合模式判断计算切片有效性的过程类似，本例每次目的迭代对应一个源迭代点，且源、目的循环的两个索引都遍历 `[0, 2]`。因此，这些切片没有超出源迭代域，并且所有目的迭代上的切片合起来完整覆盖源迭代域：切片有效，同时为最大切片。结合其他合法性检查，`canFuseLoops()` 可以判定本例融合可行。

> 校订注：有效性和最大性分别由 `isSliceValid()`、`isMaximal()` 等逻辑判断，不应把二者混称为 `isSliceValid()` 的同一个结论；仅有上下界相同，也不能脱离访问映射证明任意切片最大。

##### （4）计算循环融合收益

`isFusionProfitable()` 函数通过计算成本与内存占用量两个维度，对兄弟循环嵌套与目标循环嵌套的融合收益进行综合评估，为融合提供启发式判断。这不是对实际性能提升的保证。

从计算成本角度评估收益，由测试用例 `sibling_fusion.mlir` 可知，在兄弟融合前，兄弟循环嵌套和目的循环嵌套的循环迭代总数均为 9，最内层有效操作数量均为 4。根据“计算成本 = 操作数量 × 循环迭代总数”的计算方法，兄弟循环嵌套和目的循环嵌套的计算成本都为 36（= 4 × 9），因此融合前的计算总成本为 72（= 36 + 36）。

<!-- 原书第 220 页；PDF 第 64 页。上段跨页。 -->

兄弟融合后的目的循环计算成本由切片计算成本和融合前的目的循环计算成本构成。融合后目的循环体中包含的操作，除了融合前原有的 4 个操作外，还包括切片循环体中的 4 个操作。因此，兄弟融合后的目的循环计算成本（`fusedLoopNestComputeCost`）为 72（= 8 × 9），相比融合前的计算成本 72 没有增加；融合后增加的冗余计算比例为 0，小于可容忍冗余计算成本默认阈值 30%，因此通过这项收益检查。

从内存开销角度评估收益，关注兄弟循环嵌套和目的循环嵌套中所有内存读写操作的访问区域。兄弟融合前，两个循环嵌套中均包括 2 个 `affine.load` 和 1 个 `affine.store` 操作，其 memref 操作数类型均为 `memref<10x10xf32>`，访问索引 `%arg5`、`%arg6`、`%arg5_dst`、`%arg6_dst` 的范围均为 `[0, 2]`。因此，融合前两个循环嵌套的访问区域内存占用估算（`srcMemSizeVal` 和 `dstMemSizeVal`）均为 108（= 4 × 3 × 9）字节。

兄弟融合后的目的循环内存占用估算（`fusedMem`）等于融合前目的循环内存占用量与切片写区域内存占用量之和。源循环的 `affine.store %2, %arg3[%arg5, %arg6]` 操作类型为 `memref<10x10xf32>`，全部目的迭代覆盖的切片写索引范围在两维上均为 `[0, 2]`，其写区域大小为 36（= 4 × 9）字节。因此，估算融合后的内存占用量为 144（= 108 + 36）字节。由于 `fusedMem (144) < srcMemSizeVal (108) + dstMemSizeVal (108)`，因此该模型认为兄弟融合有收益，可以融合。

> 校订注：原书由共享输入 `affine.load %arg0` 的读取区域得到 36；本地源码实际以源循环的 store 操作计算切片写区域，并在兄弟重用融合时检查其大小与原写区域相同。本例读、写区域恰好都为 3×3，数值未变，但来源不同。`loopDepth = 0` 的区域分析会消去目的循环变量，因此这里不是单次迭代的 4 字节。144 是源码启发式公式的结果，不是最终代码实际涉及的所有不同缓冲区区域之和，也不代表 `%arg0` 被压缩。

##### （5）执行循环融合

`fuseWithSiblingNodes()` 如果检测到测试用例中的两个循环嵌套是可融合的兄弟关系，且 `isFusionProfitable()` 函数判定融合有收益，则通过调用 `fuseLoops()` 函数执行兄弟融合，将兄弟循环嵌套和目的循环嵌套融合在一起。

融合过程首先根据 `fuseLoops()` 函数参数 `srcSlice` 提供的切片状态信息，将兄弟循环嵌套转换为计算切片。如前文介绍生产者—消费者融合执行过程所述，根据 `srcSlice` 中的源循环索引变量（`ivs`）可以找到该索引变量所属的兄弟循环嵌套；复制源循环后，根据 `srcSlice` 提供的循环上下界 AffineMap 和关联操作数重新设置副本的上下界，将其转换为计算切片。测试用例中的兄弟循环嵌套为：

```mlir
affine.for %arg5 = 0 to 3 {
  affine.for %arg6 = 0 to 3 {
    %0 = affine.load %arg0[%arg5, %arg6] : memref<10x10xf32>
    %1 = affine.load %arg1[%arg5, %arg6] : memref<10x10xf32>
    %2 = arith.mulf %0, %1 : f32
    affine.store %2, %arg3[%arg5, %arg6] : memref<10x10xf32>
  }
}
```

<!-- 原书第 221 页；PDF 第 65 页。 -->

`srcSlice` 切片状态对象中提供的 `ivs` 集合为 `{%arg5, %arg6}`，兄弟循环嵌套外层循环的下界 AffineMap 和上界 AffineMap 分别为 `(d0, d1) -> (d0)` 和 `(d0, d1) -> (d0 + 1)`，两者关联操作数都是 `(%arg5_dst, %arg6_dst)`。消去未使用的第二个输入维度后，可以等价地使用一维映射 `(d0) -> (d0)`、`(d0) -> (d0 + 1)`，操作数为 `%arg5_dst`。根据循环下界 AffineMap 和下界操作数重新设置外层循环下界后的结果为：

```mlir
affine.for %arg5 = affine_map<(d0) -> (d0)>(%arg5_dst) to 3 {
  affine.for %arg6 = 0 to 3 {
    %0 = affine.load %arg0[%arg5, %arg6] : memref<10x10xf32>
    %1 = affine.load %arg1[%arg5, %arg6] : memref<10x10xf32>

    affine.store %2, %arg3[%arg5, %arg6] : memref<10x10xf32>

```

根据上述循环上界 AffineMap 和上界操作数重新设置兄弟循环嵌套外层循环上界后的结果为：

```mlir
affine.for %arg5 = affine_map<(d0) -> (d0)>(%arg5_dst)
    to affine_map<(d0) -> (d0 + 1)>(%arg5_dst) {
  affine.for %arg6 = 0 to 3 {
    %0 = affine.load %arg0[%arg5, %arg6] : memref<10x10xf32>
    %1 = affine.load %arg1[%arg5, %arg6] : memref<10x10xf32>
    %2 = arith.mulf %0, %1 : f32
    affine.store %2, %arg3[%arg5, %arg6] : memref<10x10xf32>
  }
}
```

> 校订注：原文这里误写“重新设置……下界”，实际设置的是上界。原文正文还将二维映射与一个操作数搭配，已补明去除无用维度后才可使用上述一维写法。

`srcSlice` 提供的兄弟循环嵌套内层循环的下界 AffineMap 和上界 AffineMap 分别为 `(d0, d1) -> (d1)` 和 `(d0, d1) -> (d1 + 1)`，关联操作数同样是 `(%arg5_dst, %arg6_dst)`。消去未使用的第一个维度后，可等价使用 `(d0) -> (d0)` 和 `(d0) -> (d0 + 1)`，操作数为 `%arg6_dst`。根据循环上下界 AffineMap 和操作数重新设置内层循环上下界后，得到的计算切片为：

```mlir
affine.for %arg5 = affine_map<(d0) -> (d0)>(%arg5_dst)
    to affine_map<(d0) -> (d0 + 1)>(%arg5_dst) {
  affine.for %arg6 = affine_map<(d0) -> (d0)>(%arg6_dst)
      to affine_map<(d0) -> (d0 + 1)>(%arg6_dst) {
    %0 = affine.load %arg0[%arg5, %arg6] : memref<10x10xf32>
    %1 = affine.load %arg1[%arg5, %arg6] : memref<10x10xf32>
    %2 = arith.mulf %0, %1 : f32
    affine.store %2, %arg3[%arg5, %arg6] : memref<10x10xf32>
  }
}
```

将上述计算切片的单次迭代循环体操作提升到目的循环嵌套中，以目的循环索引替换相应源循环索引，并去除切片的单次迭代循环结构后，得到最终的兄弟融合结果为：

<!-- 原书第 222 页；PDF 第 66 页。上段跨页。 -->

```mlir
func.func @sibling_fusion(%arg0: memref<10x10xf32>, %arg1: memref<10x10xf32>,
                         %arg2: memref<10x10xf32>, %arg3: memref<10x10xf32>,
                         %arg4: memref<10x10xf32>) {
  affine.for %arg5 = 0 to 3 {
    affine.for %arg6 = 0 to 3 {
      %0 = affine.load %arg0[%arg5, %arg6] : memref<10x10xf32>
      %1 = affine.load %arg1[%arg5, %arg6] : memref<10x10xf32>
      %2 = arith.mulf %0, %1 : f32
      affine.store %2, %arg3[%arg5, %arg6] : memref<10x10xf32>
      %3 = affine.load %arg0[%arg5, %arg6] : memref<10x10xf32>
      %4 = affine.load %arg2[%arg5, %arg6] : memref<10x10xf32>
      %5 = arith.addf %3, %4 : f32
      affine.store %5, %arg4[%arg5, %arg6] : memref<10x10xf32>
    }
  }
  return
}
```

上述兄弟融合后的数据依赖图已经发生变化，因此还应调用 `updateStateAfterSiblingFusion()` 函数，更新兄弟循环嵌套与目的循环嵌套的依赖边，以反映二者融合后的状态，并删除已经无效的旧兄弟循环嵌套。

兄弟融合后的所有操作都在目的循环嵌套中，相同索引的内存位置在时间上更接近地被访问。如果工作集及缓存条件适合，缓存命中率可能更高，代码性能可能有一定提升。然而，循环融合的某些切片方案可能以冗余计算为代价；上述例子本身没有增加计算次数，但仍保留了两次 `affine.load %arg0`。如果进一步优化，可以考虑在确认中间写操作不会修改该加载位置后，将其加载结果保存在一个 SSA 值中，由乘法和加法操作共用。

> 校订注：原书以本例的两次 load 说明“兄弟融合带来冗余计算”，但融合前已经有这两次 load，不能算融合新增的成本。消除第二次 load 还必须检查两次读取之间的 `%arg3` 写入是否可能通过别名改变 `%arg0` 的对应内容。
