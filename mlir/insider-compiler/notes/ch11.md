# 第 11 章精华：目标表示、ABI 与硬件执行语义

[校订正文](../insider-compiler-ch11.md) · [读前导读](../guide/ch11.md) · [笔记目录](README.md)

本章实现以 LLVM 18.1.8 为准。复习时沿着“数据表示—函数边界—硬件执行—最终输出”追踪同一个值，比记住操作目录更有效。

## 1. llvm 方言与 LLVM IR 的边界（11.1）

| 阶段 | 仍然保留什么 | 主要机制 |
| --- | --- | --- |
| 高层方言转 llvm 等方言 | MLIR 的 Operation、Region、Block 与类型系统 | `LLVMTypeConverter`、`ConvertOpToLLVMPattern`、方言转换 |
| MLIR 导出 LLVM IR | 转成 LLVM 的 Module、Function、Instruction 等对象 | `LLVMTranslationDialectInterface`，按操作与属性翻译 |
| LLVM IR 生成目标代码 | 目标指令选择、寄存器分配等后端工作 | LLVM 目标后端及工具链 |

llvm 方言仍是 MLIR；不能把它的文本交给只接受 LLVM IR 的工具。反过来，也不是所有可导出的操作都必须先改名为 `llvm.*`：NVVM 等方言可以通过相应翻译接口导出 intrinsic，部分专用操作也会先降为内联汇编。

非入口块参数通常对应 LLVM 的 phi，入口块参数对应函数参数。`llvm.mlir.constant` 可以导出为 LLVM 常量，并不一定生成运行时指令。全局对象、函数、属性同样需要对应处理，不能只统计普通指令是否全部转换。

`builtin.unrealized_conversion_cast` 是转换过程中的类型衔接占位。清理 pass 可以消去适用的冗余衔接，但不会凭空实现缺少的转换；模块残留不支持的 SCF、类型或操作时，仍可能无法导出。

## 2. memref 降级首先是 ABI 问题（11.1.1、11.1.4）

普通 ranked strided memref 描述符可概括为：

```text
{ allocatedPtr, alignedPtr, offset, sizes[rank], strides[rank] }
```

分配指针用于需要时释放存储，访问指针满足所需对齐；二者可以相同，也可以不同。offset 与 stride 以元素为单位，尺寸描述逻辑边界。rank 为零时省去两个数组；静态尺寸与动态尺寸不改变既定 rank 的字段数量。无 rank 的 memref 使用“rank＋指向具体描述符的指针”。

对合法下标 $i_0,\ldots,i_{r-1}$，先计算元素偏移：

$$e=\mathrm{offset}+\sum_{k=0}^{r-1}i_k\,\mathrm{stride}_k.$$

地址从 `alignedPtr` 出发移动 $e$ 个元素；按字节理解时再乘元素存储大小。这个公式解释了切片、转置视图为何能共享底层存储，也说明只传数据指针会丢失哪些信息。地址能算出来不证明下标在界内。

默认函数参数 ABI 会将 ranked memref 描述符展开为参数字段，不能把局部的结构体表示直接等同于“总是按一个结构体传参”。多返回值可打包为结构体；裸指针 ABI 有额外限制。`index` 的低层位宽取决于数据布局和转换选项，并非无条件等于 64。多维向量通常用嵌套数组包裹最内层一维向量，不能当作 LLVM 原生多维 vector。

## 3. GPU 坐标、内存、同步（11.2.3～11.2.4）

一维线程覆盖中常用 $g=bB+t$，其中 $b$ 为 block 编号，$B$ 为 block 大小，$t$ 为块内线程编号。多维坐标逐维计算；需要扁平地址时再按形状与步长展开。tile 程序还应先计算 `block_id * tile_size`，避免把块编号误当作元素偏移。

| 层级或资源 | 核心含义 | 易混点 |
| --- | --- | --- |
| thread / warp / block | 线程及协作执行层次 | NVIDIA warp 为 32 线程；四个 warp 的 warp-group 不等于 cluster |
| private、寄存器、local 存储 | 线程私有状态及其实现位置 | CUDA 意义的 local memory 可能在设备内存中，常与溢出有关 |
| workgroup shared memory | 同一工作组协作存储 | 可编程共享存储与 L1 缓存不是同一语义对象 |
| global memory | 设备全局存储 | 连续地址有利于合并访问，但不保证任意规模仅需一次事务 |
| barrier / 异步等待 | 参与者或异步工作之间的顺序 | 工作组屏障不能自动同步整个 grid；等待某些组不等于等待所有历史操作 |

`gpu.launch` outlining 将设备区域提取为 `gpu.module` 中的 `gpu.func`，主机侧使用 `gpu.launch_func`。后续还要完成设备目标编译、主机运行时调用及二进制装载；`gpu.binary` 保存编译产物，不是二元算术操作。异步拷贝在读取前要满足完成条件，释放共享缓冲前也要等到其最后使用结束。

## 4. 专用方言保留何种信息（11.2.2、11.2.5～11.2.6）

| 方言 | 关注的硬件结构 | 阅读边界 |
| --- | --- | --- |
| `arm_sme` | Streaming SVE、ZA tile、切片及外积 | 虚拟 tile 与物理资源分配不同；`get_tile` 不保证清零 |
| `gpu` | 启动、坐标、通用并行与存储结构 | 后端无关表达不代表各硬件能力相同 |
| `nvgpu` | NVIDIA Tensor Core、异步拷贝、TMA 等专用结构 | 保留比最终 intrinsic 更高层的描述信息 |
| `nvvm` | 更接近 NVIDIA LLVM intrinsic 与 PTX 的语义 | 操作可用性与目标架构、版本和翻译支持共同相关 |

SME 的流模式向量长度 SVL 不应与普通 SVE 长度混为一谈；ZA 字节容量为 $(\mathrm{SVL}_{bits}/8)^2$。一次外积更新 tile 不等于完成任意尺寸 GEMM，谓词的清零或合并行为要按具体指令判断。

Tensor Core 操作数常按线程片段分布，WGMMA 又有 warp-group 参与条件。类型和布局选择约束指令合法性，但高层片段表示不是最终物理寄存器分配结果。某个名字出现在较新资料中，也不证明 LLVM 18 或较早 GPU 支持它。

## 5. 用访问模型验证 swizzle（11.2.5）

本章本地例子保持 `128×128` 的共享分配形状，同时将读写列下标改为：

```text
newCol = col XOR ((row AND 31) << 2)
```

最低两位不变，适合所用的对齐 128-bit 访问模型。固定列、32 个线程各读一个标量时只分散到 8 个 bank；在核验的 8 个对齐向量访问模型中，32 个组成字可覆盖 32 个 bank。因此评价布局优化要明确访问宽度、线程组合与地址集合，不能只看 XOR 就宣布无冲突。

复习检查：能够写出一次 memref 访问的地址，指出一次转换或翻译的边界，并为每条屏障说清参与者和等待对象。第 13 章的布局与流水线，正是在这些约束下继续选择性能方案。解析、导出成功也应与真实 GPU 执行验证分开，详见[原章核验记录](../issues/ch11.md)。
