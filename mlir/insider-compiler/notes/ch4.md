# 第4章精华笔记：条件、契约与能力分派

[原章](../insider-compiler-ch4.md) · [配套读前导读](../guide/ch4.md) · [笔记目录](README.md)

以本地 LLVM18.1.8 校订正文为依据。三类机制的价值在于让方言提供足够的语义信息，供验证器与通用算法正确处理。

## 1. 谓词、特质、接口如何分工（4.1～4.3）

| 机制 | 核心作用 | 典型使用方式 |
| --- | --- | --- |
| Predicate | 表达一个条件 | `CPred`、`And`、`Or` 等生成布尔检查 |
| Constraint | 包装谓词及说明 | 类型、属性等约束参与生成验证与诊断 |
| Trait | 附加共同性质、约束或实现 | 模板继承、标记查询、验证钩子 |
| Interface | 通过共同 API 查询不同实体的能力 | 接口包装、模型注册与动态分派 |

`Constraint` 包含谓词，不继承 `Pred`。谓词生成的检查在编译器运行时验证 IR，不是 C++ 编译期求值，也不是目标程序的动态安全检查。接口又可以通过特质附加，因此“特质”和“接口”不是互斥标签。

## 2. 从 TD 条件读到 verifier（4.1.1）

`CPred` 中的 `$_self` 等占位符，在生成器选定的上下文里替换为被检查的类型、属性或对象。例如约束 `lhs:F16`、`rhs:F32`、`result:F64` 时，需要三个分别对应位置的检查，不能合成一个“F16或F32”检查去代替。

组合器也有不同用途：`And`/`Or`/`Neg`组合逻辑，`Concat`为一个子表达式拼接前后字符串，`SubstLeaves`替换谓词叶节点的字符串内容。编写涉及 `cast` 的谓词时，必须保证前置类型条件成立；例如检查整数数组的第N项，不能漏掉数组及元素类型约束。

普通 `Operation::create` 或 `OpBuilder::create` 不无条件运行完整 verifier。显式 `mlir::verify`、解析后的验证及 Pass 管线验证，才负责在对应时机检查不变量。`hasVerifier=1` 生成的是自定义验证声明，语义检查仍需实现；通过 verifier 也不能独立证明一次优化保持了原程序结果。

## 3. 特质声明的是算法能够依赖的契约（4.2）

原生特质需要 C++ 定义，即使它只是空的标记类。参数化原生特质通过 `ParamNativeOpTrait` 等对应到带参数模板；`GenInternalTrait` 由生成器解释，不要求一个同名 C++ 特质类。`PredOpTrait` 则把操作层的谓词接入验证。

`verifyTrait`、`verifyRegionTrait`、`foldTrait` 是按需要提供的钩子，不要求每个特质全部实现。操作也没有必须定义 `verifyTraitImpl()` 的统一规定。

| 契约 | 可以据此理解 | 不能据此推断 |
| --- | --- | --- |
| `IsolatedFromAbove` | 区域不隐式捕获边界外 SSA 值 | 禁止显式传参或符号引用 |
| `NoMemoryEffect` | 操作自身没有内存效果 | 任意多执行一次都安全 |
| `ConditionallySpeculatable` | 查询额外执行是否安全 | `NotSpeculatable` 表示原程序必然出错 |
| `Pure` | 无内存效果且可推测执行 | 不顾 SSA 依赖就任意移动 |
| `AttrSizedOperandSegments` | 保存各 ODS 操作数组的长度 | 数组只记录变长组 |
| `SingleBlock` | 每个非空区域一个块 | 区域必须非空 |
| `NoTerminator` | 对应单块区域可省略终结操作 | 禁止终结操作存在 |

例如整数除法可以没有内存效果，但将它提升到原先不会执行的路径上，可能引入除零或溢出问题。内存效果、可推测性与值可用性需要分别检查。`ConstantLike` 也不只是一个任意常量标签：它要求无操作数、单结果并能折叠为属性。

## 4. 接口调用究竟转发给谁（4.3.1～4.3.2）

方言接口以方言为单位注册具体实现，例如 `DialectInlinerInterface` 提供内联合法性和终结操作处理。它使用 C++ 虚函数等机制；不能概括成“MLIR 不允许虚函数”。

操作接口的包装对象引用原 `Operation`，另持有非拥有的 `Concept*`。`Concept` 保存分派函数指针，调用接口方法时同时传入模型和操作。模型通常由注册元数据的 `InterfaceMap` 管理，不由每个操作实例各持一份映射。

| 模型 | 主要转发目标 | 适用认识 |
| --- | --- | --- |
| `Model<ConcreteOp>` | 具体操作的方法，或接口指定的模型方法体 | 直接在操作定义上附加接口 |
| `FallbackModel<ConcreteModel>` | 独立模型对象的方法 | 把实现与操作类分开，不要求动态方言 |
| `ExternalModel<ConcreteModel, ConcreteOp>` | 面向指定操作的外部实现 | 给操作补充尚未提供的接口能力 |

这些类提供分派框架，不会自动计算卷积成本等业务结果。`dyn_cast<Interface>(op)` 查询已注册模型并构造轻量包装；不会新建底层操作，也不会因为转换成功而自动实现缺失的方法。

## 5. 三种“提供方法”的区别（4.3.2）

| 方式 | 生成位置及效果 |
| --- | --- |
| `methodBody` | 进入 `Model` 的方法实现；该路径不再调用操作同名方法 |
| `defaultImplementation` | 在接口特质及 ExternalModel 中生成默认实现，可按相应机制覆盖 |
| 操作或外部模型自行实现 | 在模型转发所要求的位置提供实际逻辑 |

直接把接口附加为操作特质，仍注册真正的接口模型，但不会自动补全所有操作方法声明。`DeclareOpInterfaceMethods`用于生成所需声明；给它指定方法名列表，可以要求声明某些已有默认实现的方法，以便具体操作覆盖。具有 `methodBody` 的方法不会因此变成操作方法分派。

正文的成本方法没有默认实现，所以清单4-19第二、第三种写法效果相同，不能凭多写了方法列表就推断运行行为变化。

## 6. 注册、外部扩展与算法能力（4.3.2）

在操作注册时，接口特质列表构造 `Model<ConcreteOp>` 并进入该操作种类的元数据。外部模型通常通过 `attachInterface` 附加；本地同一个接口ID重复注册时保留已有实现，不会用后注册模型覆盖。因此 ExternalModel 更适合补充未提供的接口，而非给已有实现热替换。

`declarePromisedInterface` 可记录应在使用前补齐的接口，未兑现时的相关诊断依赖 Debug 检查；承诺本身不等于实现已注册。

阅读后续算法时，可按问题寻找接口：块间分支查 `BranchOpInterface`，父操作与区域间控制流查 `RegionBranchOpInterface`，DPS结果与初始化目标的对应查 `DestinationStyleOpInterface`，整数范围查 `InferIntRangeInterface`。DPS不直接保证可原地复用缓冲区；范围推断遇到溢出也可能保守扩大到完整范围。接口提供算法所需信息，算法仍必须检查适用条件。
