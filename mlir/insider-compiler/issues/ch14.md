## 1. 数学基础与 GCD 测试

范围：PDF 第2–6页，含开篇两条脚注、凸集和凸函数注意框、一般优化问题及凸优化问题。完整独立论证见 [math-foundations-review.md](evidence/ch14/math-foundations-review.md)，可执行数值反例见 [math-counterexamples.py](evidence/ch14/math-counterexamples.py) 和[输出](evidence/ch14/math-counterexamples.json)。

以下均属于内容错误，不能仅当作 OCR 字符修正：

| 原书结论／表述 | 校订及理由 |
| --- | --- |
| GCD 整除时“当且仅当……数组元素存在依赖”；脚注写 `a*i-c*i=d-b`，并用两条直线交点说明 | 应为独立源、目标迭代 `a*i-c*j=d-b`。整除对无界二元整数方程是充要条件，对有界迭代域通常只是必要条件。例 `i=j+1000`、`1≤i,j≤100` 通过 GCD 测试却无解。 |
| “此处的依赖指的是它们访问了同一个数组元素” | 普通阻碍重排的内存依赖还需至少一次写和相应执行顺序，读—读通常不限制并行。 |
| “在凸集中，局部最优解就是全局最优解” | 还需在凸域上最小化凸目标函数。反例：`f(x)=x²(1−x)`、`x∈[−1,2]`，0为严格局部最小，但 `f(2)=−4`。 |
| “凸集内任意一点都能够用凸集内的另外两个点表示出来”；“局部最优解自然也能‘看见’……所有其他点” | 极点和单点集反驳前半句；“看见”不证明最优性。正文给出线段点与凸目标不等式构成的反证。 |
| “凸函数必定存在唯一的最优解” | 常数函数可有多个最优解，线性函数 `f(x)=x` 在实数域上无最小值。严格凸性只保证至多一个最优解，存在性需另外条件。 |
| “其线性组合也仍是凸函数” | 非负加权和保持凸性，任意含负权线性组合不保证。 |
| 将“每一种循环优化抽象为一个凸函数”后，其组合保证优化可叠加 | 仿射变换可组合，但合法调度仍须保持依赖；不能由凸函数闭包性质直接推得程序变换合法。 |
| “操作空间通常为正整数……该空间在数学层面就构成了一个凸集” | 连续多面体 `P` 为凸集，整数迭代域 `P∩Zⁿ` 通常不是实数空间中的凸集。 |
| 建模为凸域和凸函数便“确保问题存在最优解” | 凸性本身不保证最优值取得。正文补充非空紧致可行域和连续目标等充分存在条件。 |
| 脚注“若 f 是非凸非凹函数，则 g 也是非凸非凹函数” | 非凸非凹的 `f(x,y)=x²−y²` 与仿射映射 `t↦(t,0)` 复合得到凸函数 `t²`。凹函数与仿射映射复合保持凹性则正确，已保留。 |
| “最优解记为 p*”，`inf` 是“最小值的极限” | `p*` 是最优值；最优解是达到该值的可行点 `x*`。下确界为最大下界，不一定取得。`p*=+∞` 判不可行须说明可行点目标取有限实数的约定。 |
| “本书仅讨论凸优化问题” | 后文还涉及整数可行性和整数规划，不能全归入连续凸优化。凸优化中的等式约束必须为仿射，不能只要求等式函数是凸函数。 |

多面体定义中的 `x` 按列向量统一为 `(x₁,…,xₙ)ᵀ`，明确 `A∈Rᵐˣⁿ`、`C∈Rᵖˣⁿ`、`b∈Rᵐ`、`d∈Rᵖ`；原文“x表示一组向量”改为“一个列向量”。平移向量 `β` 属于对应向量空间，原印的集合包含符号改为元素关系。等式能由两条不等式代替，不代表可以直接删掉约束。定义中的矩阵、求和、上下标与不等号均目视恢复。

本地 [IntegerRelation.h:37](/opt/llvm-project/mlir/include/mlir/Analysis/Presburger/IntegerRelation.h:37)明确描述整数点和线性约束；[GCD 接口说明](/opt/llvm-project/mlir/include/mlir/Analysis/Presburger/IntegerRelation.h:370)明确它用于排除解。开篇 Graphite、Polly 仅作原书历史背景保留，未为泛泛项目介绍扩大到当前发展状态；年代改为“90年代已形成广泛研究和应用”，避免将全部技术起源断定于该年代。

## 2. 清单14-2／14-3和表14-1～14-3

原书的关键片段如下（按扫描修复 OCR 字符，保留原内容问题）：

```text
%a0 = affine.apply
  (d0, d1) -> (d0 * 2 - d1 * 4 + s1, d1 * 3 - s0)(%i0, %i1)[%M, %N]
store %v0, %m[%a0#0, %a0#1] : memref<4x4xf32>
...
%a1 = affine.apply
  (d0, d1) -> (d0 * 7 + d1 * 9 - s1, d1 * 11 + s0)(%i2, %i3)[%K, %M]
%v1 = load %m[%a1#0, %a1#1] : memref<4x4xf32>
```

问题及正文修复：

1. 本地 [`AffineApplyOp::verify`](/opt/llvm-project/mlir/lib/Dialect/Affine/IR/AffineOps.cpp:545)要求 map 只产生一个结果。将二维访问拆成两个单结果 `affine.apply`，显式使用 `affine_map<(d0,d1)[s0,s1] -> (...)>` 声明符号，补全 `affine.load`／`affine.store` 操作名。多结果 map 作为数学映射本身合法，但不能直接作为本地单结果 `affine.apply` 使用。
2. 原 `memref<4x4xf32>` 与跨度100、50的完整循环访问范围冲突。例如固定 `i1` 时，第一维随 `i0` 至少跨越198，不可能始终落在长度4内。正文改成动态二维 memref，明确由调用方保证有效范围；**动态形状不是自动消除越界风险**。
3. 原注意框称“没有任何关于内存变量 m 的维度信息”，与原静态 `4×4` 类型矛盾；并称指向中间位置时下标约束会变化。正文区分逻辑 memref 下标范围和底层分配 offset，明确该关系分析不等于越界验证。
4. 示例中的 `%v0`、三个符号和 `%m` 是外围值。正文片段保持这一边界，[access.mlir](evidence/ch14/access.mlir)增加完整函数参数并已由本地 parser 和 C++ API 读取，未作为不带调用前提的数值程序执行。可取足够大形状和适当符号保证在界内，但读取值是否初始化是另外的执行前提。
5. 将循环变量统一称为**归纳变量**（induction variable），区别于用于累加的归约状态；原“归约变量”不是此处准确术语。

## 3. 可行性与 Affine 分析的具体支持范围

原文“有解就有依赖、无解就无依赖”是对完整整数模型的数学结论；不能把本地保守分析的 `HasDependence` 等同于已经找到了整数证据。

本地 [`checkMemrefAccessDependence`](/opt/llvm-project/mlir/lib/Dialect/Affine/Analysis/AffineAnalysis.cpp:600)先筛查 memref、访存类型和作用域，再取得访问关系，反转目标关系、与源关系组合，加入先后约束，最后调用 `dstRel.isEmpty()`。[`isEmpty()` 的实现](/opt/llvm-project/mlir/lib/Analysis/Presburger/IntegerRelation.cpp:685)使用变量消元、GCD 和无效约束判断；[完整整数采样接口](/opt/llvm-project/mlir/lib/Analysis/Presburger/IntegerRelation.cpp:815)为 `isIntegerEmpty()`／`findIntegerSample()`，二者不可混同。普通有理单纯形法得到有理可行，也不能直接证明整数可行。

非单位步长的公式 `(iv−lb)−step*q=0` 正确。实际 [`addAffineForOpDomain`](/opt/llvm-project/mlir/lib/Dialect/Affine/Analysis/AffineStructures.cpp:69)对**常数下界**会添加局部商变量、向下取整约束与同余等式；下界非常数时发出调试警告并作保守近似。`AffineAnalysis.cpp` 上方“TODO处理非单位步长”的笼统注释不能覆盖这一已实现分支。正文按实现说明边界。

向下取整公式 `q=floor((i+j)/4) ↔ 4q≤i+j≤4q+3` 正确，已完整恢复，包括 `q∈Z`。这说明该运算可以用整数线性约束表示，不保证任意包含除法的表达式及所有调用路径都能精确求解。

## 4. 并行例子、关系组合及顺序约束

清单14-4来自与本地 [parallelize.mlir:159](/opt/llvm-project/mlir/test/Dialect/Affine/parallelize.mlir:159)一致的结构测试，但原分配的内容没有初始化，不能当成正确的矩阵乘数值程序。原关键部分为：

```mlir
%0 = memref.alloc() : memref<4096x4096xf32>
affine.for %arg3 = 0 to 4096 {
  affine.for %arg4 = 0 to 4096 {
    affine.for %arg5 = 0 to 4096 {
      // 原例直接读新分配的 %0，再将其与乘积相加。
      %3 = affine.load %0[%arg3, %arg4] : memref<4096x4096xf32>
      // 原 %4 为两个输入元素的乘积。
      %5 = arith.addf %3, %4 : f32
      affine.store %5, %0[%arg3, %arg4] : memref<4096x4096xf32>
    }
  }
}
```

正文在每个 `%arg3/%arg4` 元素的累加前写入0，在函数末释放临时分配；保留原接口和未使用的 `%arg2`，明确它是结构示例，未输出矩阵结果。相应清单14-5也更新，且已经由本地 Pass 实际生成。这里没有执行 `4096³` 次的数值计算。

原循环结构分析还把 `iter_args` 等同于归约，并称识别后“转化为原子归约操作”。实际 [`isLoopParallel`](/opt/llvm-project/mlir/lib/Dialect/Affine/Analysis/AffineAnalysis.cpp:100)在请求归约检测时才识别支持的组合，[Pass 默认选项](/opt/llvm-project/mlir/include/mlir/Dialect/Affine/Passes.td:371)的 `parallel-reductions=false`。`AtomicRMWKind` 是归约种类描述，不能宣称此处直接生成原子硬件操作。

原内存分析称“访问不同内存变量……不存在依赖”“仅需考虑这两条语句”。正文说明新分配和输入指针独立的本例前提；不同 SSA 名称不普遍意味着无别名。实际 [`isLoopMemoryParallel`](/opt/llvm-project/mlir/lib/Dialect/Affine/Analysis/AffineAnalysis.cpp:136)检查所有收集访问的有序对，也包括 store 与自身不同迭代，不只一个读写对；未知副作用会使并行判断失败。对不同 memref 值的直接跳过是当前分析器的局限，不能当作通用别名定理。错误交叉引用14.4.1改为14.5.1。

原关系组合解释“新定义域决定新值域”“两者值域相同……否则不是同一内存位置”，过于接近单值函数理解。正确的是两个访问关系在同一内存坐标上的连接，逆关系可多值，整个值域无需完全相等。表14-6的第1／3行共享 `y1`，第2／4行共享 `y2`；原书说第1／3行共享“y1和y2”不准确，正文逐对更正。

最重要的层次错误在 PDF 第16–17页：

| 原文名称 | 所列顺序条件 | 实际层次 |
| --- | --- | --- |
| “最内层循环” | `dst_arg3≥src_arg3+1` | 深度1，最外层 |
| “内层两个循环” | `dst_arg3=src_arg3`，`dst_arg4≥src_arg4+1` | 深度2，中间层携带依赖 |
| “整个三层循环” | 前两维相等，`dst_arg5≥src_arg5+1` | 深度3，最内层携带依赖 |

正文按 [`addOrderingConstraints`](/opt/llvm-project/mlir/lib/Dialect/Affine/Analysis/AffineAnalysis.cpp:385)的执行逻辑改正，并完整保留表14-4～14-9的8、8、16、14、15、17行。其中表14-8改称最外层15约束，表14-9说明为最内层17约束；没有擅自删掉其重复等式。源文件该函数前方深度2示例写成 `j' > j+1` 的注释也不精确，实际不等式为 `j'−j−1≥0`，即 `j'≥j+1`。

数学结果：深度1、2分别与地址相等条件矛盾；深度3存在证据 `(s3,s4,s5)=(0,0,0)`、`(t3,t4,t5)=(0,0,1)`。本地 C++ API 返回前两层无依赖、最内层有依赖；完整整数采样判该17行系统非空。[parallel-analysis.txt](evidence/ch14/parallel-analysis.txt)保存实际输出（枚举 `0=HasDependence`、`1=NoDependence`），与正文系数逐行一致。

原注意“循环内部定义的局部变量无须分析”更正为当前循环内新分配、在各迭代中独立拥有的内存及其视图。本地 [`isLocallyDefined`](/opt/llvm-project/mlir/lib/Dialect/Affine/Analysis/AffineAnalysis.cpp:124)确实基于分配效果、祖先关系和视图来源检查；本例缓冲区分配在循环外，不能豁免。

## 5. 融合、依赖图、切片边界与成本

清单14-6／14-7、14-8／14-12均在本地实跑复现，主要循环、缓冲区和访问下标与书中一致。对应本地示例见 [loop-fusion.mlir:17](/opt/llvm-project/mlir/test/Dialect/Affine/loop-fusion.mlir:17)、[loop-fusion-2.mlir:621](/opt/llvm-project/mlir/test/Dialect/Affine/loop-fusion-2.mlir:621)。这些输入保留未消费的读取结果，只用于显示 Pass 变换，不是性能基准；不把它们的结构变化当成真实提速测量。

- 原“循环融合首要条件是内存访问存在依赖”“循环并行无依赖，而融合需要依赖”只是此处生产者—消费者例子的观察，不能推广。实际 [LoopFusion.cpp:750](/opt/llvm-project/mlir/lib/Dialect/Affine/Transforms/LoopFusion.cpp:750)也支持 sibling fusion，将共享读取的循环融合。
- 原“以包含load、store操作的基本块为节点”与其表格也冲突。实际 [MemRefDependenceGraph::init](/opt/llvm-project/mlir/lib/Dialect/Affine/Analysis/Utils.cpp:111)针对一个块中的顶层操作建图，包括循环嵌套、顶层读写和有使用者的 SSA 生产者；不是每个基本块一个节点。未使用的 `%c0` 不作为有效生产者节点，表14-10的4个节点正确。
- 图14-1已实际目视：实线 `1→2`、`0→2`、`0→3`、`2→3`，每条有对应反向虚线。Mermaid保留全部8条边；正文说明虚线是反向查询关系，不能误解成约束执行顺序的真环；分配与常量边是 SSA 依赖，不全是内存写读。
- 清单14-9、14-10保留其完整示意代码，修复原符号／排版。第一个读在单次 `i1` 迭代仅需对应的一个源迭代；全外层需求覆盖10～19。第二个读独立需要15～24，不能因有两层循环就把下界改为10。原“上下界并非15和24，而是10和24”是把两个读取需求的合并／包围结果当成第二个读单独推导。正文区分两者，并保持最终真实区间 `[10,25)`。
- 原将融合边界称为“上下界均包含”容易和 Affine 语法冲突。正文明确数学文字 `10～19` 含两端，而 `to 20` 仍为不含上界。
- 原称“若可删除源循环，便将源循环中定义的私有内存变量置于融合后循环中”不是普遍次序与位置要求。实际 [删除判断](/opt/llvm-project/mlir/lib/Dialect/Affine/Transforms/LoopFusion.cpp:78)、[创建私有缓冲区](/opt/llvm-project/mlir/lib/Dialect/Affine/Transforms/LoopFusion.cpp:247)和[融合执行](/opt/llvm-project/mlir/lib/Dialect/Affine/Transforms/LoopFusion.cpp:985)分别有条件，本例分配仍位于外层。

原清单14-11的数值正确，但关键注释不正确，保留如下：

```text
storage reduction factor: 6.67x // 内存写入效率提高6.67倍
src write region size: 400      /* 融合前写内存总量为400字节 */
slice write region size: 60     /* 融合后写内存总量为60字节：融合后循环执行15次 */
```

实际计算见 [LoopFusion.cpp:498](/opt/llvm-project/mlir/lib/Dialect/Affine/Transforms/LoopFusion.cpp:498)及[收益选择](/opt/llvm-project/mlir/lib/Dialect/Affine/Transforms/LoopFusion.cpp:566)：

- 原总计算成本 `100+10×(1+10)=210`。
- 融合后成本 `10×(15+1+10)=260`，额外比例 `(260−210)/210≈23.81%`。
- 源写区域为100个不同元素，400字节；一个切片的写区域为15个不同元素，60字节。比例 `400/60≈6.67` 衡量区域大小。
- 新生产切片在10次外层迭代中各运行15次，实际写入150个 `f32`，累计600字节，比原400字节还多。空间占用和动态访问量不可混同。
- 默认阈值成员值为 `0.30f`，CLI 名 `fusion-compute-tolerance`。正常候选判断为严格 `<`，原“最高不超过30%”改为“低于约30%”。它限制动态操作成本估计，不是源码冗余行数；最大化融合有不同选择路径。
- 实现进一步估计源／目标／融合内存足迹，不能简单描述为“写入字节减少即融合”。[完整实测调试输出](evidence/ch14/fusion-union-debug.txt)含各项数值及选择结果。

## 6. 分块理论和本地实现缺陷

原文称“方向向量所有分量均为正”才可分块，又将 `(3,3)` 迭代中读下标 `(2,2)` 和写下标 `(3,3)` 直接称为两个迭代向量。正文更正：

1. 迭代向量由归纳变量取值组成；同一迭代可读写多个不同下标。清单14-13的生产迭代恰为 `(2,2)`、消费迭代为 `(3,3)`，其距离 `(1,1)` 才是该写后读依赖的距离。
2. 对按字典序调度的常见矩形分块，相关距离分量全非负是一个充分条件；0允许，不必全部严格为正，也不是固定块大小合法性的必要条件。
3. 原“某个方向为负，意味着依赖后面尚未执行的迭代”错误。例如 `(1,−1)` 的依赖仍整体向字典序后方，分块可能重排它，但原程序不因此错误。
4. “MLIR仅处理完美循环”限制为此处的 Affine 分块 Pass，不能泛指所有分块接口。完整块／部分块分离受选项控制。

**本地真实缺陷：** [`checkTilingLegality`](/opt/llvm-project/mlir/lib/Dialect/Affine/Transforms/LoopTiling.cpp:104)的注释声称检查负方向，但实际条件为 `lb.has_value() && ub.has_value() && lb < ub && ub < 0`，漏检固定负距离 `lb==ub<0`。原书的数学规则不能按这段缺陷实现解释为正确。

独立反例和本地运行记录见 [tiling-review.md](evidence/ch14/tiling-review.md)、[run-tiling-check.py](evidence/ch14/run-tiling-check.py)及[输出](evidence/ch14/tiling-runtime-check.json)。程序为 `A[i,j]=A[i−1,j+1]+1`，范围 `i∈[1,5)`、`j∈[0,4)`，真依赖距离 `(1,−1)`；实际 `--affine-loop-tile=tile-size=2` 接受并生成错误顺序，使目标 `(2,1)` 在其生产者 `(1,2)` 之前执行。

证据使用本地 MLIR 降级、`translateModuleToLLVMIR` 导出并验证 LLVM IR，再由宿主 Clang 编译原生执行。全零 `5×5` 输入中，原程序 `A[2,1]=2`，分块后 `A[2,1]=1`，已确认存在语义差异。此结论只针对已测 LLVM18提交，不宣称 LLVM20的对应状态。

## 7. 小结中流水依赖的限定

原小结称“当前MLIR框架在循环流水中尚未支持依赖分析”。本地 [SCF LoopPipelining.cpp:140](/opt/llvm-project/mlir/lib/Dialect/SCF/Transforms/LoopPipelining.cpp:140)由回调取得调度，[verifySchedule:209](/opt/llvm-project/mlir/lib/Dialect/SCF/Transforms/LoopPipelining.cpp:209)检查定义使用顺序，且有受支持的跨迭代依赖处理。因此，正文改为“该工具内部未自动完成通用仿射内存依赖分析和最优流水调度”，不否认已有 SSA 依赖验证。
