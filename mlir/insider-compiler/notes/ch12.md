# 第 12 章精华：把变换、模式和方言定义写成 IR

[校订正文](../insider-compiler-ch12.md) · [读前导读](../guide/ch12.md) · [笔记目录](README.md)

本章基于 LLVM 18.1.8。最重要的区分是：变换策略、局部匹配重写、动态方言定义分别处理什么对象，以及它们如何维护类型、关联与失败契约。

## 1. 元编程工具各自负责什么（12.1～12.3）

| 工具 | 主要输入与用途 | 不应推导出的结论 |
| --- | --- | --- |
| Transform | 通过 handle 选择负载对象，编排和执行变换 | handle 不是运行时指针，也不保证永久有效 |
| PDL | 结构化表示匹配约束及重写动作 | 匹配成功不自动证明任意替换语义等价 |
| PDLL | 更便于编写模式的语言，可生成 PDL | 生成 C++ 包装不等于把模式全部编译为原生 C++ 重写逻辑 |
| PDLInterp | 低层的匹配与重写控制流程 | 模式解释器字节码不同于 MLIR 文件序列化字节码 |
| IRDL | 定义方言中的类型、属性、操作及约束 | 允许未知操作解析，不等于加载了这些定义 |

Transform 可以调用既有变换，PDL 也可以连接原生约束和重写函数；没有要求所有元编程必须依次通过这五项工具。

## 2. Transform 的状态与生命周期（12.1.1～12.1.4）

变换 IR 操作的是负载 IR。`TransformState` 维护 handle 到负载操作列表、负载值列表或参数属性列表的关联。一个 handle 可以关联多个对象，不同 handle 也可以关联同一对象。类型化 handle 的约束要对实际关联对象检查，而不只检查变换 IR 的文本类型。

生命周期的重点是**消费**。操作 handle 被消费后，相关别名，以及指向其嵌套操作和相关值的 handle 可能一并失效；值 handle 的消费同样会影响别名，并按该值来自操作结果还是块参数扩展失效范围。不能只删除一个映射键，就假定其他关联仍安全。

消费不等于删除负载操作：某个变换可以使旧 handle 失效，同时为仍然存在的操作返回新 handle。普通只读查询可以复用有效 handle；完成会消费输入的变换后，应沿它返回的结果继续。解释器的检查能发现受支持情形下的错误使用，但实现自定义变换仍须准确声明效果、维护映射。

| 资源 | 常见效果 | 含义 |
| --- | --- | --- |
| `TransformMappingResource` | `Read` | 查询已有 handle 关联 |
| 同上 | `Read`＋`Free` | 消费输入 handle |
| 同上 | `Allocate`＋`Write` | 建立输出 handle 关联 |
| `PayloadIRResource` | `Read` / `Write` | 查询或修改负载 IR |

这里记录的是编译器变换的效果；负载程序运行时是否读写、分配内存，是另一层语义。例如调整一次 load 的位置属于对负载 IR 的修改，不等于解释器此时真的读取了该 load 的运行时地址。

## 3. 失败不是统一的回滚机制（12.1.3、12.1.5～12.1.6）

`DiagnosedSilenceableFailure` 区分成功、可抑制失败和确定失败。可抑制失败适合表达模式或前提不适用，使外层控制结构按约定处理；确定失败表示不能按普通可恢复方式继续。**抑制诊断或传播失败都不自动撤销已经修改的负载 IR。** 遍历多个目标时，后一个失败也不保证前几个目标恢复原状。

自定义变换通常实现：

```cpp
DiagnosedSilenceableFailure apply(
    TransformRewriter &rewriter,
    TransformResults &results,
    TransformState &state);
```

执行顺序可以记成：读取并检查目标关联，执行适用的变换，经 rewriter 维护修改，把产生的负载对象写入 results，并返回诊断状态。不要把所有运行时结果检查都想成在修改前一次完成。

`TransformEachOpTrait` 对关联列表逐个调用 `applyToOne()` 并汇总结果；它不替实现者证明对全部目标的语义。`MatchOpInterface` 表达对负载只读的匹配契约，部分组合操作会检查此接口。特质可以提供公共逻辑，操作仍须满足准确的接口与副作用要求。

一个容易误读的例子是 `func.func`：函数签名有返回类型，不意味着函数定义操作本身具有同样的 SSA results。`get_result` 查询的是负载操作的实际结果值；要取得函数体中的计算结果，应先选中产生该结果的操作。

## 4. PDL 的重写正确性在哪里保证（12.2）

常见路径为 PDLL → PDL → PDLInterp → 模式解释器内部字节码，并在重写驱动中执行。`FrozenRewritePatternSet` 使用的模式字节码与保存、加载 MLIR 文件的二进制格式是不同机制。PDLL 的 C++ 输出可以把 PDL 嵌入程序；它没有因此改变模式的执行语义。

阅读模式要分别列出结构、类型和语义前提。例如把某操作替换成第一个操作数，至少要求结果与替换值类型相容；更关键的是该操作在已匹配条件下确实等价于这个值。只匹配操作名、两个输入和一个输出，不能证明任意运算可以删除。复杂条件可以注册原生 C++ 约束，实际改写也可以调用原生重写函数，但这些函数的契约仍由作者负责。

## 5. IRDL 约束的“同一个值”（12.3）

IRDL 本身是已经注册的描述方言，使用它写出的新方言定义还需动态加载。加载后，新操作按所定义的操作数、结果和参数约束验证。未注册模式仅允许接受未知语法结构，不提供这套语义验证。

若定义中的同一个 SSA 约束值先选择 `f32` 或 `f64`，再用于多个操作数和结果，它约束这些位置使用同一具体类型。分别创建两个“可为 f32 或 f64”的约束值，则不自动建立相同绑定。这个区别类似逻辑变量的复用，直接决定混合精度输入是否应被拒绝。

本地 `any_of` 的匹配有贪心限制，对有重叠的备选并非一般回溯搜索；`c_pred` 也不是允许运行任意 C++ 文本的运行时求值器。先判断 IRDL 定义语言和加载器支持什么，再判断负载是否符合定义。

## 6. 三种扩展机制分开记（12.1.7）

| 机制 | 改变什么 |
| --- | --- |
| `TransformDialectExtension` | 注册新的 Transform 操作或类型，声明依赖方言与可能生成的方言 |
| `ConvertToLLVMPatternInterface` | 为方言收集到 LLVM 方向的转换模式；不同于最终 LLVM IR 翻译接口 |
| `ExternalModel` | 为既有操作附加接口实现，例如 arith.select 的缓冲区所有权释放接口 |

清单中的 arith.select 模型实现 `BufferDeallocationOpInterface`，依据两分支所有权信息选择指示值或使用通用处理。它不是 `BufferizableOpInterface`，也不是运行时替换 select 机器代码。较新 IRDL 扩展在本地不存在时，保留机制与版本边界，不能据名称推断它直接向 IRDL 方言添加操作。

复习时应能对一条变换链同时写出 handle 生命周期、负载修改和失败后的状态，并说明每个模式的语义前提。已有解析、解释执行和预期失败证据见[本章校订记录](../issues/ch12.md)。
