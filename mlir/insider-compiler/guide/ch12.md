# 第 12 章导读：元编程方言

[校订正文](../insider-compiler-ch12.md) · [精华笔记](../notes/ch12.md) · [导读目录](README.md)

本章把编译器自身的工作也表示为 IR：如何选择待处理操作，怎样安排变换，如何描述匹配与重写，以及怎样在运行时定义新方言。读前先分清四件事：Transform 编排变换，PDL/PDLL 描述模式，PDLInterp 执行模式匹配流程，IRDL 定义方言结构。它们可以协作，但并不是一条必经的四级降级链。

## 需要的背景

先回顾第 4～6 章的操作定义、模式重写与 Pass。模式通常描述“匹配一个局部结构，满足条件后怎样改写”；Pass 决定在哪些 IR 上运行哪些处理。Transform 增加一套可组合的调度表示，让策略能成为独立 IR，而具体变换仍可由 C++ 实现。

还需要区分**负载 IR**与**变换 IR**。前者是被编译的程序，后者描述如何修改前者。Transform 中的 handle 是解释器状态里的一项关联，可以对应多个操作或值；它不是待编译程序运行时的指针，也不是某个 C++ 对象的永久身份。

最后补一个资源观念：对 handle 的“消费”意味着后续使用受到限制，并不必然删除对应操作；即使操作仍在，新 handle 也可能才是合法入口。副作用接口记录这些关系，是调度和诊断契约的一部分。

## 原章的三个关注点

读 **12.1.1～12.1.4** 时，先追踪 `TransformState` 里的关联，再看操作名称。每一步都问：读了哪些 handle，消费了哪些，返回哪些新关联，负载 IR 改了什么？重点读 **12.1.3** 的失败与副作用：可抑制失败不是事务回滚，失败前的变换可能已经发生。

读 **12.1.5～12.1.7** 时，再看接口怎样实现契约。这里出现的三种扩展分别涉及 Transform 操作注册、转换模式接口、既有操作的外部接口模型；不能仅因都叫“扩展”就视为一种机制。

读 **12.2** 时，从一个“匹配后替换”的完整模式入手，沿 PDLL、PDL、PDLInterp 理清表示层次。检查形状和类型只是匹配条件的一部分，语义等价仍需模式作者保证。最后读 **12.3**：IRDL 描述的新操作经动态加载后获得验证规则；允许未知操作解析，并不等于已经定义和验证了新方言。

## 阅读时自测

- 对同一个负载操作创建两个 handle，消费其中一个后，另一个是否还能用？嵌套操作呢？
- 匹配失败、变换部分成功后失败、解释器无法继续，应该如何区分？
- 一个 PDLL 文件生成 C++，是否意味着模式已经变成原生 C++ 重写代码？
- 重复使用同一个 IRDL 约束值，与分别创建两个同类型约束值有什么不同？

读完回到第 9～11 章，尝试把已有优化写成“选择目标—应用变换—传递新 handle”的流程。第 13 章则提供更长的实际流水线，可用于思考哪些选择适合做成可调策略。涉及 API 时以正文标明的 LLVM 18.1.8 实现为准。
