# 第 7 章精华笔记：优化收益必须有合法性依据

[校订正文](../insider-compiler-ch7.md) · [读前导读](../guide/ch7.md) · [笔记目录](README.md)

## 1. 十一种技术的职责与边界

| 小节 | 技术 | 收益与关键前提 |
| --- | --- | --- |
| 7.1 | 操作数排序 | 对声明可交换的操作统一顺序，便于匹配；相同排序键保持稳定，不任意交换操作数 |
| 7.2 | 归一化 | 通过操作及方言的模式、fold 简化 IR；程序正确性不能依赖先运行 canonicalize |
| 7.3 | 控制流下沉 | 将只在目标区域使用的纯计算移入其中；区域至多执行一次，操作数仍须支配使用 |
| 7.4 | CSE | 复用等价计算；考虑支配、内存效果与中间写入，不能只比操作名 |
| 7.5 | 运行时验证 | 由 `RuntimeVerifiableOpInterface` 生成运行时检查；与静态 verifier 不同 |
| 7.6 | LICM | 移出循环不变计算；除操作数循环外可用、无内存副作用外，还须可安全投机执行 |
| 7.7 | mem2reg | 消除可提升内存槽的 load/store，以 SSA 表示内容；所有相关使用都须可处理 |
| 7.8 | 拓扑排序 | 将适用图区域中的操作按依赖排序；有环关系没有普通拓扑序 |
| 7.9 | SROA | 将聚合槽拆为实际使用的子槽；整体访问和间接使用也必须可安全处理 |
| 7.10 | 内联 | 消除调用并暴露优化机会；需要调用解析、方言合法性、递归控制及符号保留判断 |
| 7.11 | SCCP | 联合常量与路径可执行性，得到比只合并所有前驱更精确的常量结果 |

这 11 类不都是独立生产 Pass：7.1 的排序由模式填充函数提供，7.8 的例子涉及测试方言。LLVM 18.1.8 的实际入口应以正文命令为准。

## 2. 代码移动和消除的常见误判（7.2～7.6）

没有实现内存效果接口，不代表没有效果；未知行为需要保守处理。无内存副作用也不等于可投机执行：循环可能执行零次，提前执行原本不会发生的异常计算可能改变行为。因此下沉和外提具有不同的证明义务。

CSE 的等价比较涉及操作名、类型、属性、properties、操作数及相应区域结构，忽略位置信息，并非要求结果 SSA 名字相同。读取内存的操作只在受支持且没有干扰写入的条件下合并。候选操作自身含多块区域的限制，不等于 CSE 无法遍历一个多基本块函数。

归一化可用 `hasCanonicalizer` 提供模式集合，或用 `hasCanonicalizeMethod` 提供单个方法；`hasFolder` 提供受限的折叠。fold 不任意创建新操作，常量物化由驱动器完成。删除无用途操作同样要确认可以安全删除。

## 3. mem2reg 与 SROA 的配合（7.7、7.9）

mem2reg 提升的是**内存槽的内容**；表示地址的值原本就可以是 SSA。它不是 MemorySSA 分析，也不是后端寄存器分配。

1. 从分配接口取得候选槽，检查访问及阻塞使用能否处理。
2. 根据定义位置、活跃性和迭代支配边界，确定需要汇合值的基本块。
3. 用块参数表达汇合，沿控制流传播到达定义，更新分支传值并以已知值替换读取。
4. 通过接口删除访问及原分配，维护依赖顺序。

`PromotableAllocationOpInterface` 描述候选分配，`PromotableMemOpInterface` 描述读写，`PromotableOpInterface` 参与移除阻塞使用。不能只因出现 load 就断定该块入口需要合并值：同块中更早的 store 可能已提供定义。

SROA 先用 `DestructurableAllocationOpInterface`、`DestructurableTypeInterface` 及访问接口识别子槽，再为实际使用的字段创建分配并重接访问。例如数组只用第三个元素，可转成一个元素槽；随后 mem2reg 才有机会消除这个槽。拆分聚合并不等于已经消除了内存。

## 4. 内联的两个安全网（7.10）

调用操作和可调用体分别通过 `CallOpInterface`、`CallableOpInterface` 提供结构；`DialectInlinerInterface` 处理合法性、终止操作及必要的类型衔接。内联器按调用图 SCC 自底向上处理，用调用点祖先内联历史和迭代限制约束递归展开，不是全局规定每个函数只能内联一次。

外部可见函数可以被内联，但通常仍须保留定义供外部调用。更新实参、返回值和控制流之后，是否删除被调用者是另一个问题。

## 5. SCCP 是两项分析的共同不动点（7.11）

稀疏常量传播沿 SSA 定义—使用关系传播；死代码分析根据已知条件标记可执行块和边。前者提供条件常量，后者决定哪些路径参与合并，两者互相唤醒。

常量状态可记为“未初始化 → 某个已知常量 → 未知常量值”。相同常量 join 后保持原值，冲突常量合并为未知。例如汇合处两条边分别传入 1 和 2，若两边均可执行则结果未知；若只有传入 1 的边可执行，便可确定结果为 1。

对传播关系可写成：

$$
S_{i+1}(q)=S_i(q)\sqcup f_{\mathrm{op}}(S_i(p)).
$$

`DataFlowSolver` 记录状态与分析访问之间的依赖，状态变化才安排相关任务，直至不动点。组合分析读取彼此状态，不是把各自转移函数做集合交。稀疏/稠密区分状态如何依附 SSA 值或程序点；跨过程、流敏感和上下文敏感是另外的维度。

SCCP Pass 求解后物化常量、替换使用并清理无用操作，但不保证顺便删除全部不可达基本块。需要的控制流清理仍应明确安排。
