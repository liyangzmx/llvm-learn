# 第5章精华笔记：调度边界与分析生命周期

[原章](../insider-compiler-ch5.md) · [配套读前导读](../guide/ch5.md) · [笔记目录](README.md)

依据本地 LLVM18.1.8 校订正文整理。Pass 系统管理的是编译器对 IR 的工作，不是目标程序中各操作的执行顺序。

## 1. 三层管理对象（5.1）

| 对象 | 职责 | 关键区分 |
| --- | --- | --- |
| Pass | 在当前锚点上执行一次处理 | 业务主体是 `runOnOperation()` |
| OpPassManager | 描述某种锚点上的有序流水线，可进一步嵌套 | 实际 C++ 类不是模板 |
| PassManager | 继承 OpPassManager，增加顶层运行与管理能力 | 负责执行、相关准备与插桩等 |

嵌套 OpPassManager 通过适配器 Pass 接入父流水线，所以一条流水线可混合当前操作上的 Pass 与对子操作运行的流水线。嵌套适配器选择直接子操作，更深层由继续嵌套的管理器处理；`nestAny()` 不等于递归处理所有后代。

## 2. 锚点决定工作范围，过滤决定适用性（5.1.1、5.1.4）

`OperationPass<ConcreteOp>`限制操作类型；`OperationPass<>`不指定一种具体类型；`InterfacePass`可按接口限定对象。通用并不等于任意：锚点必须已注册、具备 `IsolatedFromAbove`，并满足静态调度条件。

通用流水线能否用于一种操作类型，取决于其中**所有 Pass 的过滤条件交集**。不是先运行适用的 Pass，再跳过其余。对指定锚点的流水线，若加入不支持该锚点的 Pass，准备阶段会报错。

同一锚点上，流水线内部按既定顺序运行。串行处理多个同类型操作时，可以先完成一个操作的整条流水线，再处理下一个；并行时不同操作可交错。框架可能合并相邻嵌套适配器并整理子管理器顺序，但不会替用户推导正确的优化顺序，也不任意重排普通 Pass。

文本流水线的顶层必须匹配实际根操作。`mlir-opt`默认添加隐式module，因此处理函数常需写完整的 `builtin.module(func.func(...))` 层级；源文件第一行是函数，不代表工具运行时根节点一定是函数。

## 3. 定义、名字注册与方言准备（5.1.2～5.1.3）

TD 描述名称、摘要、选项、统计项、依赖方言及构造器，生成公共基类和注册辅助；实际变换仍由具体 Pass 实现。统计字段也需要实际更新，声明不会自动统计业务事件。

Pass/Pipeline 的名字注册在进程全局注册表中，供命令行和文本流水线查找；这与 context 中的方言和操作元数据不同。直接由C++工厂函数创建 Pass 再 `addPass()`，不要求先注册名字。

`dependentDialects`或`getDependentDialects()`用于在执行前准备将创建的方言实体，尤其避免并行执行过程中临时加载。依赖列表不是方言白名单；“已登记可加载”也不同于“已经加载”。

## 4. 线程边界是 Pass 的正确性条件（5.1.5）

| 行为 | 约束与原因 |
| --- | --- |
| 检查同级操作及其内部状态 | 不允许；其他线程可能正修改它们 |
| 检查祖先状态 | 可以，但须遵守相应只读边界 |
| 修改 IR | 主要限于当前操作内部；当前操作自身仅有属性修改的例外 |
| 保存跨 `runOnOperation()` 的可变历史 | 不可依赖；实例可被复制，执行对象与顺序不固定 |
| 使用全局可变 Pass 状态 | 不允许；会破坏并行独立性 |
| 复制 Pass | 必须可复制构造，供并行调度使用 |

隔离特质只负责 SSA 捕获边界，并不能替代这些规则。使用重写器也不会扩大 Pass 的权限。跨函数变换应选择能覆盖所需 IR 的合适上层锚点，再在该范围内处理。

## 5. 插桩观察事件，不代替业务（5.1.6～5.1.7）

多个插桩先注册A、再注册B，则对应的 before 顺序为A、B，after顺序为B、A，形成嵌套。Pass成功后调用 `runAfterPass`，失败则调用 `runAfterPassFailed`，两者互斥；`runAfterPipeline`在该流水线结束后执行，包括失败路径。

分析首次计算会产生 `runBeforeAnalysis`/`runAfterAnalysis`事件，依赖分析的计算可以嵌套其中；命中缓存不应被当作又完成一次分析计算。框架对这些回调串行化保护，不意味着回调外的任何共享状态都安全。

| 排查任务 | 机制与前提 |
| --- | --- |
| 找出耗时步骤 | `enableTiming()` / `mlir-timing`；区分并行与串行统计 |
| 观察 IR 改动 | before/after打印；`after-change`需配合after选择项 |
| 打印当前锚点外的完整模块 | `mlir-print-ir-module-scope`需禁用线程 |
| 保存完整失败条件 | 完整crash reproducer，可支持并行 |
| 保存失败前局部流水线 | local reproducer需禁用线程 |

复现文件携带 IR、流水线和配置；它不是所有执行历史的录像。原书的格式示例在本地成功运行，因此不能把“展示复现格式”误读为“该输入已证明能触发失败”。

## 6. 分析缓存的有效期要由变换负责（5.2）

MLIR 分析是独立类，由 AnalysisManager 按需构造与缓存，不是必须显式插入流水线的变换 Pass。分析只能读取 IR。构造器可接收操作，也可额外接收 AnalysisManager 以请求依赖分析。

| API | 缺少缓存时是否计算 |
| --- | --- |
| `getAnalysis` | 是，对当前操作 |
| `getChildAnalysis` | 是，对指定子操作 |
| `getCachedAnalysis` | 否 |
| `getCachedParentAnalysis` | 否，不能由此触发祖先分析 |
| `getCachedChildAnalysis` | 否 |

生命周期应这样理解：首次查询产生结果，同一 Pass 内重复查询通常复用；Pass 结束时，管理器依据保留集合及自定义失效规则处理缓存。默认未保留的分析会失效，但 `isInvalidated(PreservedAnalyses)` 可以定义更细的规则，返回 `true` 表示失效；有分析依赖时也必须检查依赖是否仍有效。

`markAnalysesPreserved`和`markAllAnalysesPreserved`是“这些结果仍正确”的声明，不会更新旧结果。同一 Pass 内若已经修改 IR，再次查询也不能假设管理器自动重算。更不能在错误地标记保留后期待 verifier 修复分析缓存；分析正确性需要与变换的修改范围一起判断。
